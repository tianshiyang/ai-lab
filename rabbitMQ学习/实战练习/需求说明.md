# 统一消息通知中心 —— RabbitMQ 实战练习

## 这是什么

企业里几乎每个中台都有一个"通知中心"：业务方（订单、账号、营销）只管提交一个"我要给谁发什么"的请求，通知中心负责按用户订阅关系裁剪通道、渲染模板、调三方网关（短信/邮件/站内信）、失败重试、限速、失败留档。

这是 RabbitMQ 在企业里最典型的落地形态，一个场景能把常用能力全串起来。

**练习方式**：分 5 个练习递进，每个练习给需求 + 验收标准，代码你自己写。所有数据在 `data/` 下，所有故障通过改 `data/mock_config.json` 触发，不需要命令行参数，PyCharm 直接点运行。

---

## 数据文件

| 文件 | 内容 |
| --- | --- |
| `data/users.json` | 8 个用户，含 `channels`（该用户订阅了哪些通道） |
| `data/templates.json` | 5 个模板，含 `priority`（优先级）、`allow_channels`（该模板允许哪些通道）、带 `{占位符}` 的正文 |
| `data/requests.json` | 12 条通知请求，每条有 `note` 说明它要验证什么 |
| `data/mock_config.json` | 网关耗时/限速、故障注入规则、批量数量、消费端开关、重试阶梯 |

三个可能踩坑的地方：

- **通道要取交集**：模板的 `allow_channels` ∩ 用户的 `channels`。REQ-0003 交集只剩 `email`，REQ-0004 交集为空。
- **`requests.json` 里有两条 `REQ-0005`**，内容一样，是故意的，用来验证幂等。
- **`fail_rules` 是按 `(request_id, channel)` 匹配的**，`fail_times: 2` 指前两次调用失败、第三次成功；这个计数必须能跨进程重启保留。

环境沿用现有的：pika + `.env` 里的 `RABBITMQ_URL`，落库用 SQLite（文件放本目录并 gitignore）。资源命名统一加 `ai_lab.notify.` 前缀，跟已有教程资源分开。

## 练习一：扇出 + 通道路由

**目标**：一条通知请求，按通道拆成多条投递任务，各通道消费者独立消费。

### 核心动作：算交集

这是练习一唯一需要动脑的地方。每条请求能发到哪些通道，受两个约束：

- **模板允许哪些通道**（`templates.json` 的 `allow_channels`）——验证码模板只允许短信，不能发到站内信
- **用户订阅了哪些通道**（`users.json` 的 `channels`）——用户没开邮件通知，就不能给他发邮件

有效通道 = 两者取**交集**。看数据里的四条：

| 请求 | 模板允许 | 用户订阅 | 交集 → 发几条消息 |
| --- | --- | --- | --- |
| REQ-0001 | `[sms]` | U001 `[sms,email,inapp]` | `[sms]` → **1 条** |
| REQ-0002 | `[sms,email,inapp]` | U006 `[sms,email,inapp]` | 三个都在 → **3 条** |
| REQ-0003 | `[sms,email,inapp]` | U003 `[email]` | `[email]` → **1 条** |
| REQ-0004 | `[sms,email]` | U005 `[inapp]` | 空 → **0 条**，但要落"无可用通道"记录 |

一条请求可能变成 0 条、1 条或 3 条消息，这就是"扇出"：请求一条，投递任务多条。

### 数据流

```
requests.json ──┐
users.json    ──┼──► 生产者：算交集、渲染模板
templates.json ─┘         │
                          │ 每个有效通道一条消息
                          ▼
              topic 交换机 ai_lab.notify.events
                routing key = notify.<biz_type>.<channel>
                 例：notify.verify_code.sms
                          │
        ┌─────────────────┼─────────────────┐
        │ notify.*.sms    │ notify.*.email  │ notify.*.inapp
        ▼                 ▼                 ▼
    sms 队列          email 队列         inapp 队列
        │                 │                 │
        ▼                 ▼                 ▼
   sms 消费者         email 消费者      inapp 消费者
   sleep 0.5s         sleep 1.0s        sleep 0.1s
   落发送记录          落发送记录         落发送记录
```

routing key 拼成两段是有原因的：消费者按通道订阅用 `notify.*.sms`；将来产品说"营销类单独限流"，你用 `notify.marketing.*` 再绑一个队列即可，已有代码一行不改。这就是 topic 相比 direct 的价值——一个 key 承载两个维度，订阅方按需挑。

### 要写的程序

| 文件 | 干什么 | 怎么跑 |
| --- | --- | --- |
| `topology.py` | 声明 1 个 topic 交换机、3 个队列、3 条绑定，均持久化 | 建一次，之后重复跑不报错即可 |
| `producer.py` | 读三个 json，for 循环每条请求：查用户 → 查模板 → 算交集 → 渲染 `{占位符}` → 每个通道 publish 一条 | 想灌数据就跑 |
| `consumer.py` | 顶部写 `CHANNEL = "sms"`，只消费对应队列；按 `mock_config` 的 `send_seconds` sleep 模拟调网关，然后落库 | 改常量的值，在 PyCharm 开 3 个运行窗口 |

消费者不用写三份，一份改常量开三个进程即可，这也正好满足"不用命令行传参"。

落库一张表够用：`task_id`（唯一）、`request_id`、`user_id`、`channel`、`content`、`sent_at`。

消息体至少含：`task_id`、`request_id`、`user_id`、`channel`、`title`、渲染后的 `content`、`biz_type`、`priority`。渲染放生产端还是消费端你自己定，但要在验收记录里说明选了哪种、为什么。

### 本练习先不管的事

- 三条错误请求（REQ-0007 模板不存在、REQ-0008 缺 `{coupon}` 参数、REQ-0009 用户不存在）：先 try/except 打印跳过，正式处理是练习二。
- REQ-0006 的 `delay_seconds: 15`：先忽略，练习五再做。
- REQ-0005 在文件里出现两次，练习一会老实发两遍，**这是对的**，幂等是练习二加的。

### 验收

1. 消费者全关，跑一遍生产者，三个队列 Ready 应为 **sms 7 / email 5 / inapp 5**。先自己按数据算一遍再对答案，对不上就是交集逻辑错了。
2. 只启动 sms 消费者，只有 sms 队列被消费，另两个队列 Ready 纹丝不动——这一步证明绑定键写对了。
3. 三个消费者都启动后队列清空，发送记录里每条 `(request_id, channel)` 都能对上。
4. 交换机、队列持久化，消息持久化；重启 RabbitMQ 后未消费的消息还在。
5. 重复运行 `topology.py` 不报错、不清空已有消息。

## 练习二：手动 ack + 幂等 + 优先级

**目标**：不丢不重，且重要消息插队。

需求：

1. 关自动 ack，发送成功并落库后才 ack。
2. `(request_id, channel)` 做数据库唯一约束，重复投递不重复发送——REQ-0005 提交了两次，最终只能发一次。
3. 消费者再次收到已成功的任务，要 ack 掉它（否则会一直循环），但不重复调网关。
4. 三个永久错误请求（REQ-0007 模板不存在、REQ-0008 缺占位符参数、REQ-0009 用户不存在）要在提交阶段或消费阶段被判定为永久失败，落失败记录，**不进重试**。
5. sms 队列启用优先级（`x-max-priority`），消息带上模板的 `priority`。验证方式：先让 sms 消费者停着，用 for 循环塞 `batch.marketing_count` 条营销通知（priority=1），再塞 `batch.verify_code_count` 条验证码（priority=9），然后启动消费者。
6. 用 `consumer.pause_before_ack_seconds` 制造"已发送但还没 ack 就被杀"的场景。

**验收**：

1. 生产者连续跑 3 遍 `requests.json`，发送记录条数不变。
2. 优先级验证：验证码消息应该在营销消息前面被消费掉（不要求严格全部靠前，但明显插队）。想一想为什么必须 `prefetch_count=1` 才看得出效果——把它改成 50 再跑一次，对比现象并记下来。
3. 设 `pause_before_ack_seconds=10`，等它打印"已发送"后在 PyCharm 停掉进程；重启消费者，该消息被重投，但**没有发第二次**（网关调用次数不增加），最后正常 ack。
4. 三个永久错误请求：失败记录里能查到原因，且重试次数为 0。

## 练习三：有限重试 + 死信归档

**目标**：临时故障自动恢复，恢复不了的进死信留档。

重试阶梯用 `mock_config.retry.backoff_seconds`（5s / 15s / 60s），即首次 + 3 次重试，最多 4 次尝试。

需求：

1. 区分两类错误：临时（网关超时、连接拒绝）走重试，永久（模板/参数/用户问题）直接失败。
2. 用 TTL + DLX 做延迟重试：给每一级 backoff 建一个延迟队列，队列上设 `x-message-ttl` 和 `x-dead-letter-exchange`，消息过期后被死信转发回业务队列。
3. 尝试次数持久化，不能存内存——进程重启后 REQ-0010 不能从第一次重新数。
4. 重试次数耗尽后，消息进 `<channel>.failed` 死信队列，同时落一条最终失败记录（含原始消息、错误、尝试次数）。
5. 一个通道的重试只回到该通道队列，不能重新扇出到其他通道。

`fail_rules` 已经配好两条：REQ-0010 的 sms 前两次失败第三次成功，REQ-0011 的 email 永远失败。

**验收**：

1. REQ-0010：日志里能看到 3 次尝试、两次等待（5s、15s），第三次成功；同一请求的其他通道不受影响，不会被重试波及。
2. REQ-0011：4 次尝试后停止，`email.failed` 队列有 1 条，最终失败记录可查。
3. 第二次重试等待期间（15s 那段）停掉消费者再启动，尝试次数仍是 2，不是 0。
4. 想清楚一件事并写进记录：TTL 延迟队列有个"队头阻塞"特性——如果一个延迟队列里前面压着一条 60s 的、后面来一条 5s 的，会发生什么？为什么按 backoff 分级建队列能绕过它？

## 练习四：并发消费 + prefetch 限速

**目标**：多实例分工，且不把下游网关打爆。

`mock_config.gateway` 给每个通道配了 `rate_limit_per_sec`。email 只允许 2/秒，这个限制要靠消费端压住。

需求：

1. 同一个 email 队列启动 2 个消费者实例，每个实例有可区分的标识（进程 ID 或启动时生成的短 ID），日志里带上。
2. 用 for 循环生成 `batch.concurrent_orders` 笔发货通知（模板 TPL_ORDER_SHIPPED，用户在 users.json 里轮转），提交后观察两个实例的分工。
3. 通过 `prefetch_count` + 消费端节流，让实际发送速率不超过 `rate_limit_per_sec`。超速要能被检测出来（比如记录每次发送的时间戳，事后统计每秒条数）。
4. 中途停掉一个实例，另一个要能接着处理，未 ack 的消息被重投。

**验收**：

1. 20 笔通知，两个实例都处理了一部分（不要求均分），发送记录总数 20，无重复。
2. 统计发送时间戳：email 通道任意 1 秒窗口内不超过 2 条。
3. 停掉实例 A 后，它手上未 ack 的消息被实例 B 处理，最终总数还是 20。
4. `prefetch_count` 设成 1 和设成 20，各跑一遍，记录两次的分工差异和总耗时差异，说明这个参数实际在控什么。

## 练习五：延迟发送 + 运行观察

**目标**：定时/延迟投递，以及能说清系统当前状态。

需求：

1. REQ-0006 带 `delay_seconds: 15`，要求提交后 15 秒才真正投到业务队列。用 TTL + DLX 实现（可以复用练习三的延迟机制，也可以单独建一个延迟入口）。
2. 一个状态检查程序，输出：各队列 Ready / Unacked、待发延迟中的数量、各通道成功数、重试等待中的数量、最终失败数。
3. 日志字段至少含：`task_id`、`request_id`、`channel`、当前尝试次数、结果、耗时、错误类型、消费者实例标识。同一个 `request_id` 从提交到最终成功/失败能在日志里串起来。
4. 不打印凭据，异常提示里不要带含密码的连接 URL。

**验收**：

1. REQ-0006 提交后立即看队列：业务队列没有它，延迟队列有；约 15 秒后业务队列出现并被消费。误差几秒可以接受。
2. 状态检查能区分这几种状态：延迟等待中、待消费、处理中（unacked）、重试等待中、已成功、最终失败。
3. 清空数据库和队列后完整跑一遍全部 12 条请求，输出一份验收记录：每条请求的最终结果 + 它验证了哪个能力点。

## 通过标准

同一批请求，在重复提交、消费者重启、临时故障、限速压制之后，仍然：每个 `(request_id, channel)` 恰好发送一次，永久错误有据可查，临时故障能自愈或进死信留档，任意时刻能说清每条请求处于哪个状态。
