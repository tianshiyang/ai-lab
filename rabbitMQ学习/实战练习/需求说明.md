# 统一消息通知中心 —— RabbitMQ 实战练习

## 这是什么

企业里几乎每个中台都有一个"通知中心"：业务方（订单、账号、营销）只管提交一个"我要给谁发什么"的请求，通知中心负责按用户订阅关系裁剪通道、渲染模板、调三方网关（短信/邮件/站内信）、失败重试、限速、失败留档。

这是 RabbitMQ 在企业里最典型的落地形态，一个场景能把常用能力全串起来。

**练习方式**：分 5 个练习递进。每个练习只写**要做什么**和**怎么算做对**，具体方案自己设计。所有数据在 `data/` 下，所有故障通过改 `data/mock_config.json` 触发，不需要命令行参数，PyCharm 直接点运行。

**做完一个练习，就让 Claude 按验收标准检查一遍**（练习一、练习二这样依次来）。哪个任务看不懂，直接说，Claude 会把更具体的说明补进这份文档。

环境：**aio-pika**（RabbitMQ 的全异步客户端）+ `.env` 里的 `RABBITMQ_URL`。练习一的 demo01 是 pika 版的，留着当对照——AMQP 的声明两边是同一套，拓扑互相兼容。资源命名统一加 `ai_lab.notify.` 前缀，跟已有教程资源分开。

**已备好、直接用（不是练习内容）**：

| 文件 | 职责 |
| --- | --- |
| `db.py` | 数据库连接配置（连接串、引擎、会话工厂），直接运行是连接自检 |
| `models.py` | 三张表的模型声明；改表要走 alembic，不许手写 DDL |
| `store.py` | 全部数据库读写（都是 async 函数），直接运行是自检 |
| `alembic/` | 建表改表：`uv run alembic upgrade head` |

查库最方便的方式：PyCharm 的 Database 面板连上去，验收 SQL 直接在里面跑。

## 数据文件

| 文件 | 内容 |
| --- | --- |
| `data/users.json` | 8 个用户，含 `channels`（该用户订阅了哪些通道） |
| `data/templates.json` | 5 个模板，含 `priority`（优先级）、`allow_channels`（该模板允许哪些通道）、带 `{占位符}` 的正文 |
| `data/requests.json` | 12 条通知请求，每条有 `note` 说明它要验证什么 |
| `data/mock_config.json` | 网关耗时/限速、故障注入规则、批量数量、消费端开关、重试阶梯 |

三个可能踩坑的地方：

- **通道要取交集**：模板的 `allow_channels` ∩ 用户的 `channels`。REQ-0003 交集只剩 `email`，REQ-0004 交集为空。
- **`requests.json` 里有两条 `REQ-0005`**，内容一样，是故意的，用来验证幂等。
- **`fail_rules` 是按 `(request_id, channel)` 匹配的**，`times: 2` 指前两次调用失败、第三次成功；这个计数必须能跨进程重启保留。

## 练习一：扇出 + 通道路由

### 目标

一条通知请求，按通道拆成多条投递任务，各通道消费者独立消费。

### 规则：有效通道 = 模板允许 ∩ 用户订阅

每条请求能发到哪些通道，受两个约束：模板允许哪些通道（`allow_channels`），用户订阅了哪些通道（`channels`）。看数据里的四条：

| 请求 | 模板允许 | 用户订阅 | 交集 → 发几条消息 |
| --- | --- | --- | --- |
| REQ-0001 | `[sms]` | U001 `[sms,email,inapp]` | `[sms]` → **1 条** |
| REQ-0002 | `[sms,email,inapp]` | U006 `[sms,email,inapp]` | 三个都在 → **3 条** |
| REQ-0003 | `[sms,email,inapp]` | U003 `[email]` | `[email]` → **1 条** |
| REQ-0004 | `[sms,email]` | U005 `[inapp]` | 空 → **0 条**，但要打印"无可用通道" |

一条请求可能变成 0 条、1 条或 3 条消息，这就是"扇出"。

### 数据流

```
requests.json ──┐
users.json    ──┼──► 生产者：算交集、渲染模板
templates.json ─┘         │
                          │ 每个有效通道一条消息
                          ▼
              topic 交换机 ai_lab.notify.events
                routing key = notify.<biz_type>.<channel>
                 例：notify.verify_code.sms
                          │
        ┌─────────────────┼─────────────────┐
        │ notify.*.sms    │ notify.*.email  │ notify.*.inapp
        ▼                 ▼                 ▼
    sms 队列          email 队列         inapp 队列
        │                 │                 │
        ▼                 ▼                 ▼
   sms 消费者         email 消费者      inapp 消费者
   sleep 0.5s         sleep 1.0s        sleep 0.1s
   打印发送记录        打印发送记录       打印发送记录
```

routing key 拼成两段是有原因的：消费者按通道订阅用 `notify.*.sms`；将来产品说"营销类单独限流"，你用 `notify.marketing.*` 再绑一个队列即可，已有代码一行不改。这就是 topic 相比 direct 的价值——一个 key 承载两个维度，订阅方按需挑。

### 任务

| 文件 | 干什么 | 怎么跑 |
| --- | --- | --- |
| `topology.py` | 声明 1 个 topic 交换机、3 个队列、3 条绑定，均持久化 | 建一次，重复跑不报错 |
| `producer.py` | 读三个 json，每条请求：查用户 → 查模板 → 算交集 → 渲染 `{占位符}` → 每个有效通道 publish 一条，消息持久化 | 想灌数据就跑 |
| `consumer.py` | 顶部写 `CHANNEL = "sms"` 常量，只消费对应队列；按 `mock_config` 的 `send_seconds` sleep 模拟调网关，然后打印 | 改常量开 3 个运行窗口 |

- 消息体至少含：`task_id`、`request_id`、`user_id`、`channel`、`title`、渲染后的 `content`、`biz_type`、`priority`。
- 发送记录打印就行：一行一条，带 `request_id`、`user_id`、`channel`、`content`，17 条肉眼能核对完。
- 渲染放生产端还是消费端你自己定，但要在验收记录里说明选了哪种、为什么。

### 本练习先不管的事

- 三条错误请求（REQ-0007 模板不存在、REQ-0008 缺 `{coupon}` 参数、REQ-0009 用户不存在）：先 try/except 打印跳过，正式处理是练习二。
- REQ-0006 的 `delay_seconds: 15`：先忽略，练习五再做。
- REQ-0005 在文件里出现两次，练习一会老实发两遍，**这是对的**，幂等是练习二加的。

### 验收

1. 消费者全关，跑一遍生产者，三个队列 Ready 应为 **sms 7 / email 5 / inapp 5**。先自己按数据算一遍再对答案，对不上就是交集逻辑错了。
2. 只启动 sms 消费者，只有 sms 队列被消费，另两个队列 Ready 纹丝不动——这一步证明绑定键写对了。
3. 三个消费者都启动后队列清空，打印出来的每条 `(request_id, channel)` 都能对上。
4. 交换机、队列持久化，消息持久化；重启 RabbitMQ 后未消费的消息还在。
5. 重复运行 `topology.py` 不报错、不清空已有消息。

## 练习二：手动 ack + 幂等

### 目标

消息不丢、不重复发。

练习一有两个漏洞：消费者处理到一半被杀，那条消息就没了；REQ-0005 提交两次就真发两次，用户收到两条一样的短信。这一练把这两个洞堵上。

### 已备好的部分

**建表/清库/改表**（在 `实战练习` 目录下）：

```bash
uv run alembic upgrade head                                    # 建表
uv run alembic downgrade base && uv run alembic upgrade head   # 清空重来
uv run alembic revision --autogenerate -m "说明"               # 改了 models.py 模型后生成迁移
```

autogenerate 生成的迁移**必须打开人工检查**再 upgrade。这个库还跑着别的练习（`clm_*`、`checkpoints` 等），`env.py` 里已加了过滤只管 `notify_` 开头的表——但过滤不是万能的，比如"改列名"会被它识别成"删一列加一列"，不审就上会丢数据。第一次生成时真出过事：迁移里带了一堆删别人表的 drop 语句，幸好审了出来。

三张表，一行代表什么，先混个脸熟：

| 表 | 一行代表 | 用途 |
| --- | --- | --- |
| `notify_send_record` | 一次发送成功 | `UNIQUE(request_id, channel)` 做幂等；练习四加 `consumer_id` 看分工 |
| `notify_gateway_call` | 真的调了一次网关 | 行数 = 尝试次数（练习三）；`called_at` = 发送时间戳（练习四限速统计） |
| `notify_failed_record` | 一条最终失败 | 永久错误 / 重试耗尽留档，练习三带原始消息体 |

**store.py** 的五个函数（职责细节看各函数 docstring）：`is_sent`、`mark_sent`、`log_call`、`call_count`、`mark_failed`。

**从练习二起客户端换成 aio-pika**：消费天然是 async 的，store 的函数直接 `await`。API 速查（已连真实 RabbitMQ 冒烟验证过）：

```python
import aio_pika

connection = await aio_pika.connect(RABBITMQ_URL)          # 还是 .env 里那条 amqp://
channel = await connection.channel()
await channel.set_qos(prefetch_count=1)                     # 对应 pika 的 basic_qos

exchange = await channel.declare_exchange(
    "ai_lab.notify.events", aio_pika.ExchangeType.TOPIC, durable=True)
queue = await channel.declare_queue(
    "sms", durable=True, arguments={"x-max-priority": 10})  # TTL/DLX 也是往 arguments 塞
await queue.bind(exchange, routing_key="notify.*.sms")

await exchange.publish(
    aio_pika.Message(
        body=...,                                           # bytes
        delivery_mode=aio_pika.DeliveryMode.PERSISTENT,
        priority=9,
    ),
    routing_key="notify.verify_code.sms",
)

async for message in queue.iterator():                      # 消费循环，天然 async
    ...
    await message.ack()                                     # 手动 ack 对应 basic_ack
```

入口就是 `asyncio.run(main())` 一个循环跑到头，所以 `db.py` 的引擎用默认连接池（早先"每条消息起一个短命循环"的桥接方案才必须 NullPool，已拆掉）。aio-pika 另有 `async with message.process()` 出块自动 ack 的写法，**这个练习别用**——要练的就是手动 ack 的时机。

### 任务

1. **手动 ack**：consumer 去掉自动确认。要求：一条消息的全部处理完成之后才 ack；消费者中途被杀，这条消息不能丢（验收 3 会真的杀进程验证）。
2. **限流推送**：消费前设 prefetch（aio-pika 是 `await channel.set_qos(prefetch_count=...)`，值读 `mock_config.consumer.prefetch_count`，当前是 1）。它是对 channel 的全局设置，设一次就够。
3. **幂等**：同一个 `(request_id, channel)` 只真的调一次网关，跨进程重启成立（不能靠内存记）。查到重复消息也要把它处理完毕——它最后不应该挂在 unacked 里。
4. **永久错误拦在门外**：producer 改造——REQ-0007/0008/0009 这三种重试一万次结果都一样的错误，不投递，直接写 `notify_failed_record`（`permanent: true`、`attempts: 0`）。
5. **落库**：发送成功写 `send_record`，每次网关调用写 `gateway_call`（都用 store 的函数，别在消费者里手写 SQL）。

### 思考点（想清楚再动手，答案写进验收记录）

- ack 放在哪一步之后？收到就 ack 和处理完再 ack，消费者崩溃时分别丢什么？
- 查到重复消息时，如果直接 `return` 不 ack，管理台上会看到什么？消费者重启后会发生什么？
- "先调网关、后写 send_record" 还是反过来？两种写法各在什么时刻崩溃会出什么问题？企业里为什么普遍选前者？

### 本练习先不管的事

- 优先级队列：挪到练习二·下半场，因为它要删队列重建，跟幂等分开做不容易搞混。
- REQ-0010 / REQ-0011 的 `fail_rules`：本练习还没实现故障注入，这两条会正常发送成功，**这是对的**。
- REQ-0006 的 `delay_seconds`：继续忽略。

### 验收

1. 先 `uv run alembic downgrade base && uv run alembic upgrade head` 清空重来，再连续跑 3 遍 `producer.py`，三个消费者跑完后查库：

   ```sql
   -- send_record 应 15 行：sms 6 / email 5 / inapp 4
   SELECT channel, count(*) FROM notify_send_record GROUP BY channel;

   -- 每对 (request_id, channel) 恰好 1 次调用，说明重复的 2 条根本没碰网关
   SELECT request_id, channel, count(*) FROM notify_gateway_call
   GROUP BY request_id, channel HAVING count(*) > 1;   -- 应返回 0 行
   ```

   三个队列全空，管理台 Unacked 也是 0。数字对不上时先想清楚差在哪（17 条投递、2 条重复的去向）：

   | 通道 | 练习一投递条数 | 去重后实际发送 | 差在哪 |
   | --- | --- | --- | --- |
   | sms | 7 | **6** | REQ-0005 的 sms 重复了 1 条 |
   | email | 5 | **5** | 没有重复 |
   | inapp | 5 | **4** | REQ-0005 的 inapp 重复了 1 条 |
   | 合计 | 17 | **15** | |

2. `notify_failed_record` 里有 REQ-0007 / 0008 / 0009 三行，`permanent = true`、`attempts = 0`，且这三条从来没进过任何队列。
3. 把 `mock_config.consumer.pause_before_ack_seconds` 设成 10，消费者在"调完网关"和"ack"之间 sleep 这么久。等它打印完"已发送"，在 PyCharm 点停止按钮杀掉进程。然后重启消费者：
   - 管理台能看到这条被重新投递了
   - 但 `notify_gateway_call` 里它的行数**没有 +1**（走了跳过分支）
   - 最后正常 ack，队列清空

   这一条复现的是线上最常见的事故形态：钱扣了/短信发了，但确认没送到 MQ。

## 练习三：有限重试 + 死信归档

### 目标

临时故障自己恢复，恢复不了的进归档队列留证据。

练习二把永久错误挡在门外了，但还有一类：网关超时、连接被拒——这次失败下次可能就好了。直接扔掉太粗暴，立刻重试又会把还没缓过来的下游打死。正确做法是**隔一会儿再试，间隔逐次拉长，试够次数就放弃**。间隔阶梯读 `mock_config.retry.backoff_seconds` = `[5, 15, 60]`，即首次 + 3 次重试 = 最多 4 次。

### 背景知识（RabbitMQ 的行为事实，方案自己设计）

1. **RabbitMQ 没有"这条消息 N 秒后再投给我"这种原生功能。** 业界标准做法是拿两个特性拼：
   - `x-message-ttl`：消息在这个队列里躺满 N 毫秒就"过期"
   - `x-dead-letter-exchange`：消息过期/被拒时不删掉，自动转发到指定交换机
2. **死信转发时，如果队列没设 `x-dead-letter-routing-key`，消息会带着它原来的 routing key 走。** 这条事实很值钱，能帮你省掉一大半队列。
3. **队列是 FIFO，TTL 的到期检查只看队头。** 前面压着一条还没到期的，后面的就算早该走了也出不去，得干等——这叫队头阻塞。
4. TTL 可以设成队列参数（全队列统一），也可以给单条消息设 `expiration` 属性。

### 数据流（要求，不管你内部怎么实现）

```
sms 队列 → 消费者调网关 → 临时错误
  → 5 秒后回到 sms 队列重新被消费（只回本通道，不重新扇出到 email/inapp）
  → 再失败 → 15 秒后再回
  → 再失败 → 60 秒后再回
  → 第 4 次仍失败 → 归档队列留证据 + notify_failed_record 落库（带原始消息体），不再重试
```

### 任务

1. `topology.py`：加重试用的拓扑（几档、用什么交换机类型、建几个队列，自己设计）+ 归档部分：交换机 `ai_lab.notify.failed`（direct）绑定 `ai_lab.notify.{sms,email,inapp}.failed` 三个无消费者的归档队列。
2. `gateway.py`（新建）：模拟调网关。读 `fail_rules` 决定这次成败（REQ-0010 sms 前两次失败第三次成功；REQ-0011 email 每次都失败），成败都写一行 `gateway_call`。**计数必须跨进程重启**——想想计数存在哪（store 里有个现成的函数）。
3. `consumer.py`：区分临时错误 / 永久错误（自定义两个异常类）。临时的按档位延迟重试；重试耗尽的投归档队列并落 `notify_failed_record`（`raw_message` 带上原始消息体）。**无论哪条路径，消息最后都要有归宿**（ack 或转投），不能悬在 unacked 里。

### 思考点（答案写进验收记录）

- 重试转投用 `basic_nack`，还是"ack 掉原消息 + 重新 publish"？两种分别能把消息送到哪，谁给你挑档位的自由？
- 为什么按档位建多个延迟队列，而不是一个队列里给每条消息自己设 `expiration`？（联系背景知识第 3 条）
- 3 个档位 × 3 个通道，最省要建几个延迟队列？靠的是哪条特性？

### 本练习先不管的事

- REQ-0006 的延迟：练习五，但机制完全一样，到时候照抄这一练的。
- 限速和多实例：练习四。

### 验收

1. **REQ-0010**（sms 前两次失败）：
   - sms 日志里能看到 **3 次尝试**，中间两次等待（5 秒、15 秒）肉眼能感觉到，第三次成功
   - 同一时间 REQ-0010 的 email 通道（U004 订阅了 sms+email）**一次就成功**，不受牵连——证明重试只回本通道
2. **REQ-0011**（email 永远失败）：
   - 尝试 **4 次**后停止
   - 管理台 `ai_lab.notify.email.failed` 队列 Ready = **1**
   - `notify_failed_record` 里能查到这行：错误原因、`attempts: 4`、`raw_message` 里是原始消息

   ```sql
   SELECT request_id, channel, attempts, permanent, raw_message
   FROM notify_failed_record WHERE request_id = 'REQ-0011';
   ```
3. 在第二次重试等待期间（那 15 秒里）把消费者停掉再启动：

   ```sql
   SELECT count(*) FROM notify_gateway_call
   WHERE request_id = 'REQ-0010' AND channel = 'sms';   -- 仍是 2，不是 0
   ```

   重启后接着走第三次。这就是为什么计数不能存内存。

## 练习四：并发消费 + prefetch 限速

### 目标

多个消费者分摊同一个队列，同时别把下游网关打爆：`mock_config.gateway.email.rate_limit_per_sec = 2`，邮件网关只让发 2 条/秒。RabbitMQ 本身不管这事，得靠消费端自己压。

### 任务

1. `bulk_producer.py`（新建）：生成 20 条发货通知（TPL_ORDER_SHIPPED，数量读 `mock_config.batch.concurrent_orders`），用户轮转。注意只有订阅了 email 的用户才会产生 email 消息，轮转时别把不订阅的算进预期总量。
2. `consumer.py`：启动时生成实例 ID（`uuid4().hex[:4]` 或 `os.getpid()`），写进两个地方——日志前缀（人看）、`mark_sent` 的 `consumer_id` 参数（验收查库用）。同一份文件开 2 个窗口跑 `CHANNEL = "email"`。
3. **节流**：两个实例并发消费，任意 1 秒窗口内 email 发送数 ≤ 2。节流该怎么做、每个实例怎么配合，自己设计。
   **先想清楚一件事**：默认 `send_seconds: 1.0` 时，你可能根本验证不出节流代码有没有生效——为什么？把配置调成什么样，节流效果才看得见？
4. `rate_check.py`（新建）：按秒分桶统计 `gateway_call.called_at`，输出每秒发送数。核心就一句 SQL（见验收 2）。

### 验收

1. 20 条通知跑完：两个实例都处理了一部分（不要求均分），`notify_send_record` 总数 **20**，无重复。分工情况一查便知：

   ```sql
   SELECT consumer_id, count(*) FROM notify_send_record
   WHERE channel = 'email' GROUP BY consumer_id;
   ```
2. `rate_check.py` 输出：任意 1 秒窗口内 email 发送数 **≤ 2**：

   ```sql
   SELECT to_char(called_at, 'HH24:MI:SS') AS 秒, count(*)
   FROM notify_gateway_call WHERE channel = 'email'
   GROUP BY 1 HAVING count(*) > 2;        -- 应返回 0 行
   ```
3. 跑到一半在 PyCharm 停掉实例 A，它手上 unacked 的消息会随连接断开被重投给 B。最终 `notify_send_record` 还是 **20**，被 A 拿走但没 ack 的那几条出现在 B 的日志里。这是手动 ack 最直接的价值。
4. `prefetch_count` 设成 1 跑一遍、设成 20 再跑一遍，把现象和原因写进记录：

   | prefetch | 现象 | 原因 |
   | --- | --- | --- |
   | 1 | （记录） | （记录） |
   | 20 | （记录） | （记录） |

## 练习五：延迟发送 + 状态观察

### 目标

定时投递，以及任意时刻能说清每条请求处在哪一步。

### 任务

1. `topology.py`：加延迟拓扑，让消息能"先躺 15 秒再进业务队列"（REQ-0006 带 `delay_seconds: 15`）。机制跟练习三的重试一模一样，只是入口从"消费者失败后投"换成"生产者直接投"。
2. `producer.py`：`delay_seconds > 0` 的请求走延迟路径。REQ-0006 是 U004 + TPL_BILL_REMIND，交集 `[sms, email]`，所以延迟队列里会躺 **2 条**。
3. `status.py`（新建）：跑一次打印全局状态，六种状态分别从哪看：

   | 状态 | 数据来源 |
   | --- | --- |
   | 延迟等待中 | 延迟队列的消息数 |
   | 待消费 | sms / email / inapp 队列的 Ready 数 |
   | 处理中（unacked） | **queue_declare 拿不到，得看管理台** |
   | 重试等待中 | 三个 `ai_lab.notify.retry.*` 队列的消息数之和 |
   | 已成功 | `SELECT channel, count(*) FROM notify_send_record GROUP BY channel` |
   | 最终失败 | `notify_failed_record` 行数（区分 permanent / 重试耗尽）+ 三个 `.failed` 队列的消息数 |

   队列消息数怎么拿：声明队列时带 `passive=True` 是"只查不建"（pika 和 aio-pika 都支持），消息数从声明结果对象里读。⚠️ 这个方法只能拿 Ready 数，拿不到 Unacked（管理台或管理 HTTP API `GET /api/queues/%2F/队列名`），输出里注明这点。
4. **日志能串起来**：每条日志至少含 `task_id`、`request_id`、`channel`、第几次尝试、结果、耗时、错误类型、消费者实例 ID。标准就一条：拿一个 `request_id` 去 grep，能把它从提交到最终成功/失败的完整经过串出来。另外不打印凭据——捕获连接异常时别直接 `print(e)`，`RABBITMQ_URL` / `DATABASE_URL` 里有密码。

### 验收

1. 跑完 `producer.py` **立刻**跑 `status.py`：sms / email 队列里**没有** REQ-0006，延迟队列有 **2 条**。等约 15 秒再跑一次：延迟队列空了，业务队列里出现并被消费。误差几秒可接受。
2. `status.py` 能同时区分出六种状态，unacked 那行注明"请看管理台"。
3. `uv run alembic downgrade base && uv run alembic upgrade head` 清空数据库，管理台清空队列，从头完整跑一遍 12 条请求，输出一份验收记录：每个 `request_id` 的最终结果 + 它验证了哪个能力点。参考格式：

   | request_id | 通道 | 最终结果 | 验证了什么 |
   | --- | --- | --- | --- |
   | REQ-0001 | sms | 成功 | 单通道交集 |
   | REQ-0004 | —— | 无可用通道 | 交集为空 |
   | REQ-0005 | sms/inapp | 各成功 1 次（提交 2 次） | 幂等 |
   | REQ-0006 | sms/email | 延迟 15 秒后成功 | TTL+DLX 延迟投递 |
   | REQ-0007 | —— | 永久失败，未进队列 | 永久错误分流 |
   | REQ-0010 | sms | 第 3 次成功 | 有限重试 |
   | REQ-0011 | email | 4 次后进归档 | 重试耗尽 + 死信留档 |

## 通过标准

同一批请求，在重复提交、消费者重启、临时故障、限速压制之后，仍然：每个 `(request_id, channel)` 恰好发送一次，永久错误有据可查，临时故障能自愈或进归档留档，任意时刻能说清每条请求处于哪个状态。
