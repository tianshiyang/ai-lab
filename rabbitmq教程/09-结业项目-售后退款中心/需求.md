# 09 · 结业项目:售后退款中心(需求书 + 流程图)

第 8 讲管"卖出去"——付款、短信、积分;这一讲管"退回来"。用户对已付款订单申请退款,后面跟着审核、打款、通知一串动作。

这次给你**需求 + 全套流程图 + 拓扑表**,照图施工;代码、文件怎么拆、日志什么样式,归你。写完拿 §5 验收自检,再带着 §7 的思考题找人评审。

## 0 业务背景与需求清单

"云上小店"上线七天无理由退货。用户提交退款申请后:

- **客服审核**:两名客服共用一个工单池,谁闲谁领;审核一单 4 秒;VIP 会员的单优先审;
- **财务打款**:审核通过的进入打款队列,两名出纳竞争处理,一笔 3 秒;VIP 同样优先;
- **打款会失败**(银行接口抖动):不能立刻重试,第 1 次失败等 5 秒、第 2 次失败等 15 秒;第 3 次失败(总共尝试 3 笔)终结——告警转人工;
- **用户会撤销**:申请挂在队列里等审核时,用户改主意撤销了,客服轮到这单就跳过;
- **每个结局都要通知用户**(审核通过/拒绝、打款成功/失败),通知由独立的通知服务统一发。

真实系统里退款成功还要联动扣回第 8 讲发的积分——那就是再挂一个订阅方的事,上游一行不改。本讲不做,体会这个"可扩展"就够了。

| # | 需求 |
|---|---|
| N1 | 提交申请:先入库(待审核),再直投审核队列;提交端开 publisher confirm,每条回执打印(第 4 讲:回执只保证到了 broker) |
| N2 | 双客服竞争:同一个脚本、两个终端各跑一份,竞争消费审核队列;prefetch=1,手动 ack;日志分得清是哪个客服 |
| N3 | 双出纳竞争:同上,消费打款队列 |
| N4 | VIP 插队:审核、打款两条队列都开优先级,VIP 消息 priority=9、普通 0;两头缺一不可(第 7 讲) |
| N5 | 阶梯延迟重试:第 1 次打款失败等 5 秒重试,第 2 次失败等 15 秒重试;第 3 次失败终结——改库、广播失败事件、原消息 nack(requeue=False) 进死信,watcher 告警 |
| N6 | 状态机与幂等:状态流转全部条件 UPDATE;客服只动"待审核"的单,出纳只动"待打款"的单,状态对不上就跳过、ack——重启、重投、重试回流,都不能把活干两遍 |
| N7 | 用户撤销:只改库(已撤销),不动任何消息;客服轮到时回查识别、跳过 |
| N8 | 结局通知:approved / rejected / paid / failed 四类事件,由独立的通知服务统一消费打印;客服、出纳不许自己 print 用户通知 |
| 底线 | durable 队列 + 持久化消息 + 手动 ack + connect_robust;重发进中转队列的消息要把 priority 带上(回流后继续生效) |

## 1 流程图

### 1.1 总流程

```
 提交端(生产者,publisher confirm)
   │  提交申请:入库(待审核)→ 直投审核队列
   │  撤销申请:只改库(已撤销),不动任何消息
   ▼
 refund.audit.queue(优先级队列,无 DLX)
   │
   ▼
 客服 ×2(竞争消费,prefetch=1,手动 ack,一单 4 秒)
   ├─ 回查库:已撤销 ──────────► 跳过,ack
   ├─ 剧本=拒绝 → 库改"已拒绝" ─► 广播 refund.rejected
   └─ 剧本=通过 → 库改"待打款" ─► 广播 refund.approved
                                    │
                                    ▼
                        refund.events(topic 交换机)
                 键:approved / rejected / paid / failed
                                    │
            ┌───────────────────────┤
            │ approved          refund.*(通配,一绑全收)
            ▼                           ▼
 refund.finance.queue           refund.notify.queue
 (优先级队列,DLX=refund.dlx)          │
            │                        ▼
            ▼                   通知服务(打印用户通知)
 出纳 ×2(竞争消费,prefetch=1,手动 ack,一笔 3 秒)
   ├─ 回查库:不是"待打款" ────► 跳过,ack
   ├─ 打款成功 → 库改"已退款" ─► 广播 refund.paid
   ├─ 打款失败,重试<2 ────────► 直投中转队列(§1.2)
   └─ 打款失败,重试=2 ────────► 库改"打款失败" → 广播 refund.failed
                                 └ 原消息 nack(requeue=False) → 死信(§1.3)
```

### 1.2 重试回路(打款失败后)

```
 出纳失败 ──第 1 次失败(header retry=0)──► refund.retry.5s (TTL 5 秒)
 出纳失败 ──第 2 次失败(header retry=1)──► refund.retry.15s(TTL 15 秒)
                                              │
                                              │ 到期 expired 死信
                                              ▼
                  DLX = 默认交换机,routing-key = refund.finance.queue
                                              │
                                              ▼
                    直投回流打款队列,出纳再领,按 header 定夺

 关键性质:死信转发会**原样保留消息属性**——header 里的 retry 计数、消息的
 priority,回流后都还在。所以出纳发新消息进中转队列时带上这两样,回流后
 直接读 header 就知道是第几次;VIP 的优先级也不会在重试路上弄丢。
```

### 1.3 死信出口

```
 refund.finance.queue ──nack(requeue=False)──► refund.dlx(direct)
                                                   └─ dead ──► refund.dead.queue ──► watcher 告警
```

## 2 拓扑表(照抄进拓扑声明)

| 对象 | 类型与参数 | 绑定 / 投递关系 |
|---|---|---|
| `refund.events` | topic,durable | 唯一事件总线 |
| `refund.audit.queue` | durable,`x-max-priority=10` | 不绑交换机;提交端默认交换机直投;消息带 priority |
| `refund.finance.queue` | durable,`x-max-priority=10`,DLX=`refund.dlx`(routing-key=`dead`) | 绑 events / `approved` |
| `refund.retry.5s` | durable,`x-message-ttl=5000`,DLX=默认交换机(routing-key=`refund.finance.queue`) | 不绑交换机;出纳直投 |
| `refund.retry.15s` | durable,`x-message-ttl=15000`,DLX 同上 | 不绑交换机;出纳直投 |
| `refund.dlx` | direct,durable | — |
| `refund.dead.queue` | durable | 绑 dlx / `dead` |
| `refund.notify.queue` | durable | 绑 events / `refund.*`(通配,四类事件一绑全收) |

声明照旧幂等,谁先启动谁建;所有脚本共用一份拓扑声明 + 一个数据库模块(第 8 讲的 `common.py` 路数)。

## 3 业务规则细则

**状态机**(一张退款单的一生,每次流转都是条件 UPDATE,`where status = 旧值`,看 rowcount 判断成没成):

```
          客服·通过                      出纳·打款成功
 待审核 ───────────► 待打款 ──────────────────────► 已退款(终)
   │                     │
   │ 客服·拒绝            │ 出纳·三连败
   ▼                     ▼
 已拒绝(终)           打款失败(终)+ 死信告警
   │
   │ 用户撤销(提交端只改库,消息仍留在审核队列)
   ▼
 已撤销(终,客服轮到时识别跳过)
```

**回查规则**:客服领到单先查库,不是"待审核"就跳过;出纳领到单先查库,不是"待打款"就跳过。跳过也要 ack——消息本身处理完了,它的结论是"不用干"。

**重试计数**:放消息头(`headers={"retry": n}`),沿用第 8 讲短信的路数;档位选择看 header——第 1 次失败投 5 秒档,第 2 次失败投 15 秒档,header 到 2 还失败就终结。库里的"尝试次数"每打一次款 +1(验收查询要看)。

**耗时**:审核一单固定 4 秒,打款一笔固定 3 秒(写死,别按金额折算,验收的时间线才对得上)。**失败判定**:剧本里带"注定失败"标记的单,每次尝试都失败;其余每次都成功,不搞随机。

**通知边界**:转码日志归客服/出纳自己的终端;面向用户的通知(approved/rejected/paid/failed 四类)只许通知服务打印。

## 5 验收标准

竞争消费的日志交错是正常的——断言看**顺序和间隔**,不逐字对输出。

**验收一:终端断言**

1. 两个客服开局同时各领一单(R3001、R3002),两个出纳交替打款,日志分得清是谁;
2. **插队可见**:R3006、R3007 第 3 秒才提交,但审核领走时间早于 R3003、R3004、R3005;打款同理;
3. R3005 轮到时打印"已撤销,跳过",消息 ack,没有任何审核结论和打款记录;
4. R3004 三次打款的**开始时间**间隔约为 8 秒(5 秒等待 + 3 秒打款)、18 秒(15 + 3);
5. R3004 终结后:watcher 告警一条(x-death:死于 rejected,原队列 `refund.finance.queue`);
6. 通知服务合计 11 条:approved×5、rejected×1、paid×4、failed×1,别无其他;
7. 提交端日志能看到每条申请的 broker 确认回执。

**验收二:查库终局**(表结构自己设计,一条 SQL 要能看出每单终局和打款尝试次数)

| 单号 | 终局 | 尝试次数 |
|---|---|---|
| R3001、R3002 | 已退款 | 1 |
| R3003 | 已拒绝 | 0 |
| R3004 | 打款失败 | 3 |
| R3005 | 已撤销 | 0 |
| R3006、R3007 | 已退款 | 1 |

**里程碑对照**(大致时刻,容差 ±1 秒):

```
t=4   R3001/R3002 审核通过,出纳开始打款
t=7   R3001/R3002 已退款
t=8   R3006/R3007 审核完(插队成功)
t=12  R3003 拒绝;R3004 通过;R3005 轮到 → 已撤销跳过
t=15  R3004 第 1 次打款失败
t=23  第 2 次失败(5 秒档回流)
t=41  第 3 次失败(15 秒档回流)→ 终结:打款失败 + failed 通知 + 死信告警
```

**选做实验**(验完 N6 才算真的成立):

- 打款打到一半 `Ctrl+C` 掉一个出纳:未确认的消息被另一个出纳接手,终局不变;重启被杀的,能继续干活;
- 审核环节同理杀一个客服试试。
