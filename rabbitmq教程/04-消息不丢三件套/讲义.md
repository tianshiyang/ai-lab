# 第 4 讲 · 消息不丢三件套

先把"消息从生到死"的链路画出来,丢失可能发生在三个环节,每个环节有各自的解法:

```
 生产者 ──①网络/路由──► broker 内存 ──②落盘──► 磁盘 ──③投递──► 消费者
         (confirm+mandatory)        (durable+PERSISTENT)     (手动 ack,第 2 讲已解决)
```

第 2 讲用手动 ack 堵住了环节③。这一讲堵前两个:**broker 重启消息还在不在**(持久化),和**生产者怎么知道消息真的进了 broker**(确认机制与路由失败感知)。三件套齐了,消息的最低可靠线才算画完,订单、支付这类消息,这三样缺一不可。

两个脚本全文如下。`durability.py` 短,建议手敲;`publish_confirmed.py` 三个场景结构清晰,照着敲一遍能把三种信道的脾气摸透。

## 完整代码

`durability.py`(全文),左右对照组:

```python
"""第 4 讲·持久化对照:两个队列、两种消息,看消息能不能活过 broker 重启。

    uv run python "rabbitmq教程/04-消息不丢三件套/durability.py"

跑完后队列故意留在 broker 上不删——如果你有服务器的操作权限,可以重启
RabbitMQ 服务再跑一遍本脚本,看两个队列各自的下场(见讲义"实验")。
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        # 左右对照组:一个不落盘,一个落盘
        volatile = await channel.declare_queue("ch4.volatile", durable=False)  # ① 队列不落盘
        persist = await channel.declare_queue("ch4.persist", durable=True)  # ② 队列落盘
        await volatile.purge()
        await persist.purge()

        # 不带 delivery_mode 的消息:默认不落盘
        await channel.default_exchange.publish(
            aio_pika.Message("我是普通消息,重启就没了".encode()),
            routing_key=volatile.name,
        )
        # PERSISTENT 的消息:写盘
        await channel.default_exchange.publish(
            aio_pika.Message(
                "我是持久化消息,重启也还在".encode(),
                delivery_mode=aio_pika.DeliveryMode.PERSISTENT,  # ③ 消息落盘
            ),
            routing_key=persist.name,
        )
        print("两条消息都发好了,各在各的队列:")
        print("  ch4.volatile  ← 队列不落盘 + 消息不落盘")
        print("  ch4.persist   ← 队列落盘   + 消息落盘")
        print("去管理台 Queues 页看这两行:Features 列的 D 标志,只有 ch4.persist 有")

        # ── ④ 顺手演示一个坑:同名队列、不同参数的重复声明 ──
        print("\n下面故意用错误参数重新声明 ch4.persist( durable=False ),看看下场:")
        try:
            await channel.declare_queue("ch4.persist", durable=False)
        except Exception as e:  # pylint: disable=broad-except
            print(f"  broker 拒绝了: {type(e).__name__}: {e}")
            print("  而且这条信道已经被关掉,再用它会报错,只能重开一条")


asyncio.run(main())
```

`publish_confirmed.py`(全文),生产端三个场景:

```python
"""第 4 讲·生产端可靠性:确认机制 + 路由失败感知。

uv run python "rabbitmq教程/04-消息不丢三件套/publish_confirmed.py"
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        # ── 场景一:路由不到任何队列的消息,默认是"静默蒸发" ──────────────────
        channel = await connection.channel()  # ① 默认配置的信道
        exchange = await channel.declare_exchange(
            "ch4.probe", aio_pika.ExchangeType.DIRECT, durable=True
        )
        # 这个交换机一个绑定都没有,发进去的消息注定无处可去

        result = await exchange.publish(
            aio_pika.Message("我可能哪都到不了".encode()),
            routing_key="no.one.binds.this",
        )
        print("场景一:往没有任何绑定的交换机发消息(默认信道)")
        print(f"  publish 没抛任何异常,返回值类型是 {type(result).__name__}")
        print("  —— 被退回的消息其实就藏在这个返回值里,但没有异常没有日志,")
        print("     生产代码几乎不会有人检查它,消息实际上已被丢弃,等于毫无知觉\n")

        # ── 场景二:开着 on_return_raises,路由失败立刻炸给你看 ───────────────
        strict = await connection.channel(on_return_raises=True)  # ② 开了路由失败必抛的信道
        strict_exchange = await strict.declare_exchange(
            "ch4.probe", aio_pika.ExchangeType.DIRECT, durable=True
        )
        try:
            await strict_exchange.publish(
                aio_pika.Message("再发一次没人要的消息".encode()),
                routing_key="no.one.binds.this",
            )
        except aio_pika.exceptions.DeliveryError:
            print("场景二:同样的消息,on_return_raises=True 的信道")
            print("  立刻抛出 DeliveryError —— broker 把消息原路退回,生产端当场知道")
            print("  该记日志记日志,该补偿补偿,而不是等下游来问'消息怎么没来'\n")

        # ── 场景三:正常路由 + publisher confirm ─────────────────────────────
        queue = await channel.declare_queue("ch4.probe.target", durable=True)
        await queue.bind(exchange, routing_key="normal.key")
        confirmation = await exchange.publish(  # ③ 正常投递,confirm 默认开着
            aio_pika.Message(
                "这条能正常路由".encode(),
                delivery_mode=aio_pika.DeliveryMode.PERSISTENT,
            ),
            routing_key="normal.key",
        )
        print("场景三:正常投递(信道默认开着 publisher confirm)")
        print(f"  publish 的返回值类型: {type(confirmation).__name__}")
        print("  这就是 broker 的回执:消息已被接收。要是 broker 没收到,publish 会抛异常")

        await queue.purge()  # delete 默认拒绝删非空队列,先清空
        await queue.delete()
        await exchange.delete()


asyncio.run(main())
```

## 逐段讲

### ①②③ 持久化是两个开关,缺一不可

这是本讲最容易想当然的地方:**队列 durable 和消息 PERSISTENT,各管各的**。

- `durable=True` 管**队列的定义**(名字、绑定、参数)能不能活过 broker 重启。不落盘的队列,重启后连队列本身都消失,里面的消息无论是否持久化都陪葬;
- `delivery_mode=PERSISTENT` 管**这一条消息**要不要写到磁盘。不落盘的消息躺在内存里,broker 一重启就没。

> **敲黑板:** 四种组合里只有"**durable 队列 + PERSISTENT 消息**"能让消息真正活下来。只拧一边等于没拧:`durable 队列装普通消息`,重启后队列在、消息空;`普通队列装 PERSISTENT 消息`,重启后队列和消息一起没。所以生产代码的习惯是两个一起上,就像 durability.py 的对照组那样写。

顺带一提落盘的时机:持久化消息不是发一条写一条盘,broker 会攒一小批再刷盘,极端断电仍可能丢最后零点几秒,持久化只是把丢失概率压到极低。要求更苛刻的场景用第 7 讲会提到的 quorum 队列。

### ④ 声明参数不一致的下场(406)

durability.py 结尾自导自演了一出事故:队列 `ch4.persist` 已存在(durable=True),脚本又拿 `durable=False` 去声明同一个名字,broker 直接拒绝:

```
ChannelPreconditionFailed: PRECONDITION_FAILED - inequivalent arg 'durable'
for queue 'ch4.persist': received 'false' but current is 'true'
```

更麻烦的是这条信道同时被关掉,不重开一条没法继续干活。这事故的真实版本是:你在测试环境改了队列参数(比如加 TTL),代码一跑报 406,因为老队列还按旧参数活在 broker 上。

撞上 406,最快的解法是去管理台把旧队列删了,让新参数重建它(第 1 讲说过:同名重复声明,参数必须一字不差)。

### publisher confirm:生产端的回执(publish_confirmed.py ③)

aio-pika 的信道**默认开着 publisher confirm**:每条 `publish` 都会等 broker 回一句"收到了"才返回,正常时返回值是个 `Ack`(场景三打印的就是它);broker 没收到、内部出问题,publish 抛异常。也就是说,你在 aio-pika 里写的每一个 `await publish(...)`,背地里都已经带着回执了,这层保的是环节①里"消息到底到没到 broker"。

要极限吞吐时可以 `connection.channel(publisher_confirms=False)` 关掉它,批量发完再统一等,日常用不着。

### mandatory + on_return_raises:路由失败不许装哑巴(①②)

环节①还有个阴暗角落:消息到了 broker,但路由不到任何队列(第 3 讲 direct 实验里那条 push 消息的命运)。默认行为是 broker 把消息退回,而退回这件事被客户端静默吞掉——场景一里就能看到:没有异常,没有日志,生产端"感觉良好",消息已经没了。退回的消息本体其实塞在 publish 的返回值(DeliveredMessage)里,但正常没人检查返回值,等于无感。

> **敲黑板:** 想硬感知"路由失败",两个开关一起开:publish 传 `mandatory=True`(aio-pika 默认就是 True,不用动)+ 开信道传 `on_return_raises=True`。路由不到,`publish` 当场抛 `DeliveryError`(场景②)。又是"两头都设置才生效"的一对。生产建议:发重要消息的信道,把 `on_return_raises=True` 设为默认,该捕获捕获、该告警告警。

### 三件套合起来的样子

```
await exchange.publish(                     # 信道默认开着 confirm → 环节①有回执
    aio_pika.Message(body, delivery_mode=PERSISTENT),   # 消息落盘 → 环节②
    routing_key="order.paid",
)   # 信道是 on_return_raises=True → 路由失败当场炸
# 队列声明时 durable=True                    # 队列落盘 → 环节②的另一半
# 消费端手动 ack + 幂等                       # 环节③,第 2 讲
```

### 补充:connect_robust,断线自动重连

生产者的连接断了一般就是报错重试;常驻消费者断线才是大麻烦,总不能网络抖一下进程就死。aio-pika 的答案是:

```python
connection = await aio_pika.connect_robust(RABBITMQ_URL)
```

断线自动重连,而且重连后把你在这条连接上做过的声明、绑定、set_qos、订阅全部重放一遍。但它只救连接不救消息,断线瞬间没 ack 的消息 broker 会重投,所以幂等依然要自己做(第 2 讲讲过的债)。第 8 讲的常驻消费者统一用它。

```

```

等它起来,刷新管理台 Queues 页:ch4.volatile 整个消失了(队列和消息一起没),ch4.persist 还在,消息数还是 1——落盘与否,一条命令见分晓。没有服务器权限也不亏,管理台上两行队列的 Features 列(D 标志有无)就是持久化的可视化证据。实验完把两个队列都删掉即可。
