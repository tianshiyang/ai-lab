写完先拿 §5 验收标准自检,再带着 §7 的思考题找人评审。

## 1 业务背景

"云上影铺"是个短视频平台。用户上传视频后,后台要自动转码压缩,完成后通知作者。转码这活有几个现实约束:

- **机器少**:只有两台转码器,一次一台只干一个活,任务要排队;
- **VIP 插队**:会员的视频优先转,排着普通任务时新来的 VIP 也要先走;
- **转码会失败**:源文件损坏之类。失败不能立刻重试(缓存还没刷好),要缓一缓再试;缓两次还不行就放弃,告警转人工;
- **作者会删稿**:排在队列里的视频,作者等不及删掉了,轮到它时就不用转了。

## 2 需求清单

| # | 需求 |
|---|---|
| N1 | 上传即提交:任务先入库(待处理),再进转码队列。入库和入队的先后要想清楚,和第 8 讲"先改库后发事件"同一条纪律 |
| N2 | 两台转码器并行干活:**同一个脚本、两个终端各跑一份**,竞争消费同一条队列;一台一次只领一个活(prefetch 压到 1),干完手动 ack。日志里要能分清是哪台干的 |
| N3 | VIP 插队:普通任务还在队列里排着时,后到的 VIP 任务先被领走 |
| N4 | 阶梯延迟重试:转码失败不立刻重试——第 1 次失败后**等 5 秒**重试,第 2 次失败后**等 15 秒**重试;第 3 次失败(总共尝试 3 次)终结:进死信池,死信观察员告警 |
| N5 | 结局通知:成功和最终失败都要给作者发通知(打印即可),由**独立的通知服务**消费事件完成;转码器不许自己 print 通知——转码归转码,通知归通知 |
| N6 | 状态机与幂等:任务状态 `待处理 → 转码中 → 已成功 / 已失败(终结)`,外加"作者已删除"一种终局。状态流转用条件 UPDATE;进程重启、消息重投、任务重投,都不能把活干两遍、把状态跳乱 |
| N7 | 作者删稿:只改库(状态变已删除),消息还躺在队列里;轮到它时转码器要识别出来,跳过不转,消息照常 ack |
| N8 | 提交端显式用 publisher confirm:每条任务 publish 后拿到 broker 回执并打印。要求能说清回执**保证到哪一步、不保证哪一步**(第 4 讲:到了 broker,不等于落盘、不等于被消费) |
| 底线 | durable 队列 + 持久化消息 + 手动 ack + connect_robust:杀进程、断连接,任务不丢不重复 |

系统里至少要有这些**角色**(拆成几个文件、叫什么名字,随你):提交端(生产者)、转码器×2、通知服务、死信观察员、公共零件(数据库 + 拓扑)、清场工具。

## 3 业务规则细则

**状态机**(一条任务的一生):

```
待处理 ──领任务──► 转码中 ──成功──► 已成功(通知)
  │                  │
  │ 作者删除          │ 失败(第 1、2 次)──等 5s / 15s──► 回到转码队列再试
  ▼                  │
已删除(轮到时跳过)   └─失败(第 3 次)──► 已失败(通知)+ 死信池告警
```

**转码耗时**:用 `asyncio.sleep` 模拟,时长按视频大小折算(剧本里直接给秒数)。**失败判定**:剧本里带"注定失败"标记的任务,每次尝试都失败;其余任务每次都成功——不用搞随机。

**优先级**:队列一头、消息一头都要配置,缺一半就白搭(第 7 讲的表)。数值自己定。

**重试间隔 5 秒 / 15 秒**:意味着要有"等一会儿再回来"的能力——前八讲里有一对零件拼起来正好干这个,怎么拼、死信后怎么回流转码队列,是你这次要自己设计的核心。

**删除**:只动数据库,不发任何消息。消息还排在队列里是事实,处理它时回查库(第 6 讲的规矩)。

```
t=0    一次提交 J1~J6(两台转码器立刻分别领走 J1、J2,其余四个在队列里排队)
t=+2s  作者删除 J5(只改库,消息仍在队列)
t=+4s  提交 V1、V2、F1(此刻队列里排着 J3~J6)
```

## 5 验收标准

两台转码器竞争消费,日志交错是正常的——断言看**顺序和间隔**,不逐字对输出。

**验收一:终端断言**

1. 两台转码器从开局就交替干活(J1、J2 同时被领走),日志能分清是谁;
2. **插队可见**:V1、V2 的领走时间早于 J3、J4、J6 的领走时间(它们第 4 秒才提交,却先走);
3. J5 轮到时打印"已删除,跳过"一类日志,消息被 ack,没有转码记录;
4. F1 的三次尝试,日志时间戳间隔约 5 秒、约 15 秒;
5. F1 三连败后:死信观察员告警(能看到 x-death 档案),通知服务收到一条**失败**通知;
6. 通知服务合计收到**成功通知 7 条**(J1~J4、J6、V1、V2)+ **失败通知 1 条**(F1),别无其他;
7. 提交端日志能看到每条任务的 broker 确认回执(N8;`await publish` 的返回值就是回执,aio-pika 的 confirm 默认开着,这次要把它拿到手上看一眼)。

**验收二:查库终局**(表结构自己设计,但要能一条 SQL 看出每个任务的终局和尝试次数)

| 任务 | 终局 | 尝试次数 |
|---|---|---|
| J1~J4、J6 | 已成功 | 1 |
| J5 | 已删除 | 0 |
| V1、V2 | 已成功 | 1 |
| F1 | 已失败 | 3 |

**选做实验**(强烈建议,验完 N6 才算真的成立):

- 挑一个任务转码到一半 `Ctrl+C` / `kill -9` 掉一台转码器:未确认的消息要被另一台接手,终局不变;
- 重启被杀的转码器,它能继续干活。

**选做加分**(企业里真用,但单机只能练个脸熟——容灾差别要集群才看得出来):

- 把转码队列声明成 quorum 队列(`arguments={"x-queue-type": "quorum"}`)再跑一遍,管理台上看队列类型变了——企业集群上新项目的主流选择;
- 用管理 HTTP API `curl` 查一次转码队列的堆积数(`/api/queues/<vhost>`),脚本或命令行都行——运维巡检的基本功;
- 开一条 `on_return_raises=True` 的信道,故意往没人绑的路由键发一条消息,看它当场抛错——对比第 8 讲 `order.created` 无订阅方时"发出即丢弃"的静默。

## 7 设计思考题(评审时聊)

写之前想一遍,写完之后你应该都能答上来:

1. 重试计数放在**消息头**还是**库字段**?第 8 讲用了消息头,这次多了"隔 5 秒/15 秒"两档延迟,消息头的方案还顺手吗?两种各牺牲了什么?
2. 延迟中转队列到期死信后,怎么**回流到转码队列**?给出你的路由办法,以及为什么选它。
3. 转码器被杀时"转码中"的消息重投回来,状态机怎么接住?重干一遍安全吗——靠哪一步保证不把活干两遍?
