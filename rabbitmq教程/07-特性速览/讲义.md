# 第 7 讲 · 特性速览

前六讲覆盖企业日常 90% 的用法。本讲这些定位是**脸熟**:知道它是什么、什么场景找它、要用时回来翻。

| 特性 | 一句话 | 生产使用度 |
|---|---|---|
| 优先级队列 | 高优先级消息在 broker 排队时插到前面 | 少,通常用独立队列替代 |
| RPC 模式 | 用 `reply_to` + `correlation_id` 做请求-响应 | 少,同步调用用 HTTP/gRPC |
| quorum 队列 | Raft 多副本队列,节点挂了消息不丢 | **高**,集群新项目首选 |
| 管理 HTTP API | 管理台背后的 REST 接口 | 高,运维/巡检必用 |

## 1 优先级队列

**是什么**:队列开启优先级支持后,消息按 `priority` 数值从大到小出队。

**解决什么**:加急工单先被处理。

```python
queue = await channel.declare_queue(
    "ch7.priority",
    durable=True,
    arguments={"x-max-priority": 10},        # 队列这头:允许插队
)
await channel.default_exchange.publish(
    aio_pika.Message(body, priority=9),      # 消息这头:带优先级
    routing_key=queue.name,
)
```

| 配置 | 位置 | 默认 | 说明 |
|---|---|---|---|
| `x-max-priority` | 队列 arguments | 无(先进先出) | 最大优先级,一般给 10 |
| `priority` | `Message(...)` | 0 | 0 ~ x-max-priority,大的先出队 |

- **两头缺一不可**:队列没开 → 消息带 priority 也被无视;队列开了、消息没带 → 都是 0,仍是先进先出
- **插队只发生在 broker 排队层**。消息一旦被 prefetch 推到消费者手里囤着,顺序就定死了(第 2 讲的 prefetch)。要保优先级,消费端 prefetch 要压小
- 生产里用得少:broker 要维护有序结构有开销,而"VIP 优先"通常用**独立队列 + 独立消费者**做物理隔离更可控

`priority.py`:

```python
"""第 7 讲·优先级队列:加急消息先被消费。

uv run python "rabbitmq教程/07-特性速览/priority.py"
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        queue = await channel.declare_queue(
            "ch7.priority",
            durable=True,
            arguments={"x-max-priority": 10},
        )
        await queue.purge()

        # 队列空着、无消费者时,按 普通普通加急普通加急 的顺序发 5 条
        for priority, text in [
            (None, "普通工单-1"),
            (None, "普通工单-2"),
            (9, "加急工单-3(客户在催)"),
            (None, "普通工单-4"),
            (9, "加急工单-5(老板在催)"),
        ]:
            await channel.default_exchange.publish(
                aio_pika.Message(text.encode("utf-8"), priority=priority),
                routing_key=queue.name,
            )
        print("按 [普通, 普通, 加急, 普通, 加急] 发了 5 条,按队列顺序取出:\n")

        while True:
            message = await queue.get(no_ack=True, fail=False)
            if message is None:
                break
            print(f"  {message.body.decode('utf-8')}")

        await queue.delete()


asyncio.run(main())
```

输出:

```
  加急工单-3(客户在催)
  加急工单-5(老板在催)
  普通工单-1
  普通工单-2
  普通工单-4
```

## 2 RPC 模式

**是什么**:用两个消息属性把 MQ 变成请求-响应通道。

**解决什么**:面试常问的 AMQP 经典应用。实际项目同步调用用 HTTP / gRPC 更合适。

| 属性 | 谁设置 | 作用 |
|---|---|---|
| `reply_to` | 客户端 | 回信要发往哪个队列 |
| `correlation_id` | 客户端设、服务端原样带回 | 对暗号:哪封回信属于哪次提问 |

流程:

```
  客户端                                       服务端
   ① 声明专属临时回信队列(exclusive,连接断即删)
   ② 发请求:reply_to=回信队列, correlation_id=暗号  ──►  ③ 处理
   ⑤ 在回信队列收消息,按暗号找到对应的提问        ◄──  ④ 回信发往 reply_to,带回暗号
```

- 回信队列**整个进程只声明一次**,所有提问共用
- 必须校验 `correlation_id`:多次提问共用一个回信队列,还可能收到上一次超时提问的"陈年回复"

`rpc_server.py`:

```python
"""第 7 讲·RPC 服务端:收数字,返回平方。

uv run python "rabbitmq教程/07-特性速览/rpc_server.py"     # 常驻
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        queue = await channel.declare_queue("ch7.rpc", durable=True)
        print("RPC 服务端已启动")

        async for message in queue.iterator():
            n = int(message.body.decode("utf-8"))
            print(f"  收到请求: {n}  (correlation_id={message.correlation_id})")
            await asyncio.sleep(1)   # 假装耗时计算

            # 结果发往请求方指定的 reply_to,correlation_id 原样带回
            await channel.default_exchange.publish(
                aio_pika.Message(
                    str(n * n).encode("utf-8"),
                    correlation_id=message.correlation_id,
                ),
                routing_key=message.reply_to,
            )
            await message.ack()
            print(f"  已回复: {n * n}")


asyncio.run(main())
```

`rpc_client.py`:

```python
"""第 7 讲·RPC 客户端:发"求平方"请求,在专属回信队列上等结果。

uv run python "rabbitmq教程/07-特性速览/rpc_client.py"
"""

import asyncio
import os
import uuid
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]

NUMBERS = [7, 12]                                    # 要问的数字,想加就往里加
PENDING: dict[str, asyncio.Future[str]] = {}         # 暗号 → 等回信的 future


async def ask_square(channel: aio_pika.Channel, callback_queue: aio_pika.Queue, n: int) -> str:
    correlation_id = str(uuid.uuid4())
    future = PENDING[correlation_id] = asyncio.get_running_loop().create_future()

    await channel.default_exchange.publish(
        aio_pika.Message(
            str(n).encode(), correlation_id=correlation_id, reply_to=callback_queue.name
        ),
        routing_key="ch7.rpc",
    )
    print(f"已发出请求: {n} 的平方?")
    answer = await asyncio.wait_for(future, timeout=10)
    print(f"回信: {answer}")
    return answer


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        # 不带名字 + exclusive:本连接专属的临时队列,连接一断自动删
        callback_queue = await channel.declare_queue(exclusive=True)

        async def on_reply(message: aio_pika.IncomingMessage) -> None:
            future = PENDING.pop(message.correlation_id, None)   # 对暗号
            if future is not None and not future.done():
                future.set_result(message.body.decode())
            await message.ack()

        await callback_queue.consume(on_reply)

        for n in NUMBERS:
            await ask_square(channel, callback_queue, n)


asyncio.run(main())
```

两个终端配合跑:

```
终端 1:  uv run python "rabbitmq教程/07-特性速览/rpc_server.py"
终端 2:  uv run python "rabbitmq教程/07-特性速览/rpc_client.py"
```

## 3 quorum 队列

**是什么**:基于 Raft 共识的多副本队列类型。消息在多数节点确认后才算写入。

**解决什么**:broker 挂一台,消息不丢、服务不中断。前面所有队列都是 `classic`(单机队列)。

```python
queue = await channel.declare_queue(
    "ch7.quorum.demo",
    durable=True,                              # quorum 必须 durable
    arguments={"x-queue-type": "quorum"},      # 唯一的差别
)
```

| 场景 | 选型 |
|---|---|
| 单机、学习、非关键 | classic 足够 |
| 集群 + 消息不能丢(订单、支付) | **quorum**,官方建议新项目直接用 |
| 百万级堆积 | 曾用 lazy 队列;3.12 以后 classic 已具备类似行为,lazy 提得越来越少 |

- 管理台 Queues 页 Type 列能看到 classic / quorum
- 踩坑:**quorum 队列的 delete 不支持 `if_unused` / `if_empty` 旗标**,而 aio-pika 的 `delete()` 默认两个都开,必须显式关掉:

```python
await queue.delete(if_unused=False, if_empty=False)
```

`quorum.py`:

```python
"""第 7 讲·quorum 队列:声明的差别只有一个参数。

uv run python "rabbitmq教程/07-特性速览/quorum.py"
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        queue = await channel.declare_queue(
            "ch7.quorum.demo",
            durable=True,
            arguments={"x-queue-type": "quorum"},
        )
        await channel.default_exchange.publish(
            aio_pika.Message("存进 quorum 队列的一条消息".encode()),
            routing_key=queue.name,
        )
        message = await queue.get(no_ack=True)
        print(f"声明成功,消息进出正常: {message.body.decode('utf-8')}")
        print("管理台 Queues 页看 Type 列:quorum")

        await queue.purge()
        await queue.delete(if_unused=False, if_empty=False)   # quorum 不支持这两个旗标


asyncio.run(main())
```

## 4 管理 HTTP API

**是什么**:管理台网页背后的 REST 接口,认证后能做页面能做的一切。

**解决什么**:巡检积压、定时清理、自动化运维;Prometheus 抓 RabbitMQ 指标走的也是这套。

```bash
# 某 vhost 下所有队列:名字、消息数、消费者数
curl -s -u tianshiyang:tianshiyang http://62.234.16.180:15672/api/queues/lab

# 单个队列详情
curl -s -u tianshiyang:tianshiyang http://62.234.16.180:15672/api/queues/lab/ch2.tasks
```

| 常用端点 | 返回 |
|---|---|
| `/api/overview` | 集群概况、消息速率 |
| `/api/queues/<vhost>` | 队列列表(含 `messages`、`consumers`) |
| `/api/queues/<vhost>/<queue>` | 单队列详情 |
| `/api/exchanges/<vhost>` | 交换机列表 |

返回 JSON,配 `jq` 就是现成的监控数据源。

## 5 一句话名单

| 名字 | 是什么 | 什么时候想起它 |
|---|---|---|
| headers 交换机 | 按消息头键值对匹配路由 | 几乎不用,direct 更简单 |
| `x-single-active-consumer` | 队列多消费者但同时只有一个在收(一主多备) | 消费逻辑不支持并发时 |
| 集群 / Federation / Shovel | 多节点高可用 / 跨机房联邦 / 消息搬运 | 运维侧,开发知道名字即用途 |
| 流控与内存磁盘告警 | broker 内存超线用 TCP 背压挡住发布方 | 排查"发布突然变慢",看管理台 Alerts |

## 6 速查表

| 配置 | 位置 | 作用 |
|---|---|---|
| `x-max-priority` + `priority` | 队列 arguments + Message | 优先级,两头都要设 |
| `reply_to` + `correlation_id` | Message | RPC 的回信地址与暗号 |
| `x-queue-type: quorum` | 队列 arguments | 换成 Raft 多副本队列,必须 durable |
| `exclusive=True` | `declare_queue` | 本连接专属临时队列,断开自动删 |
| `/api/queues/<vhost>` | HTTP | 查队列积压 |
