# 第 6 讲 · TTL 与延迟队列

## 0 延迟队列 = TTL + 死信

RabbitMQ 没有原生的"定时消息"。标准做法是让消息在一个没有消费者的队列里躺够 TTL,过期变死信(第 5 讲的 `expired`),转投到真正的处理队列:

```
  发消息 ──► 等待队列(x-message-ttl=10秒,无消费者)
                   │ 到期 → expired 死信
                   ▼
             死信交换机 ──► 到点处理队列 ──► 消费者在这里等
```

消费者收到消息的那一刻 = 发送后第 10 秒。

适用需求:订单 30 分钟未支付自动取消、下单 5 分钟无人接单自动催、失败任务隔 60 秒重试。

---

## 1 队列级 TTL:x-message-ttl

**是什么**:队列的一个 argument,这个队列里**所有消息**统一寿命,单位毫秒。

**解决什么**:延迟队列的计时器。整队一个死期,broker 批量清理,高效且无副作用。

```python
wait = await channel.declare_queue(
    "ch6.pay.wait",
    durable=True,
    arguments={
        "x-message-ttl": 10_000,                    # 毫秒
        "x-dead-letter-exchange": "ch6.dlx",
        "x-dead-letter-routing-key": "pay.timeout", # 转投时改写路由键
    },
)
```

| argument | 单位 | 说明 |
|---|---|---|
| `x-message-ttl` | 毫秒 | 队列内消息统一存活时间 |
| `x-expires` | 毫秒 | **队列**闲置多久自动删除(删的是队列,不是消息),运维清理临时队列用 |

- 做延迟**只用队列级 TTL**,原因见 §3

---

## 2 消息级 TTL:expiration

**是什么**:给单条消息单独设寿命。

**解决什么**:几乎不用来做延迟(见 §3),知道它存在即可。

```python
aio_pika.Message(body, expiration=timedelta(seconds=15))
```

| 传入类型 | 含义 |
|---|---|
| `timedelta` | 按时长,**无歧义,推荐** |
| `int` / `float` | **按秒**计(aio-pika 内部乘 1000 转协议要求的毫秒) |

- 踩坑:传 `15_000` 想表达 15 秒,实际是 15000 秒(4 小时后才过期),现象是"什么都没发生"

---

## 3 队头阻塞:消息级 TTL 不能做延迟

**现象**:同一队列里 A(15 秒过期)先进、B(5 秒过期)后进,B 不会在第 5 秒死,而是等到第 15 秒跟着 A 一起死。

**原因**:RabbitMQ 的过期检查**只看队头**。队头的 A 没到期,后面已经逻辑过期的 B 一步都动不了;A 走后 B 升到队头,才被发现"早已过期"并立刻清走。

实测输出(`ttl_pitfall.py`):

```
t=0 秒:A(15 秒过期)、B(5 秒过期)先后入队
t=15.1 秒:死信到达 → A:15 秒后过期
t=15.2 秒:死信到达 → B:5 秒后过期
```

**结论**:同一个队列里的消息,延迟时长必须一致。需要多种延迟就按档位建队列:

```
延迟 5 秒  → delay.5s   (x-message-ttl=5000)
延迟 60 秒 → delay.60s  (x-message-ttl=60000)
延迟 30 分 → delay.30m  (x-message-ttl=1800000)
```

发布端按需要的延迟选队列投,各队各的节奏,互不阻塞。阶梯重试(失败一次进 5 秒档、再败进 15 秒档)就是这么搭的。

---

## 4 x-dead-letter-routing-key:一个 DLX 多个出口

**是什么**:死信转投时改写路由键。

**解决什么**:等待队列的消息是直投进来的,原路由键就是队列名,没有业务含义。改写后,死信交换机(用 direct)可以按键把不同种类的死信分流到不同队列。

```
                            ┌── pay.timeout ──► ch6.pay.timeout(超时处理)
  shop.dlx(direct) ────────┤
                            └── dead ─────────► ch6.dead(人工排查)
```

第 8 讲实战里,"付款超时"和"短信重试耗尽"两种死信走的就是同一个 DLX 的两个出口。

---

## 5 到点必须回查业务状态

延迟消息到点只说明"该看一眼了",不代表业务上该执行。

```python
async for message in timeout_queue.iterator():
    order_id = json.loads(message.body)["order_id"]
    if db.get(order_id)["status"] == "已付款":   # ← 回查当前状态
        pass                                     # 虚惊一场
    else:
        db.cancel(order_id, "超时未付款")
    await message.ack()
```

- 消息在队列里躺的 10 秒内用户可能已经付款,消息体里的 `status` 是 10 秒前的快照
- RabbitMQ **没有"撤回已发送消息"的 API**,所以只能在消费端回查兜底

---

## 6 官方延迟插件(了解)

`rabbitmq_delayed_message_exchange` 插件提供 `x-delayed-message` 交换机,发消息时带 `x-delay` 头即可任意延迟,不用拼 TTL+DLX。

| | 插件 | TTL+DLX 分档 |
|---|---|---|
| 任意延迟时长 | ✓ | ✗(按档位) |
| 需要装插件 | ✓ | ✗ |
| 云厂商托管服务 | 常常不提供 | 处处可用 |
| 可靠性 | 延迟消息存单节点 Mnesia,一般 | 与普通队列一致 |

企业主流仍是分档队列,插件了解即可。

## 7 完整示例

### delay_queue.py —— 订单 10 秒未付款自动取消

```python
"""第 6 讲·延迟队列:TTL + 死信实现"下单 10 秒未付款自动取消"。

    uv run python "rabbitmq教程/06-TTL与延迟队列/delay_queue.py"     # 约 11 秒跑完
"""

import asyncio
import json
import os
from datetime import datetime
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        # 死信交换机:direct,到点的消息走 pay.timeout 出口
        dlx = await channel.declare_exchange(
            "ch6.dlx", aio_pika.ExchangeType.DIRECT, durable=True
        )

        # 等待队列:躺 10 秒,到期死信转投,并把路由键改写成 pay.timeout
        wait = await channel.declare_queue(
            "ch6.pay.wait",
            durable=True,
            arguments={
                "x-message-ttl": 10_000,
                "x-dead-letter-exchange": "ch6.dlx",
                "x-dead-letter-routing-key": "pay.timeout",
            },
        )
        # 到点处理队列:消费者守在这里
        timeout_queue = await channel.declare_queue("ch6.pay.timeout", durable=True)
        await timeout_queue.bind(dlx, routing_key="pay.timeout")
        await wait.purge()
        await timeout_queue.purge()

        order = {"order_id": "D4001", "amount": 199, "status": "待付款"}
        await channel.default_exchange.publish(
            aio_pika.Message(json.dumps(order).encode("utf-8")),
            routing_key=wait.name,
        )
        print(f"{now()} 下单: {order}")
        print(f"{now()} 消息进入等待队列,10 秒倒计时开始")

        await asyncio.sleep(5)
        print(f"{now()} 5 秒,用户仍未付款")
        await asyncio.sleep(5)
        print(f"{now()} 10 秒,TTL 到期,死信转投到点处理队列")

        # 用 iterator 蹲守(get 是一次性的,蹲不到未来的消息)
        async for message in timeout_queue.iterator():
            received = json.loads(message.body)
            reason = message.headers["x-death"][0]["reason"]
            print(f"{now()} 收到超时事件: 订单 {received['order_id']}")
            print(f"    死因: {reason}")
            print(f"    回查订单状态 → {received['status']} → 执行取消、释放库存")
            await message.ack()
            break

        await wait.delete()
        # delete 默认 if_unused=True:有消费者挂着会拒绝删,这里显式硬删
        await timeout_queue.delete(if_unused=False)
        await dlx.delete()
        print(f"{now()} 清理完成")


asyncio.run(main())
```

### ttl_pitfall.py —— 队头阻塞实测

```python
"""第 6 讲·反面实验:消息级 TTL 的队头阻塞。

A 先进(15 秒过期)、B 后进(5 秒过期),实测两条一起在第 15 秒才死。

    uv run python "rabbitmq教程/06-TTL与延迟队列/ttl_pitfall.py"     # 约 16 秒跑完
"""

import asyncio
import os
import time
from datetime import timedelta
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        dlx = await channel.declare_exchange(
            "ch6.dlx", aio_pika.ExchangeType.DIRECT, durable=True
        )
        # 队列不设 x-message-ttl,只给每条消息单独设 expiration
        trap = await channel.declare_queue(
            "ch6.trap",
            durable=True,
            arguments={"x-dead-letter-exchange": "ch6.dlx"},
        )
        dead = await channel.declare_queue("ch6.trap.dead", durable=True)
        await dead.bind(dlx, routing_key="ch6.trap")   # 没配改写,沿用原路由键(队列名)
        await trap.purge()
        await dead.purge()

        await channel.default_exchange.publish(
            aio_pika.Message("A:15 秒后过期".encode(), expiration=timedelta(seconds=15)),
            routing_key=trap.name,
        )
        await channel.default_exchange.publish(
            aio_pika.Message("B:5 秒后过期".encode(), expiration=timedelta(seconds=5)),
            routing_key=trap.name,
        )
        start = time.monotonic()
        print("t=0 秒:A(15 秒过期)、B(5 秒过期)先后入队")
        print("按直觉 B 应在第 5 秒死。盯着死信队列:\n")

        arrivals = 0
        while arrivals < 2:
            message = await dead.get(no_ack=True, fail=False)
            if message is not None:
                arrivals += 1
                print(f"t={time.monotonic() - start:4.1f} 秒:死信到达 → "
                      f"{message.body.decode('utf-8')}")
            await asyncio.sleep(0.1)

        print("\n过期检查只看队头,A 不走 B 就出不来 —— 队头阻塞。")
        print("结论:多种延迟时长要按档位建队列。")

        await trap.delete()
        await dead.delete()
        await dlx.delete()


asyncio.run(main())
```

## 9 速查表

| 配置 | 写在哪 | 单位 | 作用 |
|---|---|---|---|
| `x-message-ttl` | 队列 arguments | 毫秒 | 队列内消息统一寿命,**做延迟用它** |
| `expiration` | `Message(...)` | timedelta / **秒** | 单条消息寿命,有队头阻塞,别用来做延迟 |
| `x-expires` | 队列 arguments | 毫秒 | 队列闲置多久自动删除 |
| `x-dead-letter-routing-key` | 队列 arguments | — | 转投时改写路由键,一个 DLX 分多个出口 |

三种死因至此到齐:`rejected`(第 5 讲)、`maxlen`(第 5 讲)、`expired`(本讲)。
