# 第 6 讲 · TTL 与延迟队列

企业需求列表里总有这么一条:订单 30 分钟不付款自动取消、下单 5 分钟后没骑手接单自动催单、失败的重试隔 60 秒再来一次。它们全是同一类问题——**让一条消息在指定时间后才被处理**。

RabbitMQ 没有原生的"定时消息",但第 5 讲攒的零件正好拼出这个能力:

```
  下单 ──► ch6.pay.wait(x-message-ttl=10秒 + 死信交换机)──► 躺 10 秒 ──► 到期死信
                                                                                │
  消费者守在这里 ◄──────── 到点处理队列(绑死信交换机) ◄──────── 转投 ←──────┘
```

消息在等待队列里躺够 TTL,broker 判它"过期而死"(第 5 讲三种死因的第二种),转投死信交换机,落到到点处理队列——消费者收到它的那一刻,恰好就是"下单后第 10 秒"。

> **敲黑板:** **延迟队列 = TTL 队列 + 死信**,没有任何新组件。这个组合是面试和实战的双高频。

两个脚本全文如下。`delay_queue.py` 是"10 秒自动取消"的完整骨架,照着敲;`ttl_pitfall.py` 是反面实验,照着敲一遍再跑,重点看现象。

## 完整代码

`delay_queue.py`(全文),订单超时取消迷你版:

```python
"""第 6 讲·延迟队列:订单 10 秒不付款自动取消(TTL + 死信组合)。

RabbitMQ 没有原生的"定时消息",延迟的标准做法是:
  业务消息 → 进"等待队列"(设 x-message-ttl)→ 到期死信 → 转投"到点处理队列" → 消费者收

    uv run python "rabbitmq教程/06-TTL与延迟队列/delay_queue.py"
"""

import asyncio
import json
import os
from datetime import datetime
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        # 死信交换机:direct 类型,到点的消息统一走 pay.timeout 这个出口
        dlx = await channel.declare_exchange("ch6.dlx", aio_pika.ExchangeType.DIRECT, durable=True)

        # 等待队列:消息进来躺 10 秒(x-message-ttl),到期后不丢弃,而是死信转投 ch6.dlx
        wait = await channel.declare_queue(
            "ch6.pay.wait",
            durable=True,
            arguments={
                "x-message-ttl": 10_000,  # 毫秒
                "x-dead-letter-exchange": "ch6.dlx",
                "x-dead-letter-routing-key": "pay.timeout",  # 转投时把路由键改写成这个
            },
        )
        # 到点处理队列:死信的最终落脚点,消费者守在这里
        timeout_queue = await channel.declare_queue("ch6.pay.timeout", durable=True)
        await timeout_queue.bind(dlx, routing_key="pay.timeout")
        await wait.purge()
        await timeout_queue.purge()

        # 下单:订单数据直接写在脚本里
        order = {"order_id": "D4001", "amount": 199, "status": "待付款"}
        await channel.default_exchange.publish(
            aio_pika.Message(json.dumps(order).encode("utf-8")),
            routing_key=wait.name,
        )
        print(f"{now()} 下单成功: {order}")
        print(f"{now()} 消息进了等待队列,开始倒计时 10 秒——付款窗口开着")

        await asyncio.sleep(5)
        print(f"{now()} 5 秒过去……用户没付款(真实场景里这 10 秒用户可能在输密码)")

        await asyncio.sleep(5)
        print(f"{now()} 10 秒到,TTL 过期,消息死信转投到点处理队列")

        # ③ 守到点处理队列,等死信落地(订阅模式,get 是一次性的蹲不到未来的消息)
        async for message in timeout_queue.iterator():
            received = json.loads(message.body)
            reason = message.headers["x-death"][0]["reason"]
            print(f"{now()} 收到超时事件: 订单 {received['order_id']}")
            print(f"    死亡档案里的死因: {reason}(TTL 过期的死信,reason 记的是 expired)")
            print(f"    回查订单状态 → {received['status']} → 执行自动取消、释放库存")
            await message.ack()
            break

        await wait.delete()
        # delete 默认 if_unused=True:队列还挂着消费者就拒绝删,这里显式硬删
        await timeout_queue.delete(if_unused=False)
        await dlx.delete()
        print(f"{now()} 演示结束,队列已清理")


asyncio.run(main())
```

`ttl_pitfall.py`(全文),单条消息 TTL 的坑:

```python
"""第 6 讲·反面实验:单条消息设 TTL 的"队头阻塞"坑。

往同一个队列塞两条消息:A 先进、15 秒过期;B 后进、5 秒过期。
直觉上 B 应该 5 秒就死——实际两条一起在第 15 秒才死,因为 RabbitMQ
只检查队头,队头的 A 没到期,后面已经过期的 B 一步都动不了。

    uv run python "rabbitmq教程/06-TTL与延迟队列/ttl_pitfall.py"
"""

import asyncio
import os
import time
from datetime import timedelta
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        dlx = await channel.declare_exchange("ch6.dlx", aio_pika.ExchangeType.DIRECT, durable=True)
        # 这个队列不给 x-message-ttl,只给每条消息单独设 expiration
        trap = await channel.declare_queue(
            "ch6.trap",
            durable=True,
            arguments={"x-dead-letter-exchange": "ch6.dlx"},
        )
        dead = await channel.declare_queue("ch6.trap.dead", durable=True)
        await dead.bind(dlx, routing_key="ch6.trap")  # 转投时默认沿用原路由键(队列名)
        await trap.purge()
        await dead.purge()

        await channel.default_exchange.publish(
            aio_pika.Message(
                "A:15 秒后过期".encode(), expiration=timedelta(seconds=15)
            ),  # ① 单条消息设 TTL
            routing_key=trap.name,
        )
        await channel.default_exchange.publish(
            aio_pika.Message("B:5 秒后过期".encode(), expiration=timedelta(seconds=5)),
            routing_key=trap.name,
        )
        start = time.monotonic()
        print("t=0 秒:A(15 秒过期)、B(5 秒过期)先后入队")
        print("按直觉,B 应该在第 5 秒变成死信,A 在第 15 秒。盯着死信队列看:")
        print()

        arrivals = 0
        while arrivals < 2:
            message = await dead.get(no_ack=True, fail=False)  # ② 轮询盯着死信队列,记录到达时刻
            if message is not None:
                arrivals += 1
                elapsed = time.monotonic() - start
                print(f"t={elapsed:4.1f} 秒:死信到达 → {message.body.decode('utf-8')}")
            await asyncio.sleep(0.1)

        print()
        print("看到了:B 明明 5 秒就到期,却和 A 一起在第 15 秒才出来——它排在没到期的 A 后面,")
        print("RabbitMQ 的过期检查只看队头,A 没走,B 到期了也动不了。")
        print("结论:要精确的延迟,别给单条消息设 TTL,按延迟时长分档建队列(见讲义)。")

        await trap.delete()
        await dead.delete()
        await dlx.delete()


asyncio.run(main())
```

## 逐段讲

### ① 两种 TTL,差在一个"排队检查"上

给消息设寿命有两个位置:

**队列级**:`x-message-ttl`,声明队列时挂在 arguments 里,**毫秒**。这个队列里所有消息统一寿命,到期由 broker 定期清理——因为整队一个死期,清理是批量的、高效的。**延迟队列只该用它**。

**消息级**:`aio_pika.Message(expiration=...)`,给单条消息单独设。它的坑就是本讲第二个实验的主角,先记住结论:**别用它做延迟**,原因见下。

另外还有个 `x-expires`(队列闲置多久自动删,删的是**队列本身**),和消息寿命不是一回事,运维清理临时队列用的,知道即可。

### ② x-dead-letter-routing-key:给死信指路

第 5 讲说过,死信转投默认沿用消息**原来的路由键**。等待队列的消息是直投进来的,原路由键就是队列名,没语义;配 `x-dead-letter-routing-key` 把它改写成有意义的键,死信交换机就能按键分流——一个 DLX 挂多个出口,每种死信各回各队。第 8 讲实战里,"付款超时"和"重试耗尽"两种死信走的就是同一个 DLX 的两个出口。

### ③ 消费端回查,别信消息里的旧状态

注意脚本里"回查订单状态"这一步。消息在队列里躺的 10 秒里,世界在变:用户可能第 8 秒付了款。

> **敲黑板:** 死信到点落地只说明"到点了",**不代表业务上该取消**——所以到点消费者必须回查订单的当前状态(真实项目里就是查数据库),查完"确实还没付款"才动手取消。消息里的 `status` 字段是 10 秒前的快照,只能当参考。这个"延迟消息到点必回查"的习惯,第 8 讲实战会再落地一次。

顺带,死因档案这次是 `expired`(第 5 讲的 rejected、maxlen 见过另外两种)——x-death 的 reason 三兄弟到齐了。

## 反面实验:单条消息 TTL 的队头阻塞

`ttl_pitfall.py` 往**同一个队列**塞两条消息:A 先进、15 秒过期(① 的 expiration);B 后进、5 秒过期。直觉上 B 应该第 5 秒就走,实测(② 记录到达时刻):

```
t=0 秒:A(15 秒过期)、B(5 秒过期)先后入队
按直觉,B 应该在第 5 秒变成死信,A 在第 15 秒。盯着死信队列看:

t=15.1 秒:死信到达 → A:15 秒后过期
t=15.2 秒:死信到达 → B:5 秒后过期
```

B 到期了却在队列里干等了 10 秒。原因:**RabbitMQ 的过期检查只看队头**。队头的 A 没到期,排在后面的 B 哪怕已经"逻辑死亡"也一步动不了;等 A 第 15 秒走了,B 升到队头,才被发现"早就过期",立刻清走。队头一直有人堵着,后面全部堵死——这就是**队头阻塞**。

> **敲黑板:** 由此得出延迟队列的黄金法则:**同一队列里的消息,延迟必须一致**。想要多种延迟时长,就按档位建队列,一档一队:
>
> ```
> 延迟 5 秒  → delay.5s   (x-message-ttl=5000)
> 延迟 60 秒 → delay.60s  (x-message-ttl=60000)
> 延迟 30 分 → delay.30m  (x-message-ttl=1800000)
> ```
>
> 发布端按需要的延迟选队列投,各队各的节奏,互不堵塞。(你上一轮课程里见过 `retry.5s / retry.15s / retry.60s` 三个队列,就是这条法则的落地——阶梯重试:失败一次进 5 秒档,再失败进 15 秒档,以此类推。)

`ttl_pitfall.py` 里还有一个写代码时真踩过的坑,顺手记下:aio-pika 的 `expiration` 参数,**传数字按"秒"算**(内部再乘 1000 转成协议要求的毫秒),传 `timedelta` 最无歧义。传了 `15_000` 想表达 15 秒,实际是 15000 秒——消息四个小时后才会过期,现象就是"什么都没发生"。

## 补充:官方延迟插件,知道就行

RabbitMQ 有个官方插件 `rabbitmq_delayed_message_exchange`,装了以后有一种 x-delayed-message 交换机,发消息时带 `x-delay` 头就能任意延迟,不用自己拼 TTL+DLX。它没进 RabbitMQ 主线,很多云厂商的托管服务不带它,而且插件本身把延迟消息存单节点 Mnesia,可靠性一般——所以企业里的主流仍然是"分档队列"这套土办法,插件当个选项了解即可。
