# 第 2 讲 · 工作队列与手动确认

第 1 讲一个消费者一条条收,没问题。但企业里队列的用法几乎总是这样的:

```
                              ch2.tasks 队列
  发任务的程序  ──10 个任务──►  [任务][任务][任务][任务]  ──┬──► 工人 A
                              (谁闲谁取,一起消化)          └──► 工人 B   ──► 再来几个也行
```

一堆任务进队,多个消费者竞争消费——处理不过来?再加一个消费者进程就行,不用改任何代码。这叫**工作队列**,是 RabbitMQ 里用得最广的形态:异步任务、削峰、日志处理,底子全是它。

本讲要靠实验看清三件事,每件都关系生产事故:

```
 ① 分活 ──► ② 出事 ──► ③ 反面教材
 prefetch    没ack就崩      no_ack=True
 (公平分发)  (消息重投)     (消息蒸发)
```

## 完整代码

发任务 `send_tasks.py`(全文)——任务清单写死在脚本里,重活(3 秒)全排在奇数位,实验二要靠它暴露问题:

```python
"""第 2 讲·发任务:往 ch2.tasks 队列放 10 个任务。

活分轻重:秒数就是"干这活要几秒"。重活全排在奇数位,这是故意的——
prefetch 实验要靠它看出"抢活不公平"和"公平分发"的差别。

    uv run python "rabbitmq教程/02-工作队列与手动确认/send_tasks.py"
"""

import asyncio
import json
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]

# 任务清单直接写死在这里:名字 + 要干多少秒
TASKS = [
    ("压缩商品图-1", 3),
    ("发送通知邮件-2", 1),
    ("压缩商品图-3", 3),
    ("发送通知邮件-4", 1),
    ("压缩商品图-5", 3),
    ("发送通知邮件-6", 1),
    ("压缩商品图-7", 3),
    ("发送通知邮件-8", 1),
    ("压缩商品图-9", 3),
    ("发送通知邮件-10", 1),
]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        queue = await channel.declare_queue("ch2.tasks", durable=True)
        await queue.purge()  # 清掉上一轮实验的残留,保证每次实验从零开始

        for name, seconds in TASKS:
            body = json.dumps({"name": name, "seconds": seconds}).encode("utf-8")
            await channel.default_exchange.publish(
                aio_pika.Message(body),
                routing_key=queue.name,
            )
            print(f"任务已入队: {name}(要干 {seconds} 秒)")

    print(f"\n共 {len(TASKS)} 个任务进队。去开两个终端跑 worker.py,看它们怎么分活")


asyncio.run(main())
```

```python
"""第 2 讲·发一个"会出事"的任务,专门用来砸崩消费者。

配合 worker.py 做实验:worker 干到这条任务时会假装进程崩溃(还没 ack)。
看看 broker 会不会把这条消息还回来。

    uv run python "rabbitmq教程/02-工作队列与手动确认/send_poison.py"
"""

import asyncio

import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

asyncio.run(main())
```

正经工人 `worker.py`(全文),**本讲主角**:

```python
"""第 2 讲·干活的人:消费 ch2.tasks,干完一个 ack 一个。

参数写死在文件开头的 PREFETCH / WORKER 两行,要换就改文件、保存、重跑。

开两个终端各跑一个,观察分活;撞上"会出事的订单"会假装崩溃——
重启它,看那条消息是不是被 broker 重新投递了(redelivered 标记)。
"""

import asyncio
import json
import os
from datetime import datetime
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]

# 一次最多从队列拿几条"还没 ack"的消息:0 = 不限制,1 = 严格干完一条再拿一条
# 实验一/实验三用 1,实验二改成 10 再跑
PREFETCH = 1
# 工人名字,输出才分得清谁干的活。开第二个终端前改成"李四"——
# 已启动的进程用的是启动那一刻读到的值,互不影响
WORKER = "张三"


def now() -> str:
    return datetime.now().strftime("%H:%M:%S")


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=PREFETCH)  # ① 限流:在途未 ack 的最多 PREFETCH 条
        queue = await channel.declare_queue("ch2.tasks", durable=True)

        print(f"[{now()}] {WORKER} 上岗(prefetch={PREFETCH}),开始接活……")

        async for message in queue.iterator():  # ② 订阅:broker 推一条,循环走一轮
            task = json.loads(message.body)
            print(
                f"[{now()}] [{WORKER}] 接单: {task['name']},干 {task['seconds']} 秒"
                f"{'  ← 这条是崩过后重新投递的' if message.redelivered else ''}"
            )
            await asyncio.sleep(task["seconds"])  # ③ 模拟干活

            if "会出事" in task["name"] and not message.redelivered:
                print(f"[{now()}] [{WORKER}] 处理到一半进程崩溃!没 ack,broker 会把消息收回去")
                os._exit(1)  # ④ 硬退出,不走任何清理,连接直接断

            await message.ack()  # ⑤ 干完了才 ack,broker 这时才删
            print(f"[{now()}] [{WORKER}] 干完并确认: {task['name']}")


asyncio.run(main())
```

反面教材 `worker_autoack.py`(全文),和 worker.py 的差别只有消费那一行:

```python
"""第 2 讲·反面教材:自动确认模式的消费者。

no_ack=True 时,broker 把消息推出去的瞬间就删,消费者死活它不管。
跑一遍 send_poison.py 再跑本脚本:worker 崩了,那条消息就永远没了。

    uv run python "rabbitmq教程/02-工作队列与手动确认/worker_autoack.py"
"""

import asyncio
import json
import os
from datetime import datetime
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        queue = await channel.declare_queue("ch2.tasks", durable=True)

        print(f"[{datetime.now():%H:%M:%S}] 自动确认模式的工人上岗(no_ack=True)")
        async for message in queue.iterator(no_ack=True):  # ① 推出去的瞬间 broker 就把消息删了
            task = json.loads(message.body)
            print(f"接单: {task['name']},干 {task['seconds']} 秒")
            await asyncio.sleep(task["seconds"])

            if "会出事" in task["name"]:
                print("处理到一半进程崩溃!——但 broker 早已把消息删了,这条消息永远丢了")
                os._exit(1)

            print(f"干完: {task['name']}")


asyncio.run(main())
```

## 逐段讲

### ① set_qos(prefetch_count=...)

prefetch 是本讲的第一个主角。它限制的是:这个消费者手上最多同时攥几条"推过来但还没 ack"的消息。broker 不是等一个消费者 ack 完才发下一条的,它一见队列有消息就往外推,prefetch 就是给推的速度装了个闸:

- `prefetch_count=1`:严格一条——处理完、ack 了,下一条才进来。工人永远只攥一件活。
- `prefetch_count=10`:broker 一口气能推 10 条到你手上囤着。
- `prefetch_count=0`:不限,队列里有多少推多少,工人被撑爆为止。

> **敲黑板:** prefetch 管的是"在途未确认的消息",所以只有手动 ack 模式下它才有意义。no_ack 模式消息发出去就算完,压根没有"在途"概念,闸门形同虚设,这也是 worker_autoack.py 的另一宗罪。

经验值:任务重、处理慢,1~10;消息轻、追求吞吐,几十上百。没有标准答案,看消费能力。

### ② iterator() 里的接单与 `redelivered`

`async for message in queue.iterator()` 订阅队列(第 1 讲的老朋友)。接单打印里多了一句 `message.redelivered`,重投标记:broker 重新投递的消息,这个属性是 True。它哪来的,看下面③④⑤的闭环。

### ③④⑤ 手动 ack 的完整闭环

第 1 讲说了,消息投递给消费者后并不删除,只标记"已投递未确认"。现在把这个闭环走完整:

- ⑤ `await message.ack()`:处理成功,告诉 broker 可以删了。
- 工人**没 ack 就死了**(④ 的 `os._exit(1)` 模拟猝死,不走任何清理):broker 察觉连接断开,把"已投递未确认"的消息收回队列、重新投递给还活着的消费者。消息没丢,只是又排队了。
- 重投的消息带着 `redelivered=True`——② 那行打印靠它区分"第一次来的"和"坑过人又回来的"。

④ 那个 `if` 还藏了一个真实模式:毒消息(内容有问题、谁来谁死的消息)会把工人无限连环崩——崩溃、重投、再崩溃。所以代码写的是"第一次见它才崩;重投回来的,说明它坑过我一回,这回人工兜底收下"。这是最粗糙的解毒法,正经解法是死信队列,第 5 讲的主角。

> **敲黑板:** 重投必然意味着"可能被处理多次"。工人第一次干到一半才崩,重投后从头再干,所以消费者必须幂等:干一半的活要有办法识别出"这条我见过"。最简单的做法是任务表里记状态,收到消息先查再做。幂等不是 RabbitMQ 的功能,是消费端的必修课,第 8 讲实战里会真刀真枪写一遍。

### worker_autoack.py 的 ①:no_ack=True 的代价

自动确认:broker 把消息推出去的瞬间就删除,之后消费者是死是活,它不知道也不管。工人崩在处理中途,这条消息就此从世界上消失,实验四会让你看到队列消息数归零、重启工人干等不到任何东西。

什么时候能用 no_ack?消息丢了也无所谓的场景,比如日志采集(丢一条日志天不塌)。凡是要"任务必须完成"的场合,手动 ack 没得商量。

## 跑起来(四个实验)

所有命令在仓库根目录执行。**开两个工人时,先开工人在那儿等,再发任务**——工人是常驻进程,真实项目里它们永远先在线。

工人的参数写死在 `worker.py` 开头,换实验就改那两行、保存、重跑。注意已启动的进程用的是它启动那一刻读到的值:终端 1 用"张三"跑起来之后,你把 WORKER 改成"李四"再开终端 2,终端 1 照旧是张三,互不影响。

**实验一:竞争消费 + 公平分发。** 两个终端各开一个 prefetch=1 的工人(第二个开工人前把 WORKER 改成"李四"),第三个终端发任务:

```
终端 1:  uv run python "rabbitmq教程/02-工作队列与手动确认/worker.py"    # 文件里 WORKER="张三"
终端 2:  把 WORKER 改成"李四"保存,跑同一条命令
终端 3:  uv run python "rabbitmq教程/02-工作队列与手动确认/send_tasks.py"
```

两个工人交替接单,总活 20 秒(5 个 3 秒 + 5 个 1 秒),一人分到约 10 秒,同时开工同时收工——prefetch=1 时,谁 ack 了 broker 才给谁派下一条,快的自然多干,慢的少干,这就是**公平分发**。干完工人继续守着,Ctrl+C 下岗。

**实验二:prefetch=10 的不公平。** 同样的流程,先把 PREFETCH 改成 10、WORKER 改回"张三",Ctrl+C 停掉上一轮的两个工人再重开:

```
终端 1:  uv run python "rabbitmq教程/02-工作队列与手动确认/worker.py"    # WORKER="张三"
终端 2:  把 WORKER 改成"李四"保存,跑同一条命令
终端 3:  uv run python "rabbitmq教程/02-工作队列与手动确认/send_tasks.py"
```

我跑出来的是:张三一口气收走全部 5 个轻活,5 秒干完闲死;李四攥着 5 个重活吭哧了 15 秒。原因是 broker 轮流派活时一次派一摞——重活全在奇数位,李四那一摞全是硬骨头,张三早早 ack 完自己那摞,却干看着兄弟受苦(prefetch 内的消息不能转手)。

> **敲黑板:** **prefetch 越大吞吐越高,但分活越盲目**。消费者处理速度不均的团队,别把 prefetch 开太大,这是生产上"加机器不见吞吐涨"的常见根源之一。

**实验三:崩溃与重新投递。** 先把 PREFETCH 改回 1(工人叫谁都行):

```
uv run python "rabbitmq教程/02-工作队列与手动确认/send_poison.py"
uv run python "rabbitmq教程/02-工作队列与手动确认/worker.py"    # 撞上毒消息,进程崩(退出码 1)
uv run python "rabbitmq教程/02-工作队列与手动确认/worker.py"    # 重启,同一条消息回来了
```

第二次启动会打印 `← 这条是崩过后重新投递的`,然后工人把它 ack 掉。消息没丢——代价是它被处理了两次的开头(第一次干到一半)。

**实验四:自动确认的丢失。**

```
uv run python "rabbitmq教程/02-工作队列与手动确认/send_poison.py"
uv run python "rabbitmq教程/02-工作队列与手动确认/worker_autoack.py"    # 崩了
uv run python "rabbitmq教程/02-工作队列与手动确认/worker_autoack.py"    # 再启动:干等,啥也收不到
```

第二次启动干等到你 Ctrl+C 为止——消息在第一次推出去时就删了。同一个毒消息,手动 ack 下它活着回来,自动确认下它尸骨无存。生产上禁用 no_ack,凭的就是这组对照。

## 补充:process() 语法糖

手动 ack 写多了会烦,aio-pika 提供了个糖:

```python
async with message.process():  # 块内正常走完 → 自动 ack;抛异常 → 自动 nack(requeue=True)
    await 干活()
```

日常业务消费,处理逻辑能一行扛住时就用它,少写两行不漏 ack。但重试、死信这些需要精细控制 nack 参数的场景,还得手动来。本课程为了让你看清确认机制的每一步,统一手写。
