# 第 2 讲 · 工作队列与手动确认

## 0 工作队列

**是什么**:多个消费者订阅同一个队列,消息每条只投给其中一个。

**解决什么**:处理不过来就多开几个消费者进程,生产者和代码都不用改。异步任务、削峰、日志处理的底子全是它。

```
                              ch2.tasks 队列
  发任务的程序  ──10 个任务──►  [任务][任务][任务][任务]  ──┬──► 工人 A(张三)
                              (每条只给一个,谁闲谁取)      └──► 工人 B(李四)
```

本讲三件事,件件关系生产事故:

| # | 主题 | 关键词 |
|---|---|---|
| 1 | 分活 | `prefetch` 公平分发 |
| 2 | 出事 | 没 ack 就崩 → 消息重投,`redelivered` |
| 3 | 反面教材 | `no_ack=True` 消息蒸发 |

---

## 1 set_qos:prefetch 限流

**是什么**:限制这个消费者手上最多同时攥几条"推过来但还没 ack"的消息。

**解决什么**:broker 见队列有消息就往外推,不管消费者吃不吃得下。prefetch 是给推的速度装闸,也决定了分活的公平性。

```python
await channel.set_qos(prefetch_count=1)
```

| 取值 | 行为 |
|---|---|
| `1` | 干完一条、ack 了,下一条才进来。**公平分发**:谁快谁多干 |
| `10` | broker 一口气推 10 条囤着 |
| `0` | 不限,队列有多少推多少 |

- prefetch 管的是"在途未确认的消息",**只有手动 ack 模式下才有意义**,no_ack 模式下形同虚设
- 经验值:任务重、处理慢 → 1~10;消息轻、追求吞吐 → 几十上百。没有标准答案,看消费能力
- prefetch 越大吞吐越高,但分活越盲目:消费者速度不均的团队开大了,会出现"快的闲死、慢的累死",这是生产上"加机器不见吞吐涨"的常见根源之一

---

## 2 手动 ack 的完整闭环

**是什么**:消息投给消费者后不删,标记"已投递未确认";`ack()` 之后 broker 才真正删除。

**解决什么**:消费者拿到消息、没处理完就崩 → broker 察觉连接断开,把未确认的消息收回队列、重新投递。消息不丢。

```
  broker 投递 ──► 消费者处理 ──┬── ack()    → broker 删除,圆满
                              └── 进程崩溃  → broker 收回,重投(redelivered=True)
```

| API | 说明 |
|---|---|
| `await message.ack()` | 处理成功,告诉 broker 可以删了 |
| `message.redelivered` | 重投标记:这条消息之前投过、没被确认。`True` = 坑过人又回来的 |
| `os._exit(1)` | 模拟猝死:不走任何清理,连接直接断,实验里用它制造"没 ack 就崩" |

- **重投必然意味着可能被处理多次**:第一次干到一半才崩,重投后从头再干。所以消费者必须**幂等**——干一半的活要有办法识别出"这条我见过"(任务表记状态、收到先查再做)。幂等不是 RabbitMQ 的功能,是消费端的必修课,第 8 讲实战真刀真枪写一遍
- 毒消息(内容非法、谁来谁死的消息)在"崩溃 → 重投"循环里会连环崩工人。最粗糙的解毒法是见 `redelivered=True` 就人工兜底收下;正经解法是死信队列,第 5 讲

---

## 3 no_ack=True:自动确认

**是什么**:broker 把消息推出去的**瞬间**就删除,消费者是死是活它不管。

```python
async for message in queue.iterator(no_ack=True):
    ...
```

| | 手动 ack | no_ack=True |
|---|---|---|
| 消息删除时机 | ack 之后 | 推出的瞬间 |
| 消费者崩在处理中途 | 消息重投,不丢 | **消息永远消失** |
| prefetch 有效 | ✓ | ✗(没有"在途"概念) |
| 适用 | 凡是"任务必须完成"的场合 | 丢了也无所谓的:日志采集 |

生产上默认手动 ack,凭的就是这组对照:同一个毒消息,手动 ack 下它活着回来,自动确认下尸骨无存。

## 4 process() 语法糖

手动 ack 写多了会烦,aio-pika 提供了糖:

```python
async with message.process():   # 块内正常走完 → 自动 ack;抛异常 → 自动 nack(requeue=True)
    await 干活()
```

处理逻辑简单时用它,少写两行不漏 ack。但重试、死信这些需要精细控制 nack 参数的场景还得手动来。本课程为了看清确认机制的每一步,统一手写。

## 5 完整示例

仓库里不提供 `.py`,照着敲到本目录。参数写死在 `worker.py` 开头,换实验改那两行、保存、重跑。已启动的进程用的是启动那一刻读到的值,互不影响。

### send_task.py

```python
"""第 2 讲·发任务:往 ch2.tasks 队列放 10 个任务。

活分轻重:秒数就是"干这活要几秒"。重活全排在奇数位,这是故意的——
prefetch 实验要靠它看出"抢活不公平"和"公平分发"的差别。

    uv run python "rabbitmq教程/02-工作队列与手动确认/send_task.py"
"""

import asyncio
import json
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]

# 任务清单直接写死在这里:名字 + 要干多少秒
TASKS = [
    ("压缩商品图-1", 3),
    ("发送通知邮件-2", 1),
    ("压缩商品图-3", 3),
    ("发送通知邮件-4", 1),
    ("压缩商品图-5", 3),
    ("发送通知邮件-6", 1),
    ("压缩商品图-7", 3),
    ("发送通知邮件-8", 1),
    ("压缩商品图-9", 3),
    ("发送通知邮件-10", 1),
]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        queue = await channel.declare_queue("ch2.tasks", durable=True)
        await queue.purge()   # 清掉上一轮实验的残留,保证每次从零开始

        for name, seconds in TASKS:
            body = json.dumps({"name": name, "seconds": seconds}).encode("utf-8")
            await channel.default_exchange.publish(
                aio_pika.Message(body),
                routing_key=queue.name,
            )
            print(f"任务已入队: {name}(要干 {seconds} 秒)")

    print(f"\n共 {len(TASKS)} 个任务进队。去开两个终端跑 worker.py,看它们怎么分活")


asyncio.run(main())
```

### worker.py(本讲主角)

```python
"""第 2 讲·干活的人:消费 ch2.tasks,干完一个 ack 一个。

参数写死在文件开头的 PREFETCH / WORKER 两行,要换就改文件、保存、重跑。
开两个终端各跑一个(第二个先把 WORKER 改名),观察分活;
撞上"会出事的订单"会假装崩溃——重启它,看那条消息是不是被 broker 重新投递了。
"""

import asyncio
import json
import os
from datetime import datetime
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]

# 一次最多攥几条"还没 ack"的消息:0 = 不限,1 = 干完一条再拿一条
# 实验一用 1,实验二改成 10 再跑
PREFETCH = 1
# 工人名字,输出才分得清谁干的活。开第二个终端前改名
WORKER = "张三"


def now() -> str:
    return datetime.now().strftime("%H:%M:%S")


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=PREFETCH)   # ① 限流
        queue = await channel.declare_queue("ch2.tasks", durable=True)

        print(f"[{now()}] {WORKER} 上岗(prefetch={PREFETCH}),开始接活……")

        async for message in queue.iterator():           # ② 订阅
            task = json.loads(message.body)
            print(
                f"[{now()}] [{WORKER}] 接单: {task['name']},干 {task['seconds']} 秒"
                f"{'  ← 这条是崩过后重新投递的' if message.redelivered else ''}"
            )
            await asyncio.sleep(task["seconds"])         # ③ 模拟干活

            if "会出事" in task["name"] and not message.redelivered:
                print(f"[{now()}] [{WORKER}] 处理到一半进程崩溃!没 ack,broker 会把消息收回去")
                os._exit(1)                              # ④ 硬退出,不走任何清理

            await message.ack()                          # ⑤ 干完了才 ack
            print(f"[{now()}] [{WORKER}] 干完并确认: {task['name']}")


asyncio.run(main())
```

**实验一:竞争消费 + 公平分发(prefetch=1)。** 两个终端各开一个工人(第二个开之前把 `WORKER` 改成"李四"),第三个终端发任务:

## 7 速查表

| API / 参数 | 位置 | 默认 | 作用 |
|---|---|---|---|
| `set_qos(prefetch_count=N)` | 信道 | 0(不限) | 在途未 ack 消息的上限,公平分发的开关 |
| `message.ack()` | 消费端 | — | 确认,broker 此时才删 |
| `message.redelivered` | 消息属性 | False | 重投标记 |
| `iterator(no_ack=True)` | 消费端 | False | 自动确认,推出即删,**慎用** |
| `message.process()` | 消费端 | — | 语法糖:块正常走完自动 ack,异常自动 nack |
