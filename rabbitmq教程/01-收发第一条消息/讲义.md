# 第 1 讲 · 收发第一条消息

先把整个 RabbitMQ 的世界压缩成一张图,这一讲只动图里这三个框:

```
                 ┌─────────────── broker(服务器上的 RabbitMQ)───────────────┐
                 │                                                        │
  生产者 send.py │      交换机(这一讲先用自带的默认交换机)      ch1.hello 队列  │   消费者 receive.py
  ───发消息───►  │  ─────────────────────────────────────────►  [ msg ][ msg ][ msg ] ───取消息───►  收到后 ack
                 │                                                        │
                 └────────────────────────────────────────────────────────┘
```

生产者不直接把消息塞给消费者——它根本不知道消费者是谁、在不在、有几个。它只管把消息丢进队列,消息在队列里排队,谁订阅这个队列谁就取走。就这么一个模型,撑起了后面七讲的所有花样:交换机换着法儿路由(第 3 讲)、消费失败重新排队(第 2 讲)、消息死了进死信(第 5 讲)。

本讲两个文件,每个十几行,是全套课程的骨架,后面每一讲都是在这副骨架上加零件。代码全文如下。仓库里没有这两个文件,得你自己开两个空文件从零敲(别复制),存成本目录下的 `send.py` 和 `receive.py`(文件名别改,下面的命令按名字找文件),敲完跑通,这讲就毕业了。后面七讲同理:讲义是唯一的代码来源。

## 完整代码

发送端 `send.py`(全文):

```python
"""第 1 讲·发送端:往 ch1.hello 队列里放三条消息。

在仓库根目录(ai-lab)下执行:
    uv run python "rabbitmq教程/01-收发第一条消息/send.py"
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

# 从仓库根目录的 .env 读连接地址(仓库是公开的,密码不能写进代码)
load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)  # ① 建立连接
    async with connection:  # ② 出了这个块,连接自动关
        channel = await connection.channel()  # ③ 开一条信道

        queue = await channel.declare_queue("ch1.hello", durable=True)  # ④ 声明队列

        # 三条消息的"业务数据"直接写在下面,跑之前不用准备任何东西
        messages = [
            "你好,RabbitMQ",
            "第二条:一张外卖订单",
            "第三条:一条短信验证码",
        ]
        for text in messages:
            await channel.default_exchange.publish(  # ⑤ 经默认交换机,直投队列
                aio_pika.Message(text.encode()),  # ⑥ 消息体必须是 bytes
                routing_key=queue.name,  # ⑦ 队列名当路由键,直达 ch1.hello
            )
            print(f"已发送: {text}")

    print("发完了。现在打开管理台 Queues 页,ch1.hello 里躺着 3 条消息等消费者来取")
    print("管理台地址: http://62.234.16.180:15672(账号密码同 .env 里的 RABBITMQ_URL)")


asyncio.run(main())
```

接收端 `receive.py`(全文):

```python
"""第 1 讲·接收端:守着 ch1.hello 队列,来一条收一条,收到第 3 条后自己退出。

在仓库根目录(ai-lab)下执行:
    uv run python "rabbitmq教程/01-收发第一条消息/receive.py"
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        # 和 send.py 一字不差地再声明一次:声明是幂等的,队列已存在就只是"拿到引用"
        queue = await channel.declare_queue("ch1.hello", durable=True)

        print("接收端已启动,等消息进来……")
        received = 0
        async for message in queue.iterator():  # ⑧ 订阅:broker 推一条,循环走一轮
            text = message.body.decode()
            received += 1
            print(f"收到第 {received} 条: {text}")
            await message.ack()  # ⑨ 告诉 broker:这条处理完了,你可以删了

            if received == 3:
                break  # 收满三条,教程脚本到此为止

    print("全部收到,连接关闭,进程退出")


asyncio.run(main())
```

## 逐段讲

### 连接地址,以及为什么从 .env 读

`RABBITMQ_URL` 长这样:

```
amqp://用户名:密码@主机:端口/vhost
```

vhost 是 broker 里的隔离舱,队列、交换机都关在 vhost 里,不同 vhost 互相看不见。咱们教程用的是专门建的 `lab`,和你服务器上业务测试用的 `clouddisk` 互不相干,教程里随便折腾不会误伤业务。有个历史包袱要知道:默认 vhost 名字是 `/`,写进 URL 时必须转义成 `%2F`,否则连错地方。咱们的 `lab` 没这问题。

URL 还能挂参数,如 `...?heartbeat=30`:心跳间隔秒数,长时间没流量的连接会被防火墙当死链掐掉,生产环境的常驻消费者一般加上,学习阶段用默认就行。

这套地址带着密码,而这个仓库推在公网 GitHub 上,所以它待在 `.env` 里(已被 .gitignore 排除),代码里用 `load_dotenv` 去读。`Path(__file__).parents[2]` 是从脚本位置往上跳两级回到仓库根目录。这套四行样板后面每一讲的脚本开头都原样出现,混个脸熟就行。

### ① aio_pika.connect(url)

建立到 broker 的 TCP 连接,握手、鉴权都在这一步。

> **敲黑板:** 它是协程函数,await 不能丢:忘了 await 不报错,只是拿到一个从没跑过的协程对象,下一行用的时候才炸。aio-pika 里所有方法都是协程,这个坑全课程通用,后面不再重复。

### ② async with connection:

连接可以当上下文管理器用,出了块自动关闭。不这么写就得自己记着 `await connection.close()`,一旦中间抛异常,关闭那行就被跳过了。学习脚本跑完就退,连接断不断无所谓,但从第一天就写对,省得以后补课。

### ③ connection.channel()

**连接是 TCP 级的,信道是连接里面的逻辑通道**,发消息、收消息、声明队列这些动作全发生在信道上。为什么不直接用连接干活?TCP 连接建立成本高,信道是廉价的,一个连接里开几十条信道,各自的动作互不干扰,和数据库连接池里"一条连接上开多个会话"是同一个思路。咱们每讲脚本就开一条信道,够用;等你在真实项目里一条连接跑多个消费者时,会感谢这个设计。

### ④ declare_queue("ch1.hello", durable=True)

声明队列 = "如果不存在就建,存在就拿到它的引用",所以 send.py 和 receive.py 各写一遍完全合法,谁先启动都行。这叫**幂等声明**,后面每一讲的脚本都靠它各自把拓扑建起来,不存在"必须先跑 A 再跑 B"的顺序要求。

> **敲黑板:** 同名队列重复声明时,参数必须一字不差。队列已存在,你又拿不同参数声明同一个名字,broker 直接报错并把信道关掉。以后你改了脚本里的队列参数、而老队列还在 broker 上,就会撞上这个错,最快的解法是去管理台把旧队列删了重跑。

`durable=True` 是让队列的定义在 broker 重启后依然存在,先记住"生产恒开",为什么、和消息落盘是什么关系,第 4 讲专门掰扯。

### ⑤⑥⑦ default_exchange.publish(...)

broker 里有个自带的交换机,名字是空字符串,叫默认交换机。它的规则简单粗暴:**路由键写什么队列名,消息就直投哪个队列**:`routing_key="ch1.hello"`,消息就进 ch1.hello,不需要任何绑定。这一讲借它把"发消息"跑通,第 3 讲才轮到真正的三种交换机登场。

`aio_pika.Message(...)` 构造消息,`body` 必须是 bytes:传字符串当场报错,所以有 `.encode()`(Python 默认就按 utf-8 编码);收到时对应 `.decode()`。真实业务里更常见的写法是 `json.dumps(业务字典).encode()`,收方 `json.loads`,第 2 讲就这么干了。

还有一件事悄悄发生了:aio-pika 的信道默认开着 **publisher confirm**,每条 publish 都会等 broker 回一句"收到了"才往下走。`await publish(...)` 返回了,消息就确实进 broker 了。这个机制第 4 讲细讲。

### ⑧ queue.iterator()

`async for message in queue.iterator()` 是订阅模式:注册一个消费者,broker 有消息就推过来,循环体走一轮。和它等价的另一种写法是回调式 `await queue.consume(回调函数)`,效果一样,教程统一用迭代器,好读。

订阅和"轮询查库"的区别值得体会:消费者挂上之后就在那儿等,消息产生的瞬间就被推过来,没有轮询间隔、没有空转。这就是 MQ 叫"消息中间件"的本钱。

### ⑨ message.ack()

> **敲黑板:** 收到消息后,消息并没有从 broker 里删掉,只是打上"已投递未确认"的标记。等你 `await message.ack()`,broker 才真正删掉它。消费者拿到消息、没处理完就崩了怎么办?没 ack,broker 知道这条没处理完,会重新投递,第 2 讲整个就是拿实验把这件事看清楚。

顺带:`ack()` 也是协程,忘 await 又是那个静默坑。

## 跑起来

两个终端,先发后收(反着来也行,receive.py 先启动等在那儿,send.py 一发,消息瞬间被推走,现象更直观):

```
$ uv run python "rabbitmq教程/01-收发第一条消息/send.py"
已发送: 你好,RabbitMQ
已发送: 第二条:一张外卖订单
已发送: 第三条:一条短信验证码
```

```
$ uv run python "rabbitmq教程/01-收发第一条消息/receive.py"
接收端已启动,等消息进来……
收到第 1 条: 你好,RabbitMQ
收到第 2 条: 第二条:一张外卖订单
收到第 3 条: 第三条:一条短信验证码
```

**这个实验值得做一遍**:send.py 跑完后别启动 receive.py,先打开管理台 `http://62.234.16.180:15672`(账号密码就是 .env 里 URL 里那对),Queues 页里找 `ch1.hello`,Features 列有个 `D`(durable),消息数是 3。这时候你可以把 receive.py 跑起来、Ctrl+C 掐掉、隔十分钟再跑,消息一条不少——队列是个能长期存东西的仓库,不是流水的管子。看完到管理台把 ch1.hello 删掉(Queues 页点进队列,拉到底 Delete Queue),给下一讲腾地方。
