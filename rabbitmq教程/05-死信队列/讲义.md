# 第 5 讲 · 死信队列

第 2 讲留了个尾巴:毒消息(谁来谁失败的消息)如果不处理,消费者就是"崩溃→重投→再崩溃"的死循环;`nack(requeue=False)` 倒是能掐断循环,但消息直接消失,出了问题连个尸首都没有。企业的标准答案是**死信队列(Dead Letter Queue)**——先看消息死后的一条完整流转:

```
                          消费者 nack(requeue=False) ──────────┐
                                                          死了 │
  ┌── 业务队列(声明时挂 x-dead-letter-exchange)─────────────────┴──┐
  │   消息的三种死法:                                                  │
  │     ① 消费失败:nack/reject 且 requeue=False                       │
  │     ② 寿终正寝:消息 TTL 到点(第 6 讲主角)                          │
  │     ③ 队列满了:达到 x-max-length,老消息被挤掉                     │
  └──────────────────────────┬───────────────────────────────────┘
                             │ broker 自动转投(附 x-death 死亡档案)
                             ▼
                    死信交换机(普通交换机)──► 死信队列(普通队列)──► 告警/人工排查/修复后重放
```

死信队列不是什么新的队列类型,就是一组配置:队列声明时挂一个 `x-dead-letter-exchange`,消息死掉时 broker 自动把它转投过去。没配这个参数的队列,死掉的消息就是真丢了。

本讲一个脚本跑两个实验,全文如下,值得整篇敲一遍,第 8 讲实战用的就是它。

## 完整代码

`dead_letter.py`(全文):

```python
"""第 5 讲·死信队列:消息"死"了不丢,而是被转投到一个专门的收容队列。

两个实验:
  实验一:消费者 nack(requeue=False),消息进死信(原因 rejected)
  实验二:队列设了最大长度,挤掉的老消息进死信(原因 maxlen)

    uv run python "rabbitmq教程/05-死信队列/dead_letter.py"
"""

import asyncio
import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]


def decode(value: object) -> object:
    """x-death 档案里的字段偶尔以 bytes 传过来,统一转成能看的"""
    return value.decode("utf-8") if isinstance(value, bytes) else value


async def drain(queue: aio_pika.Queue) -> list[str]:
    """把队列里现成的消息倒出来。注意 get 是一次性动作:队列当下是空的就返回 None,
    不会等新消息,所以调用前要给 broker 留出干活的时间"""
    messages = []
    while True:
        message = await queue.get(no_ack=True, fail=False, timeout=2)
        if message is None:
            return messages
        messages.append(message.body.decode("utf-8"))


async def show_dead(queue: aio_pika.Queue, title: str) -> None:
    print(f"\n{title}")
    while True:
        message = await queue.get(no_ack=True, fail=False, timeout=2)
        if message is None:
            return
        body = message.body.decode("utf-8")
        print(f"  收到死信: {body}")
        for death in message.headers.get("x-death", []):  # 一条消息可能死过好几轮,每轮一条档案
            print(
                f"    死亡档案: 原因={decode(death.get('reason'))}  "
                f"原队列={decode(death.get('queue'))}  "
                f"死亡次数={decode(death.get('count'))}  "
                f"时间={decode(death.get('time'))}"
            )


async def main() -> None:
    connection = await aio_pika.connect(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()

        # 死信交换机:一个普通的 fanout 交换机。哪个队列声明时配了它,死掉的消息就转投过来
        dlx = await channel.declare_exchange(  # ① 死信交换机:一个普通 fanout 而已
            "ch5.dlx", aio_pika.ExchangeType.FANOUT, durable=True
        )
        dead = await channel.declare_queue("ch5.dead", durable=True)  # 死信收容所
        await dead.bind(dlx)
        await dead.purge()

        # ── 实验一:消费失败,主动把消息"处死" ───────────────────────────────
        orders = await channel.declare_queue(
            "ch5.orders",
            durable=True,
            arguments={"x-dead-letter-exchange": "ch5.dlx"},  # ② 就这一行,队列就有了"死后去处"
        )
        await orders.purge()

        for body in [
            "正常订单-A(通道畅通)",
            "正常订单-B(通道畅通)",
            "毒订单-X(内容非法,谁来谁失败)",
        ]:
            await channel.default_exchange.publish(
                aio_pika.Message(body.encode("utf-8")), routing_key=orders.name
            )

        print("实验一:三个订单进队,消费者处理前两个正常 ack,第三个处理失败")
        for _ in range(3):
            message = await orders.get()
            body = message.body.decode("utf-8")
            if "毒" in body:
                print(f"  处理失败: {body}")
                print("  nack(requeue=False) —— 不塞回原队列,让它去死信")
                await message.nack(requeue=False)  # ③ 处死:不回原队列,去死信
            else:
                print(f"  处理成功: {body}")
                await message.ack()

        await asyncio.sleep(0.5)  # 死信转投是 broker 内部的异步动作,缓一口气再去收容所看
        await show_dead(dead, "结果:毒订单没有消失,而是躺进了死信队列,连档案都带着")

        # ── 实验二:队列限长,挤掉的老消息进死信 ─────────────────────────────
        vip = await channel.declare_queue(
            "ch5.vip",
            durable=True,
            arguments={
                "x-max-length": 2,  # 队列最多攒 2 条,满了挤掉最老的
                "x-dead-letter-exchange": "ch5.dlx",
            },
        )
        await vip.purge()
        await dead.purge()

        for i in range(1, 5):
            await channel.default_exchange.publish(
                aio_pika.Message(f"VIP 消息-{i}".encode()), routing_key=vip.name
            )

        print("\n实验二:x-max-length=2 的队列,一口气塞进 4 条消息")
        await asyncio.sleep(0.3)
        remaining = await drain(vip)
        print(f"  队列里剩下(最老的两条被挤掉了): {remaining}")
        await show_dead(dead, "结果:被挤掉的 2 条老消息也进了死信队列")

        await orders.delete()
        await vip.delete()
        await dead.delete()
        await dlx.delete()


asyncio.run(main())
```

## 逐段讲

### ①② 死信交换机:死后的去处

死信交换机就是个普通交换机(这里用 fanout),死信队列也是个普通队列,没有任何特殊血统。魔法全在业务队列的 arguments 里(②):"这个队列里死掉的消息,转投到这个交换机"。

> **敲黑板:** 队列配 DLX 和消费端 `nack(requeue=False)` 是一对,两头都到位才有"处死+收容"的完整链路:只配 DLX、消费端只写 `nack()`(默认 requeue=True),消息原地打转永远到不了死信;只写 `nack(requeue=False)`、队列没配 DLX,消息直接蒸发。

转投时默认沿用消息原来的路由键。不想沿用,配 `x-dead-letter-routing-key` 改写它,第 8 讲实战用这招把"短信失败"和"付款超时"两种死信分流到不同队列,一台 DLX 各走各的出口。

### ③ nack(requeue=False) 与 reject:处死的两种姿势

哥俩都是"处死",区别就两点:nack 默认 `requeue=True`(塞回队列立刻重投——毒消息的死循环就是这么来的),reject 默认 `requeue=False`;nack 带 `multiple=True` 可以一口气处死一批,reject 一次一条。用哪个都把 requeue 显式写出来,别赌默认值,俩默认值还相反,记混了就是事故。

### ④ x-max-length 与 x-overflow

`x-max-length=2` 限制队列长度,新消息进来、满了,默认挤掉最老的(drop-head)。挤掉不是丢,是死,配上 DLX 就进了收容所(实验二会验证)。还有另一种挤法:`"x-overflow": "reject-publish"`,满了拒收新的、老的保住,生产端开着 publisher confirm 能收到"被拒"的回执。选哪种看业务要保新还是要保旧。

### ⑤ x-death 档案:死信队列好用的一半理由

消息转投进死信时,broker 在消息头里自动写了一份档案 `x-death`,真实长这样:

```
{'x-death': [{'count': 1, 'reason': 'rejected', 'queue': 'ch5.orders',
              'time': datetime(2026, 9, 16, 9, 53, 5, tzinfo=utc),
              'exchange': '', 'routing-keys': ['ch5.orders']}],
 'x-first-death-exchange': '', 'x-first-death-queue': 'ch5.orders',
 'x-first-death-reason': 'rejected'}
```

死了几回、死在哪个队列、死于什么原因、几点死的,全在里面。做"死信重放"时,`count` 字段是重要依据:重放后还死,档案里 count 变 2,超过阈值就该告警转人工了。另有 `x-first-death-*` 三个头,记的是第一次死亡的信息——死过多轮时,x-death 列表能还原整个流转史。

### 收容之后呢

死信队列的消费方式没有任何特殊,它就是普通队列。企业的常规玩法:

- 挂个**监控消费者**,死信一到就告警(钉钉/飞书机器人),把消息体和 x-death 档案原样推给值班群——第 8 讲的 watcher.py 就是它;
- 或者干脆不消费,让死信静静躺着,每天定时任务把死信导出来人工排查、修复后重新投回业务队列。

无论哪种,都是给机器处理不了的消息留一个人工出口。

一跑到底,两段实验连着看。对照第 2 讲:同样的毒订单,当时要么无限崩、要么无声消失,现在它带着档案躺进了 `ch5.dead`,实验一的真实输出:

```
结果:毒订单没有消失,而是躺进了死信队列,连档案都带着
  收到死信: 毒订单-X(内容非法,谁来谁失败)
    死亡档案: 原因=rejected  原队列=ch5.orders  死亡次数=1  时间=2026-09-16 09:53:05+00:00
```

实验二的输出也值得看一眼:队列剩 `[VIP 消息-3, VIP 消息-4]`,死信收容 `[VIP 消息-1, VIP 消息-2]`,死因 `maxlen`——新老谁走谁留,一目了然。

脚本里有一行 `await asyncio.sleep(0.5)`,注释写着"死信转投是 broker 内部的异步动作"。这不是可有可无的装饰:nack 的回执返回时,转投可能还没落账,紧接着去收容所取会扑空——演示脚本要给 broker 留半口气。

> **敲黑板:** 这个细节顺带暴露了 `queue.get()` 的另一面:它是"当场看一眼"的一次性动作,队列空就立刻返回 None,不会蹲守等新消息;要蹲守未来的消息,用第 1 讲的订阅。
