# 第 8 讲 · 综合实战:订单事件中心

前七讲把零件一个个单独演过,这一讲把它们装配成一台完整的机器:**事件驱动的订单后续处理系统**。形态和前面七讲不同——没有新知识点,而是给你一份需求,你自己写七个文件把它实现出来,最后开五个终端跑一场剧本、查一次库验收。这一讲考的不是"学新东西",是**组装**。

## 0 需求:你要做出个什么东西

### 0.1 业务背景与需求清单

"云上小店"是个极简电商。用户提交订单后事情并没有完,后面挂着一串后续动作,分属四个互相独立的服务——它们之间不调用、也不需要知道彼此存在。订单服务做完自己的事(下单、记录付款)只负责广播事件,谁关心谁订阅:

| # | 需求 | 谁来做 |
|---|---|---|
| N1 | 用户付款成功,发一条支付成功短信 | 短信服务 |
| N2 | 用户付款成功,按金额发放积分(199 元 = 199 分);消息可能重复投递,积分必须只发一次 | 积分服务 |
| N3 | 下单后 15 秒内没付款,自动取消订单、释放库存 | 超时服务 |
| N4 | 发短信可能失败:自动重试,初次之外最多再试 2 次;三次全败消息不能无声消失,要进死信池、触发告警转人工 | 短信服务 + 死信观察员 |
| N5 | 服务可能重启、消息可能重投,任何动作都不能重复执行(幂等) | 全体 |

15 秒是演示时长,真实电商这个窗口一般是 30 分钟——零件一模一样,改个数字而已。

这份需求表就是本讲的全部业务。事件驱动架构的卖点也藏在里面:将来要加"付款后推送数据分析"的新下游,新起一个服务绑上队列就行,订单服务一行不改。

### 0.2 演示剧本:三笔订单

为了在一场演示里看到所有分支,三笔订单写死在 `order_service.py` 里,分别覆盖三种结局:

| 订单 | 金额 | 剧本 | 覆盖路径 |
|---|---|---|---|
| A2001 | 199 | 5 秒后付款 | 正常:短信发出、积分到账;15 秒到点回查时已付款,不取消 |
| A2002 | 59 | 一直不付款 | 超时:15 秒后自动取消、释放库存 |
| A2003 | 299 | 8 秒后付款,但短信注定失败 | 异常:短信三连败进死信池告警;积分照常发放 |

## 1 架构:每条需求用前七讲的哪个零件

五条需求没有一条需要新零件,全在前七讲演过。先看映射,再看拼出来的拓扑:

| 需求 | 方案 | 出处 |
|---|---|---|
| N1+N2 一次付款,短信和积分都要收到 | topic 交换机 `shop.events` 广播 `order.paid`,两个队列各绑各的 | 第 3 讲 |
| N4 失败自动重试 | ack 旧消息 + 带 retry 计数的新消息重发 | 第 2 讲 |
| N4 重试耗尽不丢消息 | 队列挂 DLX,nack(requeue=False) 进死信池,观察员告警 | 第 5 讲 |
| N3 15 秒未付款自动取消 | TTL 等待队列躺 15 秒,到期死信改写路由键进超时队列,回查订单再取消 | 第 6 讲 |
| N2+N5 动作不重复执行 | 幂等:积分条件 UPDATE、短信内存挡板 | 第 2 讲 |
| 底线:服务崩了、broker 重启,消息不丢 | durable 队列 + PERSISTENT 消息 + 手动 ack + connect_robust | 第 4 讲 |

整体架构:

```
                                 ┌────────── shop.events(topic) ──────────┐
  order_service ── order.paid ──►│──┬──► shop.sms.queue ──► sms_service     │
  (下单/付款,广播事件)           │  │      (失败重试×2,再败死信)           │
                                 │  └──► shop.points.queue ──► points_service│
                                 └────────────────────────────────────────┘

  order_service ── 延迟炸弹 ──► shop.pay.wait(TTL 15 秒)
                                     │ 到期 expired 死信,路由键改写为 timeout
                                     ▼
                     shop.dlx(direct)──┬── timeout ──► shop.timeout.queue ──► timeout_service
                                       └── dead ─────► shop.dead.queue ────► watcher
```

拓扑配置(七个对象,§3 的 `declare_topology` 就照这张表写):

| 对象 | 类型 | 关键参数 | 出处 |
|---|---|---|---|
| `shop.events` | topic 交换机 | durable | 第 3 讲 |
| `shop.dlx` | direct 交换机 | durable,两个出口 dead / timeout | 第 5 讲 |
| `shop.sms.queue` | 队列 | 绑 `order.paid`;DLX=shop.dlx,routing-key=dead | 第 5 讲 |
| `shop.points.queue` | 队列 | 绑 `order.paid` | 第 3 讲 |
| `shop.pay.wait` | 队列 | `x-message-ttl=15000`;DLX=shop.dlx,routing-key=timeout;不绑交换机 | 第 6 讲 |
| `shop.timeout.queue` | 队列 | 绑 dlx / `timeout` | 第 6 讲 |
| `shop.dead.queue` | 队列 | 绑 dlx / `dead` | 第 5 讲 |

两个设计决策提前说透,写代码时才不迷糊:

**① 同一个 DLX,两个出口。** 短信三连败和付款超时都会变死信,但归宿不同:前者出事了要人看,后者是正常业务流。办法是两个队列的 `x-dead-letter-routing-key` 分别写 `dead` 和 `timeout`,死信交换机用 direct 按改写后的路由键分流——这就是 DLX 选 direct 不选 fanout 的原因。

**② 两处"直投",走默认交换机。** `shop.pay.wait` 不绑任何交换机,延迟消息由订单服务直接点名投进去;短信重试的新消息也直投回本队列。这用到**默认交换机**——不是本讲新发明,前几讲一直在用,这里一次说清:

> **默认交换机**:AMQP 内置的无名交换机,名字是空字符串 `""`,不用声明、也删不掉。特殊规则:**每个队列都自动绑定到它,绑定键 = 队列名**,所以 `default_exchange.publish(msg, routing_key=队列名)` 的语义就是"不走路由,点名塞进这条队列"。
>
> 企业里它一点不小众:Java 的 Spring AMQP,`rabbitTemplate.convertAndSend("队列名", msg)` 底层走的就是默认交换机,大量存量系统天天在用。真正的分工惯例是:**业务事件的流转走命名交换机**(链路在管理台看得见、好做权限和审计);"点对点直投某条队列"的内部操作——延迟消息入等待队列、重试消息回本队列、RPC 回执——走默认交换机,是最省事的正统写法。本讲的两处直投都属于后者。

## 3 common.py —— 全套拓扑的幂等声明

常量区放七个名字,`declare_topology(channel)` 把两个交换机、五个队列、四条绑定声明齐,返回 `{名字: 对象}` 供调用方取用。

**要点**:声明是幂等的,五六个进程同时启动、同时建同一套拓扑不会冲突,**没有启动顺序依赖**——谁先启动谁建,后到的发现已存在且参数一致就跳过(参数不一致才报 406,第 4 讲见过的事故现场)。真实项目里对应一个集中定义的 `topology.py`。

sms 和 pay_wait 两个队列的 arguments 各带一套死信配置,照 §1 的表逐项核对,写错一处就是 406。

```python
"""第 8 讲公共零件:连接地址 + 全套拓扑的幂等声明。

每个服务脚本启动时都调一遍 declare_topology,谁先启动谁建。
"""

import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]

EXCHANGE = "shop.events"  # 业务事件交换机(topic)
DLX = "shop.dlx"  # 死信交换机(direct),两个出口:dead / timeout
SMS_QUEUE = "shop.sms.queue"  # 短信队列,绑 order.paid;失败死信走 dead
POINTS_QUEUE = "shop.points.queue"  # 积分队列,绑 order.paid
PAY_WAIT = "shop.pay.wait"  # 付款等待队列:15 秒 TTL,到期死信走 timeout
DEAD_QUEUE = "shop.dead.queue"  # 死信池,人工排查入口
TIMEOUT_QUEUE = "shop.timeout.queue"  # 超时处理队列


async def declare_topology(channel: aio_pika.Channel) -> dict[str, object]:
    """声明本讲全部交换机、队列和绑定,返回各对象供调用方使用"""
    events = await channel.declare_exchange(EXCHANGE, aio_pika.ExchangeType.TOPIC, durable=True)
    dlx = await channel.declare_exchange(DLX, aio_pika.ExchangeType.DIRECT, durable=True)

    sms = await channel.declare_queue(
        SMS_QUEUE,
        durable=True,
        # 重试耗尽的死信走 dead 出口
        arguments={"x-dead-letter-exchange": DLX, "x-dead-letter-routing-key": "dead"},
    )
    await sms.bind(events, routing_key="order.paid")

    points = await channel.declare_queue(POINTS_QUEUE, durable=True)
    await points.bind(events, routing_key="order.paid")

    pay_wait = await channel.declare_queue(
        PAY_WAIT,
        durable=True,
        arguments={
            "x-message-ttl": 15_000,  # 躺 15 秒
            "x-dead-letter-exchange": DLX,
            "x-dead-letter-routing-key": "timeout",  # 到期死信走 timeout 出口
        },
    )

    timeout_queue = await channel.declare_queue(TIMEOUT_QUEUE, durable=True)
    await timeout_queue.bind(dlx, routing_key="timeout")
    dead_queue = await channel.declare_queue(DEAD_QUEUE, durable=True)
    await dead_queue.bind(dlx, routing_key="dead")

    return {
        "events": events,
        "dlx": dlx,
        "sms": sms,
        "points": points,
        "pay_wait": pay_wait,
        "timeout": timeout_queue,
        "dead": dead_queue,
    }
```

## 4 db.py —— 订单表:业务数据兼幂等标记

orders 一张表,既是业务数据,也是幂等标记:

```
order_id        主键
amount          金额
status          待付款 / 已付款 / 已取消
cancel_reason   取消原因,可空
points_granted  积分已发标记,默认 False
sms_will_fail   演示剧本开关,默认 False
```

DATABASE_URL 从 .env 读,`create_async_engine` 配 `async_sessionmaker(expire_on_commit=False)`。六个函数:init_db / get / create / mark_paid / grant_points / cancel,全是 async。

**要点**:`points_granted` 是积分服务的幂等标记(N2),`sms_will_fail` 是演示剧本开关(A2003 靠它注定失败)。`grant_points` 用一条**条件 UPDATE** 把"检查 + 标记"合并成原子操作——伪代码版"读出来、判断、写回去"三步,两个积分进程并发时会双双通过判断、重复发分;一条 SQL 把这个缝堵死,这才是换真库的实质收益,不只是"能存盘"。

```python
"""第 8 讲订单表:SQLAlchemy 2.0 异步建模,表在 Postgres 的 ai-lab 库里。

每个函数就是一条 SQL 的事;真实项目把建表换成 alembic 迁移、engine 配连接池。
"""

import os
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, update
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]  # postgresql+asyncpg://...,已配在 .env


class Base(DeclarativeBase):
    pass


class Order(Base):
    __tablename__ = "orders"

    order_id: Mapped[str] = mapped_column(String(20), primary_key=True)
    amount: Mapped[int]
    status: Mapped[str] = mapped_column(default="待付款")
    cancel_reason: Mapped[str | None]
    points_granted: Mapped[bool] = mapped_column(default=False)  # 积分服务的幂等标记
    sms_will_fail: Mapped[bool] = mapped_column(default=False)  # 演示剧本开关


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def init_db() -> None:
    """建表。create_all 幂等 —— 和 declare_topology 一个脾气,谁先启动谁建"""
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)


async def get(order_id: str) -> Order | None:
    async with Session() as session:
        return await session.get(Order, order_id)


async def create(order_id: str, amount: int, sms_will_fail: bool = False) -> None:
    async with Session() as session:
        session.add(Order(order_id=order_id, amount=amount, sms_will_fail=sms_will_fail))
        await session.commit()


async def mark_paid(order_id: str) -> None:
    async with Session() as session:
        await session.execute(
            update(Order).where(Order.order_id == order_id).values(status="已付款")
        )
        await session.commit()


async def grant_points(order_id: str) -> bool:
    """发放积分。已发过返回 False —— 条件 UPDATE 原子生效,幂等不靠运气"""
    async with Session() as session:
        result = await session.execute(
            update(Order)
            .where(Order.order_id == order_id, Order.points_granted.is_(False))
            .values(points_granted=True)
        )
        await session.commit()
        return result.rowcount == 1


async def cancel(order_id: str, reason: str) -> None:
    async with Session() as session:
        await session.execute(
            update(Order)
            .where(Order.order_id == order_id)
            .values(status="已取消", cancel_reason=reason)
        )
        await session.commit()
```

两个细节:`get` 返回的 `Order` 对象带着已加载的字段离开 session,消费脚本里照样读 `order.amount`,不用额外查库;所有 db 函数都是 `async`,调用处记得 `await`。

## 5 order_service.py —— 生产者:下单、埋延迟炸弹、模拟付款

```
启动:connect_robust → declare_topology → db.init_db
每笔订单:db.create → 广播 order.created → 直投 PAY_WAIT(payment.deadline)
t+5s  付 A2001:db.mark_paid → 广播 order.paid
t+8s  付 A2003:db.mark_paid → 广播 order.paid
```

三个动作,各有讲究:

| 动作 | 目标 | 要点 |
|---|---|---|
| 广播 `order.created` | shop.events | 眼下没有队列绑它,消息发出即丢弃。留的扩展口:将来数据分析自己绑队列即可,上游一行不改 |
| 埋延迟炸弹 | 直投 shop.pay.wait | 第 6 讲的延迟套路,N3 的 15 秒计时器从此开始走 |
| 模拟付款 | 先改库,**再**广播 `order.paid` | 顺序反了,下游收到事件去查库还是"待付款" |

剧本 `ORDERS` 写死三笔订单(§0.2 的表);`event_message` 统一打包 json + PERSISTENT;`pay()` 就是"先改库、再广播"的落地。

```python
"""第 8 讲·订单服务(生产者):下单、模拟付款,把事件发进 shop.events。

uv run python "rabbitmq教程/08-综合实战-订单事件中心/order_service.py"
"""

import asyncio
import json
from datetime import datetime
from pathlib import Path

import aio_pika
import db
from common import PAY_WAIT, RABBITMQ_URL, declare_topology
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")

# (订单号, 金额, 短信会不会失败, 用户会不会付款)
ORDERS = [
    ("A2001", 199, False, True),
    ("A2002", 59, False, False),
    ("A2003", 299, True, True),
]


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


def event_message(payload: dict, **kwargs) -> aio_pika.Message:
    """业务事件统一打包:json 内容 + 持久化"""
    return aio_pika.Message(
        json.dumps(payload, ensure_ascii=False).encode(),
        delivery_mode=aio_pika.DeliveryMode.PERSISTENT,
        **kwargs,
    )


async def pay(channel: aio_pika.Channel, events: aio_pika.Exchange, order_id: str) -> None:
    """付款:先改库,再广播事件,顺序别反"""
    await db.mark_paid(order_id)
    await events.publish(
        event_message({"order_id": order_id, "event": "order.paid"}), routing_key="order.paid"
    )
    print(f"{now()} 用户付款:{order_id} → 广播 order.paid")


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        topo = await declare_topology(channel)
        events: aio_pika.Exchange = topo["events"]  # type: ignore[assignment]
        await db.init_db()  # 建表也幂等,谁先启动谁建,和拓扑声明一个脾气

        for order_id, amount, sms_will_fail, _will_pay in ORDERS:
            await db.create(order_id, amount, sms_will_fail)
            # 事件一:order.created(暂无订阅方)
            await events.publish(
                event_message({"order_id": order_id, "event": "order.created"}),
                routing_key="order.created",
            )
            # 事件二:延迟炸弹,直投付款等待队列
            await channel.default_exchange.publish(
                event_message({"order_id": order_id, "event": "payment.deadline"}),
                routing_key=PAY_WAIT,
            )
            print(f"{now()} 下单:{order_id},{amount} 元,15 秒付款窗口开始")

        print(f"{now()} 模拟付款:5 秒后 A2001,8 秒后 A2003")
        await asyncio.sleep(5)
        await pay(channel, events, "A2001")
        await asyncio.sleep(3)
        await pay(channel, events, "A2003")

    print(f"{now()} 订单服务退出,消费者继续在各自终端运行")


asyncio.run(main())
```

## 6 sms_service.py —— 失败处理三板斧

消费逻辑一棵分支树:

```
收到 order.paid
 ├─ 订单号已在 sent 里           → 已发过,跳过,ack
 ├─ sms_will_fail 且 retry < 2  → 原 body 重发一条,headers={"retry": retry+1},直投本队列,ack 旧的
 ├─ retry >= 2                  → nack(requeue=False),进死信
 └─ 其余                         → 打印短信,记入 sent,ack
```

retry 从消息头取,headers 可能是 None,先判空。`sent` 是模块级的 set,进程内存版幂等,重启清零——要的就是这个弱版本,和积分服务的持久版对照看(N5 的两档答案)。

| 手段 | 实现 | 说明 |
|---|---|---|
| 幂等挡板 | 内存集合 `sent` | **最弱的幂等**,进程重启即失效;生产换 Redis SET 或数据库唯一键 |
| 重试 | ack 旧消息,带 `retry` 计数的新消息直投本队列 | 消息进队列后**无法修改**,想带计数只能"发新的、确认旧的" |
| 放弃 | `nack(requeue=False)` | 队列的 DLX 接手,进死信池,watcher 告警 |

重试为什么直投 `SMS_QUEUE` 而不是发布到 `shop.events`?重试是短信服务自己的私事,广播出去积分服务会再加一次积分——§1 说"直投走默认交换机"就是为这类场景准备的。

```python
"""第 8 讲·短信服务(消费者):听 order.paid,发支付成功短信。

失败重试两次,第三次仍失败 → nack(requeue=False) → 死信池
幂等:内存集合(最弱版本,和积分服务的持久版对照看)

  uv run python "rabbitmq教程/08-综合实战-订单事件中心/sms_service.py"
"""

import asyncio
import json
from datetime import datetime

import aio_pika
import db
from common import RABBITMQ_URL, SMS_QUEUE, declare_topology

sent: set[str] = set()  # 本进程已发过短信的订单,重启清零


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=1)
        topo = await declare_topology(channel)
        sms: aio_pika.Queue = topo["sms"]  # type: ignore[assignment]

        print(f"{now()} 短信服务已启动")
        async for message in sms.iterator():
            event = json.loads(message.body)
            order_id = event["order_id"]
            order = await db.get(order_id)
            retry = message.headers.get("retry", 0) if message.headers else 0

            if order_id in sent:  # 幂等挡板
                print(f"{now()} 短信:{order_id} 已发过,跳过")
                await message.ack()
                continue

            if order and order.sms_will_fail:
                if retry < 2:  # 重试
                    print(f"{now()} 短信:{order_id} 失败(第 {retry + 1} 次),带计数重发")
                    await channel.default_exchange.publish(
                        aio_pika.Message(
                            message.body,
                            headers={"retry": retry + 1},
                            delivery_mode=aio_pika.DeliveryMode.PERSISTENT,
                        ),
                        routing_key=SMS_QUEUE,  # 直投本队列,不广播
                    )
                    await message.ack()  # 旧消息以"重发"的方式处理完毕
                else:  # 放弃
                    print(f"{now()} 短信:{order_id} 三次全败 → nack(requeue=False) → 死信")
                    await message.nack(requeue=False)
                continue

            amount = order.amount if order else "?"
            print(f"{now()} 短信:【云上小店】订单 {order_id} 已支付 {amount} 元")
            sent.add(order_id)
            await message.ack()


asyncio.run(main())
```

延伸:想改成"隔 5 秒再试",把直投目标换成一条 `x-message-ttl=5000`、死信指回 `SMS_QUEUE` 的中转队列即可(第 6 讲的分档延迟)。配上 15s / 60s 两档就是常见的阶梯重试。

## 7 points_service.py —— 持久化幂等

**铁律:先落库,后 ack**。反过来的话,落库失败但消息已确认,这条消息凭空蒸发。

逻辑就一句:`await db.grant_points(order_id)` 返回 True 打印发放,返回 False 打印"已发过,跳过"。消费者骨架和短信服务同款。

```python
"""第 8 讲·积分服务(消费者):听 order.paid,按金额发放积分。

幂等标记写在订单表里:进程随便重启、消息随便重投,积分只发一次。

    uv run python "rabbitmq教程/08-综合实战-订单事件中心/points_service.py"
"""

import asyncio
import json
from datetime import datetime

import aio_pika
import db
from common import RABBITMQ_URL, declare_topology


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=1)
        topo = await declare_topology(channel)
        points: aio_pika.Queue = topo["points"]  # type: ignore[assignment]

        print(f"{now()} 积分服务已启动")
        async for message in points.iterator():
            event = json.loads(message.body)
            order_id = event["order_id"]
            order = await db.get(order_id)

            if await db.grant_points(order_id):  # 先落库
                print(f"{now()} 积分:{order_id} 发放 {order.amount} 分")
            else:
                print(f"{now()} 积分:{order_id} 已发过,跳过(表里标记拦下,重启也拦得住)")
            await message.ack()  # 后 ack


asyncio.run(main())
```

两种幂等对比(N5 的两档答案):

| | sms_service | points_service |
|---|---|---|
| 存储 | 进程内存 `set` | 订单表字段 |
| 进程重启后 | 失效,会重复发短信 | 仍然有效 |
| 生产可用 | 否 | 是(真实项目用 Redis SET / 数据库唯一键) |

## 8 timeout_service.py —— 延迟到点回查

第 6 讲的规矩落地:到点只代表"该看一眼",N3 落成三个分支:

```
死信到点(timeout 队列)
 ├─ 已付款 → 不处理(A2001、A2003 走这里)
 ├─ 已取消 → 跳过(幂等)
 └─ 其余   → db.cancel(order_id, "超时未付款"),释放库存

无论哪个分支,最后都 ack
```

```python
"""第 8 讲·超时服务(消费者):听 15 秒延迟到期的死信,回查订单再决定取消。

uv run python "rabbitmq教程/08-综合实战-订单事件中心/timeout_service.py"
"""

import asyncio
import json
from datetime import datetime

import aio_pika
import db
from common import RABBITMQ_URL, declare_topology


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=1)
        topo = await declare_topology(channel)
        timeout_queue: aio_pika.Queue = topo["timeout"]  # type: ignore[assignment]

        print(f"{now()} 超时服务已启动")
        async for message in timeout_queue.iterator():
            event = json.loads(message.body)
            order_id = event["order_id"]
            order = await db.get(order_id)
            status = order.status if order else "不存在"

            if status == "已付款":
                print(f"{now()} 超时:{order_id} 到点但已付款,不处理")
            elif status == "已取消":
                print(f"{now()} 超时:{order_id} 已取消过,跳过(幂等)")
            else:
                await db.cancel(order_id, "超时未付款")
                print(f"{now()} 超时:{order_id} 15 秒未付款 → 取消,释放库存")
            await message.ack()


asyncio.run(main())
```

## 9 watcher.py —— 死信告警

第 5 讲"收容之后呢"的答案,N4 的最后一环。守 dead 队列,消息一到打印消息体和 x-death 档案。生产里 `print` 换成钉钉 / 飞书机器人。

档案的字段值可能是 bytes,isinstance 判断过再 decode,和第 5 讲的 decode 小工具一个用法。

```python
"""第 8 讲·死信观察员:守着死信池,消息一到就告警。

uv run python "rabbitmq教程/08-综合实战-订单事件中心/watcher.py"
"""

import asyncio
from datetime import datetime

import aio_pika
from common import RABBITMQ_URL, declare_topology


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        topo = await declare_topology(channel)
        dead: aio_pika.Queue = topo["dead"]  # type: ignore[assignment]

        print(f"{now()} 死信观察员已启动")
        async for message in dead.iterator():
            print(f"{now()} 死信到达,推送告警:")
            print(f"    消息体: {message.body.decode('utf-8')}")
            for death in message.headers.get("x-death", []):
                reason = death.get("reason")
                reason = reason.decode() if isinstance(reason, bytes) else reason
                origin = death.get("queue")
                origin = origin.decode() if isinstance(origin, bytes) else origin
                print(f"    档案: 死于 {reason},原队列 {origin}")
            await message.ack()


asyncio.run(main())
```
