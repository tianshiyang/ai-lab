# 第 8 讲 · 综合实战:订单事件中心

前七讲的知识点,这一讲全部串起来,拼一个企业里最典型的 MQ 落地场景。先看全图:

```
                                     ┌─────────────── shop.events(topic) ───────────────┐
                                     │                                                   │
  order_service.py ── order.paid ──► │ ──┬──► shop.sms.queue ──► sms_service.py          │
  (下单/付款,广播事件)                │    │        (失败重试×2,再败死信)                    │
                                     │    └──► shop.points.queue ──► points_service.py   │
                                     │              (持久化幂等加积分)                     │
                                     └───────────────────────────────────────────────────┘
  order_service.py ── 延迟炸弹 ──► shop.pay.wait(TTL 15秒)
                                        │ 到期死信(x-dead-letter-routing-key=timeout)
                                        ▼
                              shop.dlx(direct)──timeout──► shop.timeout.queue ──► timeout_service.py
                                        │                        (回查订单,没付才取消)
                                        └───dead──────────► shop.dead.queue ──► watcher.py
                                                                 (死信告警,转人工)
```

三笔订单的剧本(写死在 `order_service.py` 里,不用你准备任何数据):

| 订单 | 剧本 | 应该看到的结局 |
|---|---|---|
| A2001 | 5 秒后付款 | 短信发出、积分到账、15 秒到期时"虚惊一场" |
| A2002 | 死活不付款 | 15 秒后被超时服务自动取消、释放库存 |
| A2003 | 8 秒后付款,但这单短信注定失败 | 短信重试三次全败 → 死信 → 观察员告警 |

用到的每一招都有出处:topic 路由(第 3 讲)、持久化+确认(第 4 讲)、手动 ack 与重试(第 2 讲)、死信(第 5 讲)、TTL 延迟与到点回查(第 6 讲)、断线重连(第 4 讲补充)。

> **怎么练这一讲:** 代码量大,不必全敲。优先手敲三个核心——`common.py`(拓扑)、`order_service.py`(生产者)、`sms_service.py`(失败处理最精彩);`points / timeout / watcher` 结构与前几讲的消费者大同小异,读懂思路、想跑再敲;`db.py` 短,顺手敲了。仓库里唯一保留的现成脚本是 `reset.py`(清场工具,不贴讲义),它 import 了 `common.py` 和 `db.py`,所以得等你把这两个敲出来它才能跑。

## 完整代码

`common.py`(全文),全套拓扑:

```python
"""第 8 讲公共零件:连接地址 + 全套拓扑的幂等声明。

每个服务脚本启动时都调一遍 declare_topology——声明是幂等的,
谁先启动谁建,后启动的拿到引用,不存在启动顺序要求。
"""

import os
from pathlib import Path

import aio_pika
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")
RABBITMQ_URL = os.environ["RABBITMQ_URL"]

EXCHANGE = "shop.events"  # 业务事件交换机(topic)
DLX = "shop.dlx"  # 死信交换机(direct),两个出口:dead / timeout
SMS_QUEUE = "shop.sms.queue"  # 短信服务队列,绑 order.paid;失败死信走 dead 出口
POINTS_QUEUE = "shop.points.queue"  # 积分服务队列,绑 order.paid
PAY_WAIT = "shop.pay.wait"  # 付款等待队列:15 秒 TTL,到期死信走 timeout 出口
DEAD_QUEUE = "shop.dead.queue"  # 死信池,人工排查入口
TIMEOUT_QUEUE = "shop.timeout.queue"  # 超时处理队列


async def declare_topology(channel: aio_pika.Channel) -> dict[str, object]:
    """声明本讲全部交换机、队列和绑定,返回各对象的字典供调用方直接用"""
    events = await channel.declare_exchange(EXCHANGE, aio_pika.ExchangeType.TOPIC, durable=True)
    dlx = await channel.declare_exchange(DLX, aio_pika.ExchangeType.DIRECT, durable=True)

    sms = await channel.declare_queue(
        SMS_QUEUE,
        durable=True,
        # ① 短信队列的"死后去处":重试耗尽的死信,改走路由键 dead
        arguments={"x-dead-letter-exchange": DLX, "x-dead-letter-routing-key": "dead"},
    )
    await sms.bind(events, routing_key="order.paid")

    points = await channel.declare_queue(POINTS_QUEUE, durable=True)
    await points.bind(events, routing_key="order.paid")

    pay_wait = await channel.declare_queue(
        PAY_WAIT,
        durable=True,
        arguments={
            "x-message-ttl": 15_000,  # ② 付款等待队列:躺 15 秒
            "x-dead-letter-exchange": DLX,
            "x-dead-letter-routing-key": "timeout",  # 到期死信改走 timeout 出口
        },
    )

    timeout_queue = await channel.declare_queue(TIMEOUT_QUEUE, durable=True)
    await timeout_queue.bind(dlx, routing_key="timeout")
    dead_queue = await channel.declare_queue(DEAD_QUEUE, durable=True)
    await dead_queue.bind(dlx, routing_key="dead")

    return {
        "events": events,
        "dlx": dlx,
        "sms": sms,
        "points": points,
        "pay_wait": pay_wait,
        "timeout": timeout_queue,
        "dead": dead_queue,
    }
```

`db.py`(全文),假装是 MySQL 的订单表:

```python
"""极简订单表:一个 json 文件假装是数据库。

真实项目里这就是 MySQL 的 orders 表,下面每个函数换成一条 SQL。
这里追求把注意力留给 MQ,所以没有锁、没有事务,只供本讲演示。
"""

import json
from pathlib import Path

DB_FILE = Path(__file__).parent / "orders.json"


def load() -> dict:
    if not DB_FILE.exists():
        return {}
    return json.loads(DB_FILE.read_text(encoding="utf-8"))


def save(orders: dict) -> None:
    DB_FILE.write_text(json.dumps(orders, ensure_ascii=False, indent=2), encoding="utf-8")


def get(order_id: str) -> dict | None:
    return load().get(order_id)


def create(order_id: str, amount: int, sms_will_fail: bool = False) -> None:
    orders = load()
    orders[order_id] = {
        "order_id": order_id,
        "amount": amount,
        "status": "待付款",
        "points_granted": False,  # 积分服务的幂等标记
        "sms_will_fail": sms_will_fail,  # 短信服务的"剧本":这笔单的短信注定失败
    }
    save(orders)


def mark_paid(order_id: str) -> None:
    orders = load()
    orders[order_id]["status"] = "已付款"
    save(orders)


def grant_points(order_id: str) -> bool:
    """发放积分。已发过返回 False——积分服务靠它做幂等"""
    orders = load()
    if order_id not in orders or orders[order_id]["points_granted"]:
        return False
    orders[order_id]["points_granted"] = True
    save(orders)
    return True


def cancel(order_id: str, reason: str) -> None:
    orders = load()
    orders[order_id]["status"] = "已取消"
    orders[order_id]["cancel_reason"] = reason
    save(orders)
```

`order_service.py`(全文),生产者:

```python
"""第 8 讲·订单服务(生产者):下单、模拟付款,把事件发进 shop.events。

三笔订单的剧本全写死在 ORDERS 里:
  A2001 正常单 —— 5 秒后付款,一切顺利
  A2002 拖延单 —— 死活不付款,15 秒后被超时服务自动取消
  A2003 倒霉单 —— 8 秒后付款,但这单的短信注定失败,短信服务重试三次后扔进死信池

    uv run python "rabbitmq教程/08-综合实战-订单事件中心/order_service.py"
"""

import asyncio
import json
from datetime import datetime
from pathlib import Path

import aio_pika
import db
from common import PAY_WAIT, RABBITMQ_URL, declare_topology
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")

# (订单号, 金额, 短信会不会失败, 用户会不会付款)
ORDERS = [
    ("A2001", 199, False, True),
    ("A2002", 59, False, False),
    ("A2003", 299, True, True),
]


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


def event_message(payload: dict, **kwargs) -> aio_pika.Message:
    """业务事件统一打包:json 内容 + 持久化"""
    return aio_pika.Message(
        json.dumps(payload, ensure_ascii=False).encode(),
        delivery_mode=aio_pika.DeliveryMode.PERSISTENT,
        **kwargs,
    )


async def pay(channel: aio_pika.Channel, events: aio_pika.Exchange, order_id: str) -> None:
    """用户付款:③ 先改库,再广播 order.paid 事件——顺序别反"""
    db.mark_paid(order_id)
    await events.publish(
        event_message({"order_id": order_id, "event": "order.paid"}), routing_key="order.paid"
    )
    print(f"{now()} 用户付款了:{order_id} → 广播 order.paid,订阅方各自行动")


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        topo = await declare_topology(channel)
        events: aio_pika.Exchange = topo["events"]  # type: ignore[assignment]

        for order_id, amount, sms_will_fail, _will_pay in ORDERS:
            db.create(order_id, amount, sms_will_fail)
            # ① 事件一:order.created 广播出去(眼下没人订阅,但以后加订阅方零成本)
            await events.publish(
                event_message({"order_id": order_id, "event": "order.created"}),
                routing_key="order.created",
            )
            # ② 事件二:延迟炸弹直投付款等待队列,15 秒后到期死信(第 6 讲的延迟套路)
            await channel.default_exchange.publish(
                event_message({"order_id": order_id, "event": "payment.deadline"}),
                routing_key=PAY_WAIT,
            )
            print(f"{now()} 下单成功:{order_id},金额 {amount} 元,15 秒付款窗口开始倒计时")

        print(f"{now()} 订单服务收工前,再模拟两笔付款(5 秒后 A2001,8 秒后 A2003)……")
        await asyncio.sleep(5)
        await pay(channel, events, "A2001")
        await asyncio.sleep(3)
        await pay(channel, events, "A2003")

    print(f"{now()} 订单服务进程退出。三个消费者还在各自终端里跑着,好戏在它们那边")


asyncio.run(main())
```

`sms_service.py`(全文),本讲戏最多的消费者:

```python
"""第 8 讲·短信服务(消费者):听 order.paid,给用户发支付成功短信。

两个看点:
  1. 失败重试:发不出去就带着 retry 计数重发到自己队列,三次全败 → nack 进死信;
  2. 幂等:用内存集合记"发过的订单"。注意这是最弱的幂等——进程一重启就忘,
     生产要换成 Redis/数据库的唯一键(积分服务演示的就是持久版)。

    uv run python "rabbitmq教程/08-综合实战-订单事件中心/sms_service.py"
"""

import asyncio
import json
from datetime import datetime

import aio_pika
import db
from common import RABBITMQ_URL, SMS_QUEUE, declare_topology

sent: set[str] = set()  # 本进程已发过短信的订单(内存幂等,重启清零)


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=1)
        topo = await declare_topology(channel)
        sms: aio_pika.Queue = topo["sms"]  # type: ignore[assignment]

        print(f"{now()} 短信服务已启动,等 order.paid 事件……")
        async for message in sms.iterator():
            event = json.loads(message.body)
            order_id = event["order_id"]
            order = db.get(order_id)
            retry = message.headers.get("retry", 0) if message.headers else 0

            if order_id in sent:
                print(f"{now()} 短信:{order_id} 已发过,跳过(① 内存幂等集拦下)")
                await message.ack()
                continue

            if order and order["sms_will_fail"]:
                if retry < 2:
                    print(f"{now()} 短信:{order_id} 发送失败(第 {retry + 1} 次尝试),带上计数重发")
                    await channel.default_exchange.publish(
                        aio_pika.Message(
                            message.body,
                            headers={"retry": retry + 1},
                            delivery_mode=aio_pika.DeliveryMode.PERSISTENT,
                        ),
                        routing_key=SMS_QUEUE,  # ② 直投本队列重试,不广播给别人
                    )
                    await message.ack()  # 原消息处理完毕(以重发的方式)
                else:
                    print(
                        f"{now()} 短信:{order_id} 三次尝试全失败 → nack(requeue=False),进死信转人工"
                    )
                    await message.nack(requeue=False)  # ③ 三次全败,处死 → 队列的 DLX 接手
                continue

            amount = order["amount"] if order else "?"
            print(f"{now()} 短信:【云上小店】您的订单 {order_id} 已支付 {amount} 元")
            sent.add(order_id)
            await message.ack()


asyncio.run(main())
```

`points_service.py`(全文):

```python
"""第 8 讲·积分服务(消费者):听 order.paid,按金额发放积分。

看点是持久化幂等:发没发过记在订单表里(points_granted 字段),
进程随便重启、消息随便重投,积分只会发一次。和短信服务的内存集对比着看。

    uv run python "rabbitmq教程/08-综合实战-订单事件中心/points_service.py"
"""

import asyncio
import json
from datetime import datetime

import aio_pika
import db
from common import RABBITMQ_URL, declare_topology


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=1)
        topo = await declare_topology(channel)
        points: aio_pika.Queue = topo["points"]  # type: ignore[assignment]

        print(f"{now()} 积分服务已启动,等 order.paid 事件……")
        async for message in points.iterator():
            event = json.loads(message.body)
            order_id = event["order_id"]
            order = db.get(order_id)

            if db.grant_points(order_id):  # ① 先落库、后 ack;发过返回 False
                print(f"{now()} 积分:{order_id} 发放 {order['amount']} 分(已记入订单表)")
            else:
                print(f"{now()} 积分:{order_id} 已发过,跳过(表里的标记拦下,重启也拦得住)")
            await message.ack()


asyncio.run(main())
```

`timeout_service.py`(全文):

```python
"""第 8 讲·超时服务(消费者):听 15 秒延迟到期的死信,回查订单再决定取消。

第 6 讲讲过的铁律:消息到点只代表"该看一眼了",不能直接信消息里的旧状态。
付款在等待期内随时可能发生,所以先查库:付了就放行,没付才取消。

    uv run python "rabbitmq教程/08-综合实战-订单事件中心/timeout_service.py"
"""

import asyncio
import json
from datetime import datetime

import aio_pika
import db
from common import RABBITMQ_URL, declare_topology


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        await channel.set_qos(prefetch_count=1)
        topo = await declare_topology(channel)
        timeout_queue: aio_pika.Queue = topo["timeout"]  # type: ignore[assignment]

        print(f"{now()} 超时服务已启动,等付款期限到点的死信……")
        async for message in timeout_queue.iterator():
            event = json.loads(message.body)
            order_id = event["order_id"]
            order = db.get(order_id)
            status = order["status"] if order else "不存在"

            if status == "已付款":  # ① 回查三分支:付了/早取消了/真没付
                print(f"{now()} 超时:{order_id} 到点了,但用户其实付过款——虚惊一场,什么都不做")
            elif status == "已取消":
                print(f"{now()} 超时:{order_id} 已经取消过了,跳过(幂等)")
            else:
                db.cancel(order_id, "超时未付款")
                print(f"{now()} 超时:{order_id} 15 秒未付款 → 自动取消,释放库存")
            await message.ack()


asyncio.run(main())
```

`watcher.py`(全文):

```python
"""第 8 讲·死信观察员:守着死信池,消息一到就打印出来(生产里这里接的是告警机器人)。

uv run python "rabbitmq教程/08-综合实战-订单事件中心/watcher.py"
"""

import asyncio
from datetime import datetime

import aio_pika
from common import RABBITMQ_URL, declare_topology


def now() -> str:
    return f"[{datetime.now():%H:%M:%S}]"


async def main() -> None:
    connection = await aio_pika.connect_robust(RABBITMQ_URL)
    async with connection:
        channel = await connection.channel()
        topo = await declare_topology(channel)
        dead: aio_pika.Queue = topo["dead"]  # type: ignore[assignment]

        print(f"{now()} 死信观察员已启动,机器处理不了的消息都会到我这儿……")
        async for message in dead.iterator():
            print(f"{now()} 死信到达,推送告警给值班群,消息如下:")
            print(f"    消息体: {message.body.decode('utf-8')}")
            for death in message.headers.get("x-death", []):
                reason = death.get("reason")
                reason = reason.decode() if isinstance(reason, bytes) else reason
                origin = death.get("queue")
                origin = origin.decode() if isinstance(origin, bytes) else origin
                print(f"    档案: 死于 {reason},原队列 {origin}")
            await message.ack()


asyncio.run(main())
```

## 逐个文件讲

### common.py:拓扑声明,一人一份,谁先谁后都行

每个服务脚本启动都先调 `declare_topology(channel)`。第 1 讲说过声明是幂等的,所以五六个进程同时启动、同时建同一套拓扑,谁都不冲突——**分布式系统里"没有启动顺序依赖"是省心的开始**。交换机、队列、绑定全在这里声明,拓扑一目了然,真实项目里对应的就是这样一个集中定义的 `topology.py`。

队列参数里藏着两条第 5、6 讲的组合技:

- ① 短信队列配 `x-dead-letter-exchange` + `x-dead-letter-routing-key="dead"`——重试耗尽的死信走 dead 出口,进死信池等人工;
- ② 付款等待队列配 `x-message-ttl=15_000` + 死信走 timeout 出口——15 秒一到,死信进超时服务自动处理;
- ③ **同一个死信交换机,两个出口**,靠 `x-dead-letter-routing-key` 各自改写路由键分流——这就是死信交换机用 direct 而不是 fanout 的理由。

### order_service.py:生产者的自我修养

每笔订单发两样东西,加上付款一共三个动作,每个都按前面讲的规矩来:

- ① 广播 `order.created`——眼下没有任何队列绑它,这条消息发出去就没了,**故意的**:哪天数据分析想订阅订单创建,它自己绑个队列就行,订单服务一行不改。这就是第 3 讲"解耦落到实处的样子",代码里看不见,但架构上值钱;
- ② 延迟炸弹直投付款等待队列——第 6 讲的套路;
- ③ 付款:**先改库、再发事件,顺序别反**——反过来的话,事件都广播出去了,查库却还是"待付款",下游拿着旧状态做决定。

### sms_service.py:失败处理的完整套路

消息消费失败,处置三板斧在这段代码里齐了:

- ① **幂等挡板**:内存集合 `sent` 记住发过的订单,重投的消息直接跳过。注意这是最弱的幂等——进程一重启就忘,重启后重投的消息会再发一次短信。生产上换成 Redis SET 或数据库唯一键就补上了,这个缺陷是故意的,和积分服务对照着看;
- ② **重试**:原消息 ack 掉,带着 retry 计数的新消息**直投本队列**(`routing_key=SMS_QUEUE`),不广播——重试是短信服务自己的私事,不该再广播给积分服务。为什么"ack 旧的、发新的"?因为消息一旦进队列就改不了(没有"改消息"的 API),想带计数只能发新的、确认旧的——这个手法在重试、延迟、优先级调整场景通用;
- ③ **放弃**:三次全败,`nack(requeue=False)`,队列的 DLX 接手,进死信池由 watcher 告警,人工兜底。

> **敲黑板:** 这里演示的是"立刻重试"。想要"隔 5 秒再试"呢?把直投目标从 SMS_QUEUE 换成一条 `x-message-ttl=5000`、死信再指回 SMS_QUEUE 的中转队列——第 6 讲的"分档延迟",一模一样的积木,多拼一块而已。再配 15s/60s 两档,就是你上一轮课程里那三个 retry 队列的真身。

### points_service.py:持久化幂等,先落库后 ack

① `db.grant_points()` 把"已发积分"记在订单表里,发过返回 False——进程随便重启、消息随便重投,积分永远只发一次。

> **敲黑板:** 顺序有讲究:**先落库、后 ack**。反过来的话,落库失败但消息已确认,这条就凭空蒸发了。这半句是第 2 讲"ack 的时机"在真实业务里的落点,财务、库存类消费者全是这个铁律。

### timeout_service.py:到点回查,延迟消费的铁律

第 6 讲立的规矩,实战里兑现:① 拿到死信先查库,三个分支——已付款(虚惊一场,什么都不做)/已取消(幂等跳过)/真没付(取消、释放库存)。15 秒里用户随时可能付款,**RabbitMQ 又没有"撤回消息"的 API**,所以延迟消息到点后唯一正确的动作就是回查业务状态。真实输出里三笔单三种结局,就是这条分支逻辑的展示。

### watcher.py 与 reset.py

观察员是第 5 讲"收容之后呢"的答案:消费死信、打印、(生产里)推告警。人工处理完,可以把消息体拿去修数、或重新投回业务队列。reset.py 则是演示脚本的卫生习惯:清队列、删交换机、删订单表,一键回到初始状态。

## 这个架构在企业里对应什么

把文件名换成真实世界的名字,这套结构随处可见:

- `shop.events` = 订单中心的领域事件总线;
- `sms/points_service` = 各下游域的通知、会员服务,**新增订阅方不动上游**;
- `shop.pay.wait` + `shop.timeout` = 订单超时关闭任务(电商标配,30 分钟版);
- 短信三连败 + 死信池 = 通知中心的失败兜底与人工重放;
- 全员手动 ack + 幂等 = 财务、库存类消费者的底线操作。

学完这讲,你已经能读懂绝大多数"XX 平台订单系统设计"文章里的消息队列部分,并且知道每一块积木为什么长那样。
