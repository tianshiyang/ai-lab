# 第 5 讲 · 周期任务与 Beat

## 0 开场:任务的第二个来源

前四讲的任务都由**事件**触发:代码里某处 `.delay()`。还有一类任务由**时间**触发:每晚对账、每分钟清理、每天 9 点报表。兔 MQ 里没有这种原生的"定时发消息"(你在第 6 讲用 TTL + 死信拼过一次性延迟,但"每天 3 点"这种循环触发只能靠外部 cron)。Celery 自带了一个:**beat,看表的进程**。

```
   beat 进程(拿表的对时员)                worker
   ┌─────────────────────────┐
   │ 到 10 秒 → heartbeat.delay()──┼──► cel5 队列 ──► 领走执行
   │ 到整分   → cleanup.delay()───┼──►     ↑
   │ 到 3:00  → reconcile.delay()─┘        │
   └─────────────────────────┘            │
        beat 就是个"自动的调用端":不干活,只按时投递
```

beat 不执行任务,它只是**到点替你调 `.delay()`**;干活的还是 worker。两件事两个进程,这本身就是部署常识:beat 起在哪台机器、worker 起几台,互不相干。

## 1 beat_schedule:调度表

```python
from celery.schedules import crontab

app.conf.beat_schedule = {
    "心跳巡检": {
        "task": "tasks.heartbeat",           # 任务名,字符串——别 import 函数,beat 和任务解耦
        "schedule": 10.0,                     # 每 10 秒(float 秒)
    },
    "清理过期购物车": {
        "task": "tasks.cleanup_expired_carts",
        "schedule": crontab(minute="*"),      # 每分钟整分
    },
    "每日对账": {
        "task": "tasks.daily_reconcile",
        "schedule": crontab(hour=3, minute=0),            # 每天凌晨 3 点(北京时间)
        "options": {"expires": 3600},                      # 投递选项:一小时没执行就作废
    },
}
```

`schedule` 两种形态:

| 形态 | 写法 | 从哪起算 |
|---|---|---|
| float | `10.0` | **beat 启动时刻**起,每 10 秒一跳 |
| `crontab(...)` | 五个字段 | **挂钟时间**:整分、整点对齐 |

`crontab` 五字段(不写就是 `*`):

| 字段 | 取值 | 例子 |
|---|---|---|
| `minute` / `hour` | 0-59 / 0-23 | `minute=0, hour=3` = 每天 3:00 |
| `day_of_month` | 1-31 | `day_of_month=1` = 每月 1 号 |
| `month_of_year` | 1-12 | 少单独用 |
| `day_of_week` | 0-6 或 mon-sun | `day_of_week="mon-fri"` = 工作日 |

字段内语法:`*` 全部;`*/5` 每隔 5;`3,15` 列举;`8-18` 区间。例:`crontab(minute="*/30", day_of_week="mon-fri")` = 工作日每半小时。

`options` 里放的就是 apply_async 的投递选项(`expires`、`queue`、`priority`)——周期任务常常配 `expires`:对账任务到点没被干(队列堆积)就作废,免得 worker 缓过来后一口气补跑十次。

时区就是第 1 讲配置的 `timezone="Asia/Shanghai"`——`hour=3` 是北京时间 3 点,不用换算。

## 2 两个进程,两条命令

```
终端 1:  uv run celery -A celery_app worker --pool=solo -l info
终端 2:  uv run celery -A celery_app beat -l info
```

beat 的日志很有性格,到点就一行:

```
[19:10:00: INFO/MainProcess] Scheduler: Sending due task 清理过期购物车 (tasks.cleanup_expired_carts)
```

worker 那边随即 `received`。beat 是"发"的记录,worker 是"干"的记录,对着看才完整。

两个细节:

- beat 在本地存一个小文件(`beat-schedule`),记着每项任务**上次跑到哪**。别手欠删它:删了失忆,重启时 crontab 任务可能立刻补发一次。
- **beat 是常驻进程**,和 worker 一样用 systemd/supervisor 守着(第 7 讲)。

## 3 敲黑板:beat 必须单实例

beat 没有"选主"机制,起两个 beat,每个都会按时投递——**每个周期任务准时双倍执行**。对账跑两遍算轻的,给用户发两遍营销短信就是事故。防御姿势:

| 场景 | 做法 |
|---|---|
| 单机部署 | systemd 只配一个 beat 服务,机器挂了它也挂,不会多 |
| 多机/容器,怕单点 | **redbeat**(celery-redbeat):调度表放 Redis,自带分布式锁,多开也只有一个在发 |
| 运营要后台改周期 | **django-celery-beat**:调度表进数据库,管理后台改时间不用发版 |

下面实验二会亲眼看看双 beat 的双倍事故,先立此存照。

## 4 周期任务的自我修养

| 修养 | 为什么 |
|---|---|
| **幂等** | beat 不在乎上一轮干没干完,到点就投。对账任务跑两遍结果还得是对的(扫表式天然幂等:SELECT 没结算的 → 逐条处理) |
| **想好重叠** | 心跳 10 秒一跳,任务干 15 秒,队列稳步上涨。防御:`expires` 作废积压、任务开头查"上轮还在跑吗"(Redis 锁)、或把间隔放宽 |
| **带水位** | "扫表"类任务记 `last_watermark`(上次处理到哪),下轮从水位接着扫,别每轮全表 |

兔 MQ 第 2 讲那句"重投必然意味着可能被处理多次",在周期任务这儿换了个说法又来了:**到点必然意味着可能再处理,幂等是后台任务的通用税**。

## 5 完整示例

### celery_app.py

```python
"""第 5 讲·Celery 应用:配 beat_schedule,cel5。"""

import os
from pathlib import Path

from celery import Celery
from celery.schedules import crontab
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")

app = Celery(
    "cel5",
    broker=os.environ["RABBITMQ_URL"],
    backend=os.environ["REDIS_URL"],
    include=["tasks"],
)

app.conf.update(
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    timezone="Asia/Shanghai",
    task_default_queue="cel5",
    task_acks_late=True,
    task_reject_on_worker_lost=True,
    worker_prefetch_multiplier=1,
    result_expires=3600,
    beat_schedule={
        "心跳巡检": {
            "task": "tasks.heartbeat",
            "schedule": 10.0,
        },
        "清理过期购物车": {
            "task": "tasks.cleanup_expired_carts",
            "schedule": crontab(minute="*"),
        },
        # 这条今天等不来(凌晨 3 点),写上是让你见见真身:
        # 真实项目里的对账、日报、账单,全是这个形态
        "每日对账": {
            "task": "tasks.daily_reconcile",
            "schedule": crontab(hour=3, minute=0),
            "options": {"expires": 3600},
        },
    },
)
```

### tasks.py

```python
"""第 5 讲·任务:三个周期任务,心跳可数、清理可看、对账等不到。"""

from datetime import datetime

from celery.utils.log import get_task_logger

from celery_app import app

logger = get_task_logger(__name__)


@app.task(ignore_result=True)
def heartbeat() -> None:
    """心跳:10 秒一跳,专门用来看节奏"""
    logger.info("♥ %s", datetime.now().strftime("%H:%M:%S"))


@app.task(ignore_result=True)
def cleanup_expired_carts() -> None:
    """清理过期购物车:每分钟整分,扫表式(真实项目里是一条 UPDATE)"""
    logger.info("扫了一圈购物车表,清理了 2 个过期的")


@app.task
def daily_reconcile() -> dict:
    """每日对账:凌晨 3 点,睡 3 秒假装在对"""
    logger.info("对账开始……")
    return {"date": datetime.now().strftime("%Y-%m-%d"), "diffs": 0}
```

## 6 跑起来

**实验一:看表。** worker、beat 两个终端都起好,盯着 beat 和 worker 的输出(两边按时间对齐):

```
beat:    [19:20:10: INFO] Scheduler: Sending due task 心跳巡检 (tasks.heartbeat)
worker:  [19:20:10: INFO] Task tasks.heartbeat[...] received
worker:  [19:20:10: INFO] tasks.heartbeat[...]: ♥ 19:20:10
beat:    [19:20:20: INFO] Scheduler: Sending due task 心跳巡检 (tasks.heartbeat)
worker:  [19:20:20: INFO] tasks.heartbeat[...]: ♥ 19:20:20
...
beat:    [19:21:00: INFO] Scheduler: Sending due task 清理过期购物车 (tasks.cleanup_expired_carts)
worker:  [19:21:00: INFO] tasks.cleanup_expired_carts[...]: 扫了一圈购物车表,清理了 2 个过期的
```

注意两个节拍器:**心跳从 beat 启动那刻起算 10 秒一跳**(启动在 19:20:00,跳在 :10、:20……);**清理按挂钟整分**(19:21:00、19:22:00)。float 看启动,crontab 看挂钟——选哪个就看你要哪种节奏。

**实验二:双 beat 事故现场(做完就关)。** 再开一个终端,把 beat 命令**原样再跑一份**:

```
终端 3:  uv run celery -A celery_app beat -l info
```

十秒之内 worker 终端出现**同一时刻两行心跳**——两个 beat 各发各的,谁也不知道对方存在。这就是第 3 节敲黑板的现场版。看完立刻 Ctrl+C 关掉终端 3,别让心脏多跳。

**实验三(顺手):周期任务也是任务。** Ctrl+C 停掉 beat,worker 留着,手动投一发对账:

```
uv run python -c "from tasks import daily_reconcile; print(daily_reconcile.delay().id)"
```

worker 正常把它干掉——beat 只是投递者,任务的执行逻辑和前四讲的任何一个任务没有任何区别。调试周期任务的日常:**写好先手动 delay 跑通,再交给 beat**。

收摊:两个终端都 Ctrl+C,顺手删掉本讲目录下的 `beat-schedule` 文件(本地进度档案,留着下轮实验会"记得"旧节拍)。

## 7 速查表

| 部件 | 位置 | 作用 |
|---|---|---|
| `beat_schedule = {"名字": {...}}` | app.conf | 调度表 |
| `task`(字符串) | 条目 | 要投的任务名 |
| `schedule: 10.0` | 条目 | float 秒,从 beat 启动起算 |
| `schedule: crontab(...)` | 条目 | 五字段挂钟时间 |
| `options={"expires": ...}` | 条目 | 投递选项,周期任务常配 expires 防积压补跑 |
| `celery -A celery_app beat` | 命令行 | 启动调度进程,必须单实例 |
| redbeat / django-celery-beat | 生态 | 分布式锁 / 后台动态改周期 |
