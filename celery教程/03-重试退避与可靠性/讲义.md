# 第 3 讲 · 重试退避与可靠性

## 0 开场:失败的两条路

兔 MQ 教程第 2 讲的闭环是:**消费者没 ack 就崩 → broker 收回重投**。到了 Celery,先破一个想当然:

| 出事方式 | Celery 的反应(默认配置) |
|---|---|
| 任务函数**抛异常** | 消息照样 ack,**不重投**。失败被记录成 FAILURE 存进 backend |
| 任务函数抛异常(声明了自动重试) | **发一条带计数的新消息,ack 旧消息**,到点再干 |
| **worker 进程崩溃**(没 ack) | broker 收回重投——和兔 MQ 教程一模一样,但要先开两个开关 |

"异常"和"崩溃"在兔 MQ 教程里都走"重投",在 Celery 里**是两条路**:异常是应用层的,靠重试机制;崩溃是传输层的,靠 ack 机制。第 2 讲实验二你已经见过第一条的默认行为(必败任务 FAILURE、消息被确认);这一讲把三条路全打通。

还有个让人会心一笑的对照:第 2 条路"ack 旧的、发带计数的新消息"——你在兔 MQ 第 8 讲**手写过这套**(`sms_service` 的重试三板斧)。Celery 的 `self.retry()` 内置了它,还附赠指数退避。

## 1 autoretry:声明式重试

企业里九成的重试就这几行装饰器参数:

```python
@app.task(
    autoretry_for=(ConnectionError, TimeoutError),  # 这些异常触发重试
    retry_backoff=True,        # 指数退避:间隔 1、2、4、8……秒
    retry_backoff_max=60,      # 间隔封顶:再指数也不超过 60 秒
    retry_jitter=True,         # 抖动:间隔加个随机量,别让重试踩着正步走
    max_retries=4,             # 最多重试 4 次,之后认 FAILURE
)
def sync_price(goods_id: int) -> dict:
    ...
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `autoretry_for` | () | 元组列异常类型,命中就重试。**只列值得重试的**:网络抖动、下游 503 值得;参数错误、余额不足重试一百次也没用,还白白烧机器 |
| `retry_backoff` | False | True = 间隔按 2 的幂走(1、2、4、8……);填数字则从它起步 |
| `retry_backoff_max` | 600 | 间隔的上限 |
| `retry_jitter` | True | 间隔加随机抖动。下游刚重启,一千个任务同秒重试会把下游再拍死——抖动把"齐步走"打散,**生产必开** |
| `max_retries` | 3 | 重试上限。耗尽后任务以最后一次的原异常终局为 FAILURE |
| `dont_autoretry_for` | () | 例外:这些异常即便命中 autoretry_for 也不重试 |

不开 backoff 时的固定间隔由 `default_retry_delay`(默认 180 秒)管——老代码里常见,新代码直接 backoff + jitter。

**敲黑板:重试期间状态是 RETRY**,backend 里可查;每次重试 worker 日志打一行 `Retry in Xs: 异常摘要`——间隔带着 jitter,别指望精确的 1、2、4,2.7 秒、4.1 秒都是它。

## 2 self.retry:手动精确控制

哪些错值得重试要**看情况**时,手动版出马:

```python
@app.task(bind=True, max_retries=4)      # bind=True:self 才进得来
def sync_price(goods_id: int) -> dict:
    logger.info("第 %s 次尝试同步商品 %s 的价格", self.request.retries, goods_id)
    try:
        return call_price_api(goods_id)
    except HTTPError as exc:
        if exc.status >= 500:            # 下游病了,等等再试
            raise self.retry(exc=exc, countdown=5 * 2 ** self.request.retries)
        raise                            # 参数错/没权限,直接失败,别重试
```

| 部件 | 说明 |
|---|---|
| `bind=True` | 把任务实例绑为第一参数 `self`,装饰器参数和 self.request 都从它来 |
| `self.retry(exc=...)` | 必须以 `raise self.retry(...)` 的形式调用——它内部就是"发新消息、抛 Retry 异常终止本轮" |
| `self.request.retries` | 当前是第几次重试,从 0 数起。退避数列、剧本判断全靠它 |
| `countdown=` | 这次隔多久再试,自己算(例子:5、10、20 秒) |
| 重试耗尽再调 `self.retry` | 抛 `MaxRetriesExceededError` |

## 3 ack 的两个开关

第 1 讲配置里埋的三件套,现在兑现。先看 Celery 的默认有多"乐观":

| | `task_acks_late=False`(默认) | `task_acks_late=True` |
|---|---|---|
| 消息何时确认 | worker **领到就 ack** | 任务**干完才 ack** |
| worker 干到一半被硬杀 | 消息已确认,**任务凭空蒸发** | broker 收回重投 |
| 兔 MQ 教程对照 | 相当于 ack 了才开干,比 no_ack 强不到哪去 | 第 2 讲的手动 ack 闭环 |

`acks_late=True` 单用还有个缝:worker 进程死于任务执行中(比如 OOM 被系统杀),这一条消息卡在"已投递未确认"里晾着——`task_reject_on_worker_lost=True` 补上:进程丢了,**主动 reject 让 broker 重投**。

配套的 `worker_prefetch_multiplier=1`(囤任务上限 = 1 × 并发数):干完一个再领一个,兔 MQ 第 2 讲公平分发的翻版。三件套合起来才是企业起步配置,第 1 讲起就写进了 `app.conf`。

**敲黑板:优雅停机与硬杀是两回事。** worker 收到 Ctrl+C(SIGTERM)会走 warm shutdown:把手头的活干完、ack 完才退出,消息不丢。硬杀(关窗口、`kill -9`、断电)才会触发"收回重投"。下面的实验两种都做。

## 4 重试耗尽之后

三次(或 N 次)重试全败,任务以 FAILURE 终局:**异常已存档,消息已确认,没有死信队列**——这点和兔 MQ 第 5 讲不同,Celery 圈子的主流做法不是 DLX,而是"FAILURE + 告警"。企业里告警挂在这里:

```python
from celery import Task

class AlertOnFailure(Task):                 # 任务基类:失败时自动派一个告警任务
    def on_failure(self, exc, task_id, args, kwargs, einfo):
        alert_ops.delay(                     # 告警本身也是个任务,进告警队列
            task_name=self.name, task_id=task_id,
            args=str(args), error=str(exc),
        )


@app.task(base=AlertOnFailure, ...)         # 想要告警的任务挂这个基类
def sync_price(goods_id: int) -> dict:
    ...
```

真想把失败扔进 MQ 死信队列也行:`task_acks_on_failure_or_timeout=False`(失败不确认、改 reject)+ 队列配 DLX——你在兔 MQ 第 5 讲的全套知识原样可用,watcher 都能复用。但这条路会让"哪些任务进了死信"变得隐晦,**先 FAILURE + 告警,DLX 留给确实需要的场景**。

不管走哪条,别忘了兔 MQ 第 2 讲的老结论在这里同样成立:**重试 = 可能被处理多次,任务必须幂等**(干一半崩了重投,重投后从头再干;autoretry 到点再干也是第二次执行)。幂等做法(任务表记状态、先查再做)第 8 讲实战再写一遍。

## 5 完整示例

### celery_app.py

三件套已在,和第 2 讲只差名字(cel3),照第 2 讲那份把 `"cel2"`/`"cel2"` 换成 `"cel3"`/`"cel3"` 存盘即可。

### tasks.py

三个任务对应三条路:重试后成功 / 重试耗尽 / 干得慢(给崩溃实验当靶子):

```python
"""第 3 讲·任务:会好的病、不会好的病、干得慢的活。"""

import time

from celery.utils.log import get_task_logger

from celery_app import app

logger = get_task_logger(__name__)


@app.task(
    bind=True,
    autoretry_for=(ConnectionError,),
    retry_backoff=True,
    retry_backoff_max=30,
    retry_jitter=True,
    max_retries=3,
)
def sync_price(self, goods_id: int) -> dict:
    """同步商品价格:前两次抛 ConnectionError(会好的病),第三次成功"""
    attempt = self.request.retries + 1
    logger.info("第 %s 次尝试同步商品 %s 的价格", attempt, goods_id)
    if attempt < 3:
        raise ConnectionError(f"价格服务连接超时(第 {attempt} 次)")
    logger.info("商品 %s 价格同步成功", goods_id)
    return {"goods_id": goods_id, "price": 99.0, "attempts": attempt}


@app.task(
    autoretry_for=(ConnectionError,),
    retry_backoff=True,
    max_retries=3,
)
def sync_price_hopeless(goods_id: int) -> dict:
    """同步价格:永远失败,演示重试耗尽 → FAILURE"""
    raise ConnectionError(f"价格服务彻底挂了(goods_id={goods_id})")


@app.task
def slow_io(seconds: int = 30) -> str:
    """慢活:睡 30 秒,给'杀 worker'实验当靶子"""
    logger.info("慢活开干,要 %s 秒 —— 现在去杀我", seconds)
    time.sleep(seconds)
    logger.info("慢活干完了")
    return f"done after {seconds}s"
```

`bind=True` + `autoretry_for` 可以同用:`self` 供你读 `request.retries`,重试本身交给声明式。

### send.py

```python
"""第 3 讲·调用端:看一条任务从 RETRY 走到 SUCCESS,再看一条走到 FAILURE。

    cd "celery教程/03-重试退避与可靠性"
    uv run python send.py
"""

import time

from tasks import sync_price, sync_price_hopeless

r = sync_price.delay(goods_id=3001)
print(f"① sync_price 已投递,ID: {r.id}(病两次,第三次好)")
for _ in range(20):
    print(f"   [{time.strftime('%H:%M:%S')}] 状态: {r.state}")
    if r.ready():
        break
    time.sleep(1)
print(f"   结果: {r.get(propagate=False)}")

bad = sync_price_hopeless.delay(goods_id=3002)
print(f"② sync_price_hopeless 已投递,ID: {bad.id}(病到天荒地老)")
for _ in range(20):
    if bad.ready():
        break
    time.sleep(1)
print(f"   终局: {bad.state},异常: {bad.get(propagate=False)!r}")
```

## 6 跑起来

worker 常驻,三个实验:

```
终端 1:  cd "celery教程/03-重试退避与可靠性"
         uv run celery -A celery_app worker --pool=solo -l info
终端 2:  cd "celery教程/03-重试退避与可靠性"
         uv run python send.py
```

**实验一:重试节奏,worker 日志是主角。** send.py 跑完后看终端 1:

```
[INFO/MainProcess] Task tasks.sync_price[...] received
[INFO/MainProcess] tasks.sync_price[...]: 第 1 次尝试同步商品 3001 的价格
[INFO/MainProcess] Task tasks.sync_price[...] retry: Retry in 2s: ConnectionError('价格服务连接超时(第 1 次)')
[INFO/MainProcess] Task tasks.sync_price[...] received
[INFO/MainProcess] tasks.sync_price[...]: 第 2 次尝试同步商品 3001 的价格
[INFO/MainProcess] Task tasks.sync_price[...] retry: Retry in 3s: ConnectionError('价格服务连接超时(第 2 次)')
[INFO/MainProcess] Task tasks.sync_price[...] received
[INFO/MainProcess] tasks.sync_price[...]: 第 3 次尝试同步商品 3001 的价格
[INFO/MainProcess] tasks.sync_price[...]: 商品 3001 价格同步成功
[INFO/MainProcess] Task tasks.sync_price[...] succeeded in 0.1s: {'goods_id': 3001, 'price': 99.0, 'attempts': 3}
```

两件事:`Retry in 2s / 3s` 是 backoff + jitter 的实拍(理论间隔 1、2 秒,jitter 上下随机揉——实际比理论大点小点都正常);每次重试都是一条 `received`——**新消息**。终端 2 里状态同步走着:`PENDING → RETRY → RETRY → SUCCESS`,拿到 `attempts: 3`。

紧接着 `sync_price_hopeless` 的日志:三次 `Retry in ...` 之后一行 `raised unexpected: ConnectionError(...)`——重试耗尽,终局 FAILURE,send.py 的第二段打印:

```
② sync_price_hopeless 已投递,ID: ...(病到天荒地老)
   终局: FAILURE,异常: ConnectionError('价格服务彻底挂了(goods_id=3002)')
```

**实验二:优雅停机。** 投一个慢活再 Ctrl+C:

```
终端 2:  uv run python -c "from tasks import slow_io; r = slow_io.delay(); print(r.id)"
终端 1:  (worker 打出"慢活开干,要 30 秒 —— 现在去杀我")此时按 Ctrl+C
```

worker 打出 `Warm shutdown (MainProcess)` 后**并不退出**——它在等手头的慢活干完。30 秒后慢活 `succeeded`、消息确认,worker 才告别。消息没丢,也没重投:优雅停机对在途任务是无感的。

**实验三:硬杀与重投。** 再投一个慢活,这次不 Ctrl+C,直接**点终端窗口的 ×**(或另开终端 `taskkill /F /IM celery.exe`——硬杀,不给人收拾的机会)。然后去管理台 `cel3` 队列页:消费者消失了,**Unacked 里挂着 1 条**。重启 worker:

```
[INFO/MainProcess] Task tasks.slow_io[同一个ID...] received
```

同一条任务回来了——broker 收回未确认消息重新投递,兔 MQ 第 2 讲实验三的复刻。补一刀:`slow_io` 干完输出 `done after 30s`,而 `self.request.retries` 若打印的话是 0——**崩溃重投不带重试计数**(那是 autoretry 发新消息时才写的 header),任务从函数第一行重新执行。幂等,还是那句话。

## 7 速查表

| API / 参数 | 层 | 作用 |
|---|---|---|
| `autoretry_for=(异常,...)` | 装饰器 | 声明式重试 |
| `retry_backoff` / `retry_backoff_max` / `retry_jitter` | 装饰器 | 指数退避 + 抖动 |
| `max_retries` | 装饰器 | 上限,耗尽 → FAILURE |
| `bind=True` + `raise self.retry(exc=, countdown=)` | 装饰器 + 函数体 | 手动精确重试 |
| `self.request.retries` | 任务内 | 当前重试次数(0 起) |
| `task_acks_late` | app.conf | 干完才确认(默认 False,企业开 True) |
| `task_reject_on_worker_lost` | app.conf | 进程暴毙时 reject 触发重投 |
| `worker_prefetch_multiplier` | app.conf | 囤任务上限倍数,1 = 公平分发 |
| `task_acks_on_failure_or_timeout` | app.conf | 失败是否确认(想走 DLX 才关) |
| `Task.on_failure` | 基类 | 失败告警挂点 |
