# 第 1 讲 · 第一个任务与工程骨架

## 0 模型

**Celery 是什么**:一个分布式任务队列框架。你把"要慢慢干的活"写成函数,扔给后台去跑,你的程序立刻返回该干嘛干嘛。

```
   调用端 send.py            broker(还是那台 RabbitMQ)            worker(后台进程)
   ──────────────           ────────────────────────            ──────────────────
   compress_image.delay()──►│  cel1 队列                           │──► 领任务、执行函数
   返回一张回执(ID)          │  [task][task][task]                 │    干完把结果写走
        │                    └────────────────────────────────────┘        │
        │                                                            结果backend(Redis)
        └────────────── result.get() 拿结果 ◄──────── celery-task-meta-<ID> ┘
```

你在 rabbitmq教程 里手写的那些活——消费者循环、手动 ack、崩溃重投、发消息编码解码——**Celery 全包了**。你只剩两件事:写任务函数、配置应用。代价是多学一层"企业写法的规矩",这套规矩就是本教程的主线。

先做概念翻译。学过兔 MQ 教程的话,右边这列你全认识:

| 兔 MQ 教程里的你 | Celery 里的对应 | 变化 |
|---|---|---|
| 生产者程序(你写) | 调用端(一行 `.delay()`) | 不再自己连 broker |
| 消费者循环(你写) | **worker 进程**(框架的) | 你只提供"循环体"=任务函数 |
| 队列(broker 上) | 还是队列(broker 上) | Celery 开工时自动声明 |
| 消息体 `json.dumps(...).encode()` | 任务名 + 参数(框架序列化) | json,默认就是 |
| ack / nack / prefetch | 框架的确认机制(配置开关) | 第 3 讲 |
| 死信、TTL、交换机路由 | 都还在 broker 里,Celery 少量用到 | 第 3、4 讲对照 |

新增两个角色:**结果 backend**(Redis,任务干完的返回值存这儿,调用端凭 ID 来取)和 **beat**(定时器进程,第 5 讲)。

## 1 零件清单

| 概念 | 一句话 |
|---|---|
| 应用 app | 全工程唯一的 `Celery(...)` 实例,配置总开关盒 |
| 任务 task | 加了 `@app.task` 的普通函数,名字全局唯一 |
| worker | 干活的常驻进程,守着队列领任务 |
| broker | 任务消息走的中间件,本课程用你的 RabbitMQ |
| backend | 结果存取处,本课程用你的 Redis |
| 调用端 | 任何 import 了任务并 `.delay()` 的代码:脚本、Web 服务、定时器 |
| beat | 周期调度进程(第 5 讲) |

## 2 工程骨架

企业里一个 Celery 工程就三个角色文件(第 4 讲起任务会拆成包):

```
01-第一个任务与工程骨架/
├── celery_app.py   # 应用实例 + 全部配置:全工程唯一,worker 和调用端都 import 它
├── tasks.py        # 任务模块:函数头上加装饰器,普通函数就成了后台任务
└── send.py         # 调用端:把任务丢给后台,拿回执
```

规矩:**一个项目一个 app,配置全部集中在 `app.conf`**。散落在各处的 `@app.task(...)` 参数、worker 命令行选项能表达一部分配置,但企业里"总配置在 app、个别例外在装饰器"是铁律——第 4 讲你会看到它的好处(路由表集中管理)。

仓库里不提供 `.py`,照着敲到本目录,文件名按下面的写。

## 3 celery_app.py —— 应用与配置

```python
"""第 1 讲·Celery 应用实例:整个工程的底盘。

worker 和调用端都从这份文件 import app;配置集中在这里,全教程的"总开关盒"。
"""

import os
from pathlib import Path

from celery import Celery
from dotenv import load_dotenv

# 和 rabbitmq教程 同款:连接地址住在仓库根目录的 .env,不进代码
load_dotenv(Path(__file__).parents[2] / ".env")

app = Celery(
    "cel1",                            # 项目名,出现在 worker 启动横幅和日志里
    broker=os.environ["RABBITMQ_URL"],  # 任务消息走哪:还是那台 RabbitMQ
    backend=os.environ["REDIS_URL"],    # 结果存哪:你的 Redis
    include=["tasks"],                  # 任务模块清单,worker 启动时按它导入
)

app.conf.update(
    # —— 序列化:企业底线,参数和结果都走 json ——
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    # —— 时区:周期任务按它算(第 5 讲) ——
    timezone="Asia/Shanghai",
    # —— 队列:不配的话默认队列名就叫 "celery";各讲各的队列,互不干扰 ——
    task_default_queue="cel1",
    # —— 可靠性三件套,第 3 讲整章展开 ——
    task_acks_late=True,
    task_reject_on_worker_lost=True,
    worker_prefetch_multiplier=1,
    # —— 结果在 Redis 里的保质期,过一小时自动清理,别住成垃圾 ——
    result_expires=3600,
)
```

词条:

| 配置 | 默认 | 说明 |
|---|---|---|
| `Celery("cel1", ...)` 第一参数 | 必填 | 项目名。只影响横幅与日志前缀,叫什么都行,各讲用 cel1~cel8 |
| `include=[...]` | 空 | 任务模块名字符串。worker 启动时 import 它们——**字符串是惰性的**,调用端 import app 不会连任务一起拖进来 |
| `task_serializer` | json | 任务参数的序列化格式。**企业永不打开 pickle**:接收端会反序列化执行,等于远程代码执行漏洞 |
| `accept_content` | [json] | 白名单,收到别的格式的任务直接拒收 |
| `timezone` | UTC | crontab(第 5 讲)按这个时区解释 |
| `task_default_queue` | celery | 任务没指定队列时的去处。这里改叫 cel1,各讲不串台 |
| `task_acks_late` | False | 任务**干完**才 ack(而不是领到就 ack)。对照兔 MQ 第 2 讲的手动 ack,第 3 讲展开 |
| `worker_prefetch_multiplier` | 4 | 一个 worker 最多囤几倍的任务。设 1 = 干完一个再领一个,公平分发的老朋友 |
| `result_expires` | 86400 | 结果在 backend 的存活秒数,到期 Redis 自动删 |

**敲黑板:配置分三层。** `app.conf`(全局)→ `@app.task(...)`(单个任务例外)→ `apply_async(...)`(单次调用微调)。后两层只放"例外",默认值一律第一层管。全教程的配置都长在 `celery_app.py` 里,就是照这个规矩写的。

## 4 tasks.py —— 任务函数

```python
"""第 1 讲·任务模块:函数头上加 @app.task,普通函数就成了后台任务。"""

import time

from celery.utils.log import get_task_logger

from celery_app import app

logger = get_task_logger(__name__)   # 任务专用 logger,每行自动带 任务名[任务ID] 前缀,见下方实拍


@app.task
def compress_image(goods_id: int, seconds: int = 2) -> dict:
    """压缩商品图:睡 seconds 秒假装在干活,返回报告"""
    logger.info("开始压缩商品 %s 的图片,要干 %s 秒……", goods_id, seconds)
    time.sleep(seconds)
    logger.info("商品 %s 压缩完成", goods_id)
    return {"goods_id": goods_id, "compressed": True, "bytes_saved": goods_id * 1024}
```

| 要点 | 说明 |
|---|---|
| `@app.task` | 注册:函数体还是普通函数,能本地调用也能 `.delay()` 后台调 |
| 任务名 | 默认 = `模块.函数`,即 `tasks.compress_image`。**名字是全局坐标**:第 4 讲按它路由、第 7 讲按它撤回监控。别随手改任务名,改了等于旧坐标作废 |
| 参数与返回值 | 必须可 json 序列化(int/str/list/dict……)。返回值就是调用端 `.get()` 将拿到的东西 |
| `get_task_logger` | 任务里别用 `print`(在 solo 池里会被接管成 WARNING 级日志,第 7 讲细说),正经写法是它 |

## 5 send.py —— 调用端

```python
"""第 1 讲·调用端:把任务丢给后台,拿回执、取结果。

    cd "celery教程/01-第一个任务与工程骨架"
    uv run python send.py
"""

from tasks import compress_image

result = compress_image.delay(goods_id=1001, seconds=2)   # 投递,立刻返回
print(f"已投递,任务 ID: {result.id}")
print(f"此刻状态: {result.state}")
print("等结果……")
report = result.get(timeout=10)                           # 阻塞等 worker 干完
print(f"结果: {report}")
print(f"最终状态: {result.state}")
```

| API | 说明 |
|---|---|
| `compress_image.delay(...)` | 投递。**一瞬间就返回**,不管 worker 在不在、活多久——和 `publish` 只管发一个道理 |
| `result.id` | 任务 UUID,backend 里结果的存档号 |
| `result.state` | 状态机:第 2 讲整章 |
| `result.get(timeout=10)` | 阻塞取结果。**演示和学习用**,生产 Web 请求里这么写等于自杀,第 2 讲展开 |

## 6 启动 worker

```
uv run celery -A celery_app worker --pool=solo -l info
```

| 段 | 作用 |
|---|---|
| `celery ... worker` | celery 命令行,子命令 worker |
| `-A celery_app` | 应用在哪:import 这个模块找 app。**这就是命令必须在本讲目录执行的原因**——celery 靠 import 找应用,你得站在应用旁边 |
| `--pool=solo` | 并发池选 solo(单进程) |
| `-l info` | 日志级别 info,能看见每个任务的收发记录 |

**敲黑板:Windows 上必须 `--pool=solo`。** Celery 默认的 prefork 进程池依赖 Unix 的 fork,Linux 服务器上开箱即用;Windows 上不带 `--pool=solo` 启动会在干活时报 `ValueError: not enough values to unpack` 一类怪错。本课程所有 worker 命令都带它,`--pool` 的全家福在第 7 讲。

**敲黑板:worker 只在启动时 import 一次任务模块。** 改了 tasks.py,正在跑的 worker 毫不知情——Ctrl+C 重启它才生效。这是新手第一大坑(本教程实测时也踩了一脚)。生产上没有热重载,正经做法是发布新版本后滚动重启 worker。

启动横幅(你的机器 CPU 数不同,`concurrency` 数字会不一样,solo 池里它只是摆设):

```

- *** --- * ---

- ** ---------- .> app:         cel1:0x1f3a3a5ee40
- ** ---------- .> transport:   amqp://tianshiyang:**@62.234.16.180:5672//
- ** ---------- .> results:     redis://:**@62.234.16.180:6379/0
- *** --- * --- .> concurrency: 16 (solo)

[tasks]

[2026-09-19 18:19:54,547: INFO/MainProcess] Connected to amqp://tianshiyang:**@62.234.16.180:5672//
```

## 7 跑起来

命令都在**本讲目录**执行(和 rabbitmq教程 的"仓库根目录"不同,celery 靠 import 找应用):

```
终端 1:  cd "celery教程/01-第一个任务与工程骨架"
         uv run celery -A celery_app worker --pool=solo -l info
终端 2:  cd "celery教程/01-第一个任务与工程骨架"
         uv run python send.py
```

终端 2 的输出:

```
已投递,任务 ID: f6dc0716-cddd-453f-8d55-d19ce9b46e3f
此刻状态: PENDING
等结果……
结果: {'goods_id': 1001, 'compressed': True, 'bytes_saved': 1025024}
最终状态: SUCCESS
```

终端 1(worker)同刻打的日志:

```
[18:20:12: INFO/MainProcess] Task tasks.compress_image[f6dc0716-...] received
[18:20:12: INFO/MainProcess] tasks.compress_image[f6dc0716-...]: 开始压缩商品 1001 的图片,要干 2 秒……
[18:20:14: INFO/MainProcess] tasks.compress_image[f6dc0716-...]: 商品 1001 压缩完成
[18:20:15: INFO/MainProcess] Task tasks.compress_image[f6dc0716-...] succeeded in 2.06s: {'goods_id': 1001, ...}
```

一条任务的一生都在这两块屏幕上:`received` → 你的函数在跑(logger 两行,每行自动带 `任务名[任务ID]:` 前缀,出了事按 ID 串联全链路)→ `succeeded`,耗时和返回值附在后面。

> 说明:终端 2 的脚本结尾**可能**跟一小段红字 `Exception ignored while calling deallocator ... Python is likely shutting down`——这是 redis 客户端在解释器退出时清理订阅连接的已知噪音(结果早已打印完,无害),本课程里见到一律忽略。

**值得做的实验一:worker 不在,消息等它。** 只跑终端 2(send.py 不改),`get(timeout=10)` 十秒后抛 `TimeoutError`——没人干活,等不来。这时去管理台 Queues 页:`cel1` 队列 Ready 数 1。再把 worker 跑起来,看它立刻 `received` → `succeeded`,终端 2 之前超时的调用虽已错过,但 Redis 里结果已就位,重新 `get` 同一个 ID 能拿到(拿法:`AsyncResult("那个ID").get()`,第 2 讲)。**队列还是那个仓库,不是流水的管子**——兔 MQ 第 1 讲的实验,换了框架原样复现。

**值得做的实验二:管理台看 Celery 声明了什么。** Queues 页点开 `cel1` → Bindings:两行——默认交换机(名字空)绑定键 `cel1`,和交换机 `cel1`(direct)绑定键 `cel1`。发布走的是后者:**direct 交换机 + 绑定键全等匹配,第 3 讲的老套路**,只是这回不是你写的,是 Celery 开工时自动声明的。Consumers 一栏能看到 worker 连接,`ack_required: true`——这就是 `task_acks_late=True` 在 broker 侧的证据,第 3 讲拿它做实验。

看完到管理台把 `cel1` 队列删掉(下一轮实验从零开始)。
