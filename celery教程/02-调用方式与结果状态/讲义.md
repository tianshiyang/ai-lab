## 1 apply_async:调用的完全体

```python
compress_image.delay(goods_id=1001, seconds=2)                    # 快捷方式
compress_image.apply_async(kwargs={"goods_id": 1001, "seconds": 2})  # 完全体,不带旋钮时两者等价
compress_image.apply_async(args=[1001], countdown=5)              # 带旋钮就必须用它
```

| 参数 | 类型 | 说明 |
|---|---|---|
| `args` / `kwargs` | 列表 / 字典 | 位置参数 / 关键字参数,内容必须可 json 序列化 |
| `countdown` | 秒数 | **多少秒之后**再执行。相对时间,推荐 |
| `eta` | datetime | **绝对时刻**执行。要传"时区-aware 的 UTC 时间"才不翻车——算时区太容易错,能用 countdown 就别碰 eta |
| `expires` | 秒数 / datetime | 多久没人执行就作废。作废的任务 worker 领到也不跑 |
| `priority` | 0~255 | 插队,要队列开优先级才生效(第 4 讲) |
| `queue` | 队列名 | 临时改投别的队列(第 4 讲) |

`countdown` 是"延时任务"的正解:关单倒计时、付款提醒、注册后发欢迎邮件,全是它。兔 MQ 教程第 6 讲你用 TTL + 死信 + 中转队列拼出来的延迟效果,Celery 里就一个数字。机制上:消息**立刻**投进队列、立刻可被 worker 领走,只是执行时刻写在消息头里——worker 领到先挂进自己的 ETA 计划表,到点才开跑(实验一亲眼验证)。

`expires` 落到 RabbitMQ 上就是你在第 6 讲见过的**单条消息 expiration 属性**——过期的消息 broker 直接丢弃。"拼团 10 分钟内不成团就别再发了"这类"过时不候"的语义用它。

## 2 结果状态机

任务从投递到终局,状态走这条线:

```
PENDING ──► STARTED ──► SUCCESS
   │           │
   │           └─(抛异常,重试中)──► RETRY ──►(再试)──► STARTED …
   └─(抛异常,不重试)───────────────► FAILURE
```

| 状态 | 含义 | 陷阱 |
|---|---|---|
| PENDING | 还没干 | **歧义最大**:在排队、在执行、根本没这个 ID、任务 ignore_result——全显示 PENDING |
| STARTED | worker 已领走开干 | 默认**不产生**,要任务声明 `track_started=True` 才有 |
| RETRY | 失败了,排队等下次重试(第 3 讲) | |
| SUCCESS / FAILURE | 终局 | 结果和异常都存在 backend,可随时查 |
| REVOKED | 被人为撤回(第 7 讲) | |

`AsyncResult` 的读取 API:

| API | 说明 |
|---|---|
| `r.state` | 当前状态字符串 |
| `r.ready()` | 到终局了吗(SUCCESS/FAILURE) |
| `r.get(timeout=10)` | 阻塞拿结果。FAILURE 时**重放异常**(默认 `propagate=True`);`propagate=False` 则拿到异常对象本身,不炸 |
| `r.id` | UUID。结果在 Redis 里的键就是 `celery-task-meta-<ID>` |

**敲黑板:PENDING 不等于"在排队"。** 拿一个编造的 UUID 查状态,也是 PENDING——backend 里查无此档,显示"还没完"。判断任务是否真的存在,得靠任务表或日志,别靠状态机。

## 3 结果的经济学

结果不是免费存的:每条任务干完,backend 都要写一份、留到过期。企业里的第一道选择题就是**这个任务要不要结果**:

| 任务类型 | 要结果吗 | 配置 |
|---|---|---|
| 发短信、发邮件、清缓存 | 不要,发完就忘 | `@app.task(ignore_result=True)` |
| 报表计算、对账、图片处理产物 | 要,调用端要取 | 默认 |
| 只要知道成败,不要返回值 | 折中 | 默认 + 调用端只看 `state` |

三层配套(第 1 讲的"配置三层"又用上了):

| 旋钮 | 层 | 作用 |
|---|---|---|
| `ignore_result=True` | 装饰器 | 这个任务不写结果。之后查它的 AsyncResult,永远是 PENDING(见上面敲黑板) |
| `result_expires=3600` | app.conf | 结果保质期,全局兜底,别让 Redis 堆垃圾 |
| `r.forget()` | 调用端 | 这一份结果读完了,现在就删 |

## 4 企业调用姿势

调用端最常见宿主是 Web 服务(本仓库的 FastAPI 也一样)。**铁律:Web 请求处理里禁止 `.get()` 等任务**——`get` 是阻塞的,等任务等于把 Web 进程挂在那儿,worker 慢一点,HTTP 连接全被拖死,雪崩就是这么来的。

| 场景 | 新手写法(事故) | 企业写法 |
|---|---|---|
| 用户点"生成报表" | `.delay()` 然后 `.get(timeout=60)` | `.delay()` 拿 `r.id` 立刻返回 202 + 任务 ID;前端轮询 `/report/status/<task_id>` |
| 任务完成要通知 | 调用端死等 | 第 6 讲的回调链:`link=` / `chord` |
| 发一条短信 | 等发送结果 | `ignore_result` + 失败靠第 3 讲的重试兜底 |

"把 ID 交给前端轮询"就是状态机最常见的生意:轮询接口里 `AsyncResult(task_id).state` 和 `.result` 各回各的,FAILURE 时 `str(r.result)` 给出异常摘要。

## 5 完整示例

### celery_app.py

和第 1 讲只差项目名和队列名(cel2),完整再敲一遍——每讲独立成工程,练的就是手熟:

```python
"""第 2 讲·Celery 应用:与第 1 讲同款配置,队列换 cel2。"""

import os
from pathlib import Path

from celery import Celery
from dotenv import load_dotenv

load_dotenv(Path(__file__).parents[2] / ".env")

app = Celery(
    "cel2",
    broker=os.environ["RABBITMQ_URL"],
    backend=os.environ["REDIS_URL"],
    include=["tasks"],
)

app.conf.update(
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    timezone="Asia/Shanghai",
    task_default_queue="cel2",
    task_acks_late=True,
    task_reject_on_worker_lost=True,
    worker_prefetch_multiplier=1,
    result_expires=3600,
)
```

### tasks.py

三个任务各演一个知识点:

```python
"""第 2 讲·任务:慢报表(状态机)/必败任务(FAILURE)/发短信(不要结果)。"""

import time

from celery.utils.log import get_task_logger

from celery_app import app

logger = get_task_logger(__name__)


@app.task(track_started=True)     # 例外放装饰器:只有这个任务报告 STARTED
def build_report(report_id: int, seconds: int = 4) -> dict:
    """生成报表:慢,专门用来看状态一步步走"""
    logger.info("开始生成报表 %s,要干 %s 秒", report_id, seconds)
    time.sleep(seconds)
    return {"report_id": report_id, "rows": report_id * 100}


@app.task
def sync_inventory(goods_id: int) -> dict:
    """同步库存:剧本写死第 3 秒翻车,演示 FAILURE"""
    time.sleep(3)
    raise RuntimeError(f"库存服务连接超时(goods_id={goods_id})")


@app.task(ignore_result=True)     # 发完就忘:不写结果
def send_welcome_sms(user_id: int) -> str:
    logger.info("已给用户 %s 发出欢迎短信", user_id)
    return f"sms sent to {user_id}"   # 这个返回值没人收得到,worker 日志里能看到
```

### send.py(countdown + 状态轮询)

```python
"""第 2 讲·调用端:延时投递,亲眼看着状态机走完。

    cd "celery教程/02-调用方式与结果状态"
    uv run python send.py
"""

import time

from tasks import build_report

result = build_report.apply_async(args=[7], kwargs={"seconds": 4}, countdown=5)
print(f"已投递(5 秒后才开始),任务 ID: {result.id}")

for _ in range(15):
    print(f"[{time.strftime('%H:%M:%S')}] 状态: {result.state}")
    if result.ready():
        break
    time.sleep(1)

print(f"结果: {result.get(timeout=10)}")
```

### send_fail.py(失败与"发完就忘")

```python
"""第 2 讲·调用端:必败任务 + ignore_result。

    cd "celery教程/02-调用方式与结果状态"
    uv run python send_fail.py
"""

import time

from celery.result import AsyncResult

from tasks import send_welcome_sms, sync_inventory

# ① 必败任务:get 默认重放异常
bad = sync_inventory.delay(goods_id=2001)
print("① 任务已投递,干 3 秒后必败。等它 FAILURE……")
exc = bad.get(propagate=False, timeout=15)      # 不让它炸,拿到异常对象本身
print(f"   状态: {bad.state},异常: {exc!r}")

# ② ignore_result:发完就忘,状态机查无此档
sms = send_welcome_sms.delay(user_id=88)
print(f"② 短信任务已投递,ID: {sms.id}")
time.sleep(3)                                    # 给 worker 三秒干完
print(f"   状态: {sms.state}   ← 干完了也是 PENDING:没存结果,不是没完成")
```

## 6 跑起来

三个实验,worker 常驻,调用脚本换着跑:

```
终端 1:  cd "celery教程/02-调用方式与结果状态"
         uv run celery -A celery_app worker --pool=solo -l info
终端 2:  cd "celery教程/02-调用方式与结果状态"
         uv run python send.py
```

**实验一:countdown + 状态机全走一遍。** send.py 输出:

```
已投递(5 秒后才开始),任务 ID: 3d9c6a02-9f3d-4b0e-a1b7-1c2b3a4d5e6f
[18:31:02] 状态: PENDING
[18:31:03] 状态: PENDING
[18:31:04] 状态: PENDING
[18:31:05] 状态: PENDING
[18:31:06] 状态: PENDING        ← 倒计时到,worker 开跑(消息早被领走挂着)
[18:31:07] 状态: STARTED        ← track_started=True 的功劳
[18:31:08] 状态: STARTED
[18:31:09] 状态: STARTED
[18:31:10] 状态: STARTED
[18:31:11] 状态: SUCCESS
结果: {'report_id': 7, 'rows': 700}
```

对照 worker 终端:`received` 在投递后**一瞬间**就打出来——消息立刻被领走,worker 把它挂进 ETA 计划表,到点才执行(`inspect scheduled`,第 7 讲,能看到这批"已领未跑"的任务)。两个推论:①倒计时任务**不会卡住** worker,领到它时 Celery 会临时放宽预取额度,后面的普通任务照常干活;②"消息躺在队列里等"只在 worker 不在线时发生——实验三见。

**实验二:失败与"发完就忘"。** 换 send_fail.py:

```
① 任务已投递,干 3 秒后必败。等它 FAILURE……
   状态: FAILURE,异常: RuntimeError('库存服务连接超时(goods_id=2001)')
② 短信任务已投递,ID: 6f2b1c40-....
   状态: PENDING   ← 干完了也是 PENDING:没存结果,不是没完成
```

worker 终端同刻打印 `raised unexpected: RuntimeError(...)`,并附完整 traceback——**异常存了档(FAILURE 的 result 就是它),但消息本身已被确认**,不会像兔 MQ 教程第 2 讲那样重投。失败该怎么救,第 3 讲整章讲。

**实验三:expires 过时不候。** 把 send.py 的投递行改成:

```python
result = build_report.apply_async(args=[7], kwargs={"seconds": 1}, expires=10)
```

并把轮询和 `get` 两段注释掉,只留投递和 print。**先不开 worker**,跑一次:管理台 `cel2` 队列 Ready 数 1;盯着它,10 秒左右归 0——broker 按消息 TTL 把它丢了,正是兔 MQ 第 6 讲的单条 `expiration`。这时再开 worker:什么都不会发生,任务作废,worker 一个 `received` 都不会有。

## 7 速查表

| API / 参数 | 位置 | 作用 |
|---|---|---|
| `apply_async(args=, kwargs=)` | 调用端 | 完全体投递 |
| `countdown=N` | apply_async | N 秒后执行(延时任务的正解) |
| `eta=dt` | apply_async | 绝对时刻执行,时区坑多,少用 |
| `expires=N` | apply_async | 没人执行就作废(= 消息 TTL) |
| `r.state / ready() / get(timeout=)` | 回执 | 状态机读取 |
| `get(propagate=False)` | 回执 | 拿异常对象而不是重放异常 |
| `track_started=True` | 装饰器 | 报告 STARTED(默认关) |
| `ignore_result=True` | 装饰器 | 不写结果,查状态永远 PENDING |
| `result_expires` | app.conf | 结果保质期 |
| `forget()` | 回执 | 这份结果现在就删 |
