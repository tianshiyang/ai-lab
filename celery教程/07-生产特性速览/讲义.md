## 1 时间限制:给任务上闹钟

```python
@app.task(soft_time_limit=8, time_limit=10)
def call_external_api(...):
    ...
```

| 配置 | 行为 |
|---|---|
| `soft_time_limit=8` | 8 秒时在任务里抛 `SoftTimeLimitExceeded`——**可捕获**:except 里清理现场、记日志、走失败分支 |
| `time_limit=10` | 10 秒时**硬杀**执行进程,任务以失败收场,不可捕获 |

也可以在 `app.conf` 里设全局 `task_time_limit` / `task_soft_time_limit`,个别任务在装饰器里覆盖(配置三层的老规矩)。外部调用必须限时,这是铁律:下游卡死,你的 worker 就跟着陪葬。

**Windows 上的实况(实测)**:两个限制都依赖 Unix 信号,`--pool=solo` 的 Windows 开发机上**拦不住**卡死任务——实验一亲眼验证。别慌,Linux prefork(生产环境)上它们是有效的;开发机上把它们当"写在代码里的文档",别指望它救你。

## 2 并发池:worker 里的执行模型

`--pool` 决定 worker 进程里**同时**干几个任务、用什么方式干:

| 池 | 并发单位 | 适合 | 场景 |
|---|---|---|---|
| prefork(默认) | 子进程 | CPU 密集;通用 | **Linux 生产默认**。`--concurrency=4` 开 4 个子进程,兔 MQ 第 2 讲"多工人"的自动化版 |
| solo | 单线程 | 开发、调试 | Windows 开发机唯一顺手的选择(第 1 讲敲黑板) |
| threads | 线程 | IO 密集、中低并发 | 受 Python GIL 限制,CPU 活没戏 |
| gevent | 绿色协程 | **IO 密集、超大并发** | 几百上千路并发调 HTTP API 的通知类 worker:`--pool=gevent --concurrency=200` |
| eventlet | 协程 | 同 gevent | 老项目多,新项目选 gevent |

选型一句话:**CPU 活 prefork,海量 IO 活 gevent,Windows 开发 solo。** 配合第 4 讲的分队列:通知队列的 worker 用 gevent 池、转码队列的用 prefork——队列分了家,池才能各配各的。

## 3 内存保险:治泄漏的土方

有些任务跑着跑着内存就涨(第三方库泄漏、C 扩展不还内存)。让子进程**干满 N 个任务就换一个新人**,泄漏跟着旧进程一起被回收:

```python
app.conf.update(
    worker_max_tasks_per_child=1000,     # 每个子进程干满 1000 个任务就重启
    # worker_max_memory_per_child=300000,  # 或按内存算:KB,超过就重启(solo 池下两者都无意义)
)
```

不是不治泄漏,是**控制泄漏的损失**——排障归监控(下一节),这俩是兜底。

## 4 监控:看清 worker 在干什么

三层,由浅入深:

**① inspect:命令行点名,只读。**

```
uv run celery -A celery_app inspect ping          # 活着吗
uv run celery -A celery_app inspect active        # 正在执行哪些任务
uv run celery -A celery_app inspect scheduled     # 已领未跑(eta/重试)的
uv run celery -A celery_app inspect registered    # 认识哪些任务名
uv run celery -A celery_app inspect stats         # 池、队列、收发计数全景
```

**② 任务事件 + flower:网页看板。** worker 加 `-E` 开任务事件,flower 把事件画成网页:

```
终端 1:  uv run celery -A celery_app worker --pool=solo -l info -E
终端 2:  uv run --with flower celery -A celery_app flower --port=5555
浏览器:  http://localhost:5555
```

`uv run --with flower` 是 uv 的巧劲:临时把 flower 装进这次运行的环境,不污染 pyproject。flower 页面上任务的成功率、耗时、失败明细、worker 状态一屏全有——生产上它常驻一个,值班同学的第一入口。

**③ broker 侧:**管理台 Queues 页看堆积和 Unacked(第 3 讲实验用过),Redis 里 `celery-task-meta-*` 键看结果存档。框架之上,broker 之下,两头都是你的老地盘。

## 5 远程控制:隔着网线下命令

`inspect` 只读,`control` 是动真格(广播给在线 worker):

```
uv run celery -A celery_app control shutdown             # 远程优雅停机
uv run celery -A celery_app control add_consumer c7.extra  # 运行中加守一条队列
uv run celery -A celery_app control revoke <task-id>     # 撤回一个任务
```

`revoke` 的分寸:任务**还没开跑**(排队中、或 countdown 还没到),撤回后到点直接丢弃;已经开跑的,默认撤不回(加 `terminate=True` 强杀进程,连带 acks_late 语义一起破坏,**慎用**)。撤回是紧急刹车,不是流程控制——不该跑的任务,应该在投递前就别投。

## 6 部署:systemd 与优雅停机

Linux 生产的标配是 systemd 守两个服务(worker 和 beat 各一个):

```ini
# /etc/systemd/system/celery-mail.service
[Unit]
Description=celery worker(mail)
After=network.target

[Service]
User=www
WorkingDirectory=/srv/shop
ExecStart=/srv/shop/.venv/bin/celery -A celery_app worker -Q mail --concurrency=4 -l info
Restart=on-failure
KillSignal=SIGTERM            # systemd 停服务发 TERM → warm shutdown,等任务干完(第 3 讲实验二)

[Install]
WantedBy=multi-user.target
```

beat 同款再来一个 `celery-beat.service`(ExecStart 里 `beat`,**只此一份**,第 5 讲敲黑板)。发版流程:部署新代码 → 逐台 `systemctl restart celery-mail@...` ——worker 重启捡起未确认消息接着干,第 3 讲的三件套保证这条流水线不丢活。Docker/K8s 部署同理,只是把 systemd 换成容器的 ENTRYPOINT 和探针。

## 7 完整示例

### celery_app.py

第 2 讲模板,名字换 `cel7`,在 `app.conf.update(...)` 里**追加**两行:

```python
    worker_max_tasks_per_child=1000,
    task_time_limit=60,          # 全局兜底:任何任务超过 60 秒按失败处理
```

### tasks.py

```python
"""第 7 讲·任务:卡死任务(测时间限制)、慢任务(测监控与撤回)。"""

import time

from celery.utils.log import get_task_logger

from celery_app import app

logger = get_task_logger(__name__)


@app.task(soft_time_limit=8, time_limit=10)
def stuck_task(task_no: int) -> str:
    """睡 60 秒:Linux 上 8 秒抛 SoftTimeLimitExceeded、10 秒被硬杀"""
    logger.info("任务 %s 开跑,打算睡 60 秒", task_no)
    time.sleep(60)
    return "never"


@app.task(ignore_result=True)
def slow_probe(seconds: int = 5) -> None:
    """普通慢任务:监控页面上看它跑"""
    logger.info("探针任务开跑,%s 秒", seconds)
    time.sleep(seconds)
```

## 8 跑起来

**实验一:Windows 上时间限制的实况。** 起 worker,投一个卡死任务,另开终端看它卡着:

```
终端 2:  uv run python -c "from tasks import stuck_task; print(stuck_task.delay(1).id)"
终端 3:  uv run celery -A celery_app inspect active
```

`inspect active` 显示 `stuck_task` 已跑超过 10 秒——`time_limit=10` 没拦它(Windows + solo,信号机制缺席,第 1 节说好的实况)。Ctrl+C 结束实验。心里记下:**这条配置的价值在 Linux 生产上兑现**。

**实验二:监控三板斧。** worker 加 `-E` 重启,flower 起来:

```
终端 1:  uv run celery -A celery_app worker --pool=solo -l info -E
终端 2:  uv run --with flower celery -A celery_app flower --port=5555
```

浏览器开 `http://localhost:5555`:Tasks 页有历史、Workers 页有在线名单。投两个 `slow_probe`,趁它跑着回终端敲 `inspect active`——命令行和网页看到的是同一份事实。

**实验三:撤回排队的任务。** worker 保持在线,投一个 30 秒后才开跑的任务并立刻撤回:

```
终端 3:  uv run python -c "from tasks import slow_probe; r = slow_probe.apply_async(args=[5], countdown=30); print(r.id)"
终端 3:  uv run celery -A celery_app control revoke <上面打印的ID>
```

撤回命令立刻回 `-> celery@主机名: OK`,worker 打出 `Tasks flagged as revoked: <ID>`;30 秒倒计时到点,worker 打出 `Discarding revoked task: tasks.slow_probe[那个ID]`——任务到点即弃,`slow_probe` 的日志一行都不会出现(第 2 讲说过:countdown 任务是被领走挂账的,所以弃它发生在到点那一刻)。

## 9 速查表

| 配置 / 命令 | 层 | 作用 |
|---|---|---|
| `soft_time_limit` / `time_limit` | 装饰器或 app.conf | 软限抛异常(可捕获)/ 硬杀(Linux prefork 生效) |
| `--pool=` + `--concurrency=` | 命令行 | prefork / solo / threads / gevent |
| `worker_max_tasks_per_child` | app.conf | 子进程干满 N 个任务换新,治泄漏兜底 |
| `-E` | 命令行 | 开任务事件(flower 要它) |
| `uv run --with flower celery -A celery_app flower` | 命令行 | 监控看板:localhost:5555 |
| `inspect ping/active/scheduled/registered/stats` | 命令行 | 只读点名 |
| `control shutdown / add_consumer / revoke` | 命令行 | 远程下命令;revoke 撤回未开跑的任务(在跑的默认撤不回) |
| systemd `KillSignal=SIGTERM` | 部署 | 优雅停机,warm shutdown |
