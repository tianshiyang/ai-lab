# 第 6 讲 · 工作流 Canvas

## 0 开场:编排也住进后台

前五讲的调用都是"单发"。可真实业务是**流程**:下单成功 → 校验订单 → 扣库存 → 打包;两条通知**并行**发:短信 + 邮件回执;都发完了 → 汇总留档。要是在调用端手写,就是 `.delay()` 一发、轮询中间结果、再发下一个——编排逻辑全糊在调用端,还占着连接干等。

Canvas(画布)是 Celery 的编排层:**把几个任务"签名"拼成链、扇、网,一次性丢给后台,后台自己接力**。三种积木:

```
chain(直线)   A ──► B ──► C            上游的返回值流给下游

group(扇出)   A ──┬──► B1              并行开跑,互不等待
                   ├──► B2
                   └──► B3

chord(扇出+汇总) A ──┬──► B1 ──┐
                   ├──► B2 ──┼──► C(拿 [B1,B2,B3] 的结果列表)
                   └──► B3 ──┘
```

---

## 1 签名 signature:任务的"消息形态"

```python
from tasks import check_order, deduct_stock, send_sms

check_order.s(6001)          # 签名:任务 + 参数,还没投递
send_sms.si(6001)            # 不可变签名:同样,但明确"不接收上游结果"
check_order.s(6001).set(expires=60)   # 还能带投递选项
```

| API | 说明 |
|---|---|
| `task.s(*args, **kwargs)` | 签名。它是**可序列化的**——能存数据库、能当参数传给别的任务、能跨进程传。这就是"编排积木"的底气 |
| `task.si(...)` | immutable 签名:拼进 chain 后**不接**上游返回值,参数就是写死的那些 |
| `.set(队列/优先级/过期...)` | 给这个签名附加 apply_async 选项 |

签名的组合结果(链、组)还是"消息形态",直到你 `()` 或 `.delay()` / `.apply_async()` 才真正投递。

## 2 chain:直线流水

```python
from celery import chain

pipeline = chain(
    check_order.s(order_id),     # 参数在第一环给全
    deduct_stock.s(),            # 后续环节参数留空:等上游的返回值来填
    pack_goods.s(),
)
result = pipeline.apply_async()  # 投递整条链
print(result.get(timeout=30))    # 拿的是最后一环的返回值
```

**数据流**:每一环的 return 就是下一环的第一个位置参数。所以设计 chain 时先设计**穿线数据**(例子:每环都返回 `order_id`,让下一环接得住);返回值要变结构,就让它返回一个 tuple 或 dict,下游照单全收。

| 规矩 | 说明 |
|---|---|
| 中途失败 | 某环 FAILURE,下游默认**不再执行**——订单校验都不过,扣什么库存 |
| 不需要上游结果的环节 | 用 `.si()` 挂进链(比如链尾"通知客服",只认 order_id) |
| 环要小 | 每环都是一次独立的投递/确认,环里别把三分钟的活塞一块,重试的粒度跟着环走 |

## 3 group:并行扇出

```python
from celery import group

jobs = group(send_sms.si(order_id), send_email_receipt.si(order_id))
results = jobs.apply_async()      # 同时投递
print(results.get(timeout=30))    # 等全部,拿到结果列表
```

group 里的任务**互不依赖、同时投递**。注意一个物理事实:canvas 给的是**并行的机会**,真并几路取决于 worker 的总并发——单 worker(solo 单进程)里,group 也就是排队挨个干。下面的实验会开两个 worker,亲眼看并行成真。

## 4 chord:扇出之后收拢

```python
from celery import chord

flow = chord(
    group(send_sms.si(order_id), send_email_receipt.si(order_id)),
)(settle_summary.s())            # 回调:参数 = 扇出全部结果的列表

print(flow.get(timeout=30))       # {"sms": "...", "email": "...", "all_sent": True}
```

`chord(header)(body)`:header 全部 SUCCESS 后,body 被投递,收到**结果列表**(顺序与 header 一致)。订单履约"通知全发完 → 客服留档"、批量报表"全算完 → 合并",全是它。

| 要点 | 说明 |
|---|---|
| backend 有讲究 | chord 的"全部完成"判定靠 backend。**Redis backend 原生支持**;兔 MQ 的 rpc:// backend 不支持,这是企业选 Redis 当结果后端的现实理由之一 |
| header 有人失败 | 回调不会正常执行,整场以失败收场——所以 header 任务要把第 3 讲的重试配硬气,别让偶发抖动炸掉整场编排 |
| 兜底 | 给 chord 挂 `.link_error(...)`,失败走告警分支(下一节 link_error 同款) |

## 5 link / link_error:单任务的成功与失败分支

```python
place_order.apply_async(
    args=[order_id],
    link=notify_ops.s(),           # 成功了:拿返回值去 notify_ops
    link_error=alert_ops.s(),      # 失败了(重试耗尽含在内):拿异常去 alert_ops
)
```

第 3 讲说"FAILURE + 告警",`link_error` 就是挂告警最轻的手法;`link` 则是"成功后的下一步"的单发版。编排里链式失败默认静默(下游不执行),**关键的链要显式挂 link_error**,不然断了都没人吭声。

## 6 脸熟三件

| API | 一句话 |
|---|---|
| `task.starmap([(1,2),(3,4)])` | 一批参数各自调一次(等价 group) |
| `task.chunks(可迭代, 100)` | 把一大批数据切成 100 一块,分几个任务干 |
| `group(...).sk(...)` / `chain(...).sk(...)` | 整个编排再当签名嵌进更大的编排(套娃) |

## 7 完整示例

业务:订单 6001 履约——直线链(校验→扣库存→打包)+ 扇出通知(短信、邮件回执)+ 汇总留档。

### celery_app.py

照第 2 讲的模板,把 `"cel2"` 换 `"cel6"`(项目名和 `task_default_queue` 都换),其余一字不差。

### tasks.py

```python
"""第 6 讲·任务:订单履约流水线的各环节。"""

import time

from celery.utils.log import get_task_logger

from celery_app import app

logger = get_task_logger(__name__)


# —— chain 直线:每环返回 order_id,穿线数据 ——
@app.task
def check_order(order_id: int) -> int:
    time.sleep(1)
    logger.info("订单 %s 校验通过", order_id)
    return order_id


@app.task
def deduct_stock(order_id: int) -> int:
    time.sleep(1)
    logger.info("订单 %s 库存已扣", order_id)
    return order_id


@app.task
def pack_goods(order_id: int) -> dict:
    time.sleep(1)
    logger.info("订单 %s 已打包", order_id)
    return {"order_id": order_id, "box": f"BOX-{order_id}"}


# —— group 扇出:互不依赖,各睡 2 秒 ——
@app.task
def send_sms(order_id: int) -> str:
    time.sleep(2)
    logger.info("订单 %s 短信已发", order_id)
    return f"sms:{order_id}"


@app.task
def send_email_receipt(order_id: int) -> str:
    time.sleep(2)
    logger.info("订单 %s 邮件回执已发", order_id)
    return f"email:{order_id}"


# —— chord 回调:收拢全部通知结果 ——
@app.task
def settle_summary(results: list) -> dict:
    logger.info("全部通知发完,留档:%s", results)
    return {"notifications": results, "all_sent": len(results) == 2}
```

### flow.py(编排端)

```python
"""第 6 讲·编排端:一条链、一场扇出收拢,外加并行计时对照。

    cd "celery教程/06-工作流Canvas"
    uv run python flow.py
"""

import time

from celery import chain, chord, group

from tasks import (
    check_order,
    deduct_stock,
    pack_goods,
    send_email_receipt,
    send_sms,
    settle_summary,
)

ORDER = 6001

# ① chain:直线流水,get 拿链尾结果
t0 = time.time()
pipeline = chain(check_order.s(ORDER), deduct_stock.s(), pack_goods.s())
print(f"① 链尾结果: {pipeline.apply_async().get(timeout=60)}")
print(f"   链耗时 {time.time() - t0:.1f} 秒(三环各睡 1 秒)")

# ② 对照:两条通知串行发 vs group 并行发
t0 = time.time()
send_sms.apply_async(args=[ORDER]).get(timeout=30)             # 串行:发完一条,再发下一条
send_email_receipt.apply_async(args=[ORDER]).get(timeout=30)
serial_secs = time.time() - t0

t0 = time.time()
group(send_sms.si(ORDER), send_email_receipt.si(ORDER)).apply_async().get(timeout=30)
parallel_secs = time.time() - t0
print(f"② 串行 {serial_secs:.1f} 秒 / 并行 {parallel_secs:.1f} 秒(并行省多少,看 worker 开了几个)")

# ③ chord:通知全发完 → 汇总留档
t0 = time.time()
flow = chord(group(send_sms.si(ORDER), send_email_receipt.si(ORDER)))(settle_summary.s())
print(f"③ 汇总结果: {flow.get(timeout=60)}")
print(f"   耗时 {time.time() - t0:.1f} 秒")
```

## 8 跑起来

**实验一:单 worker,链与收拢。** 开一个 worker,跑 flow.py:

```
① 链尾结果: {'order_id': 6001, 'box': 'BOX-6001'}
   链耗时 3.0 秒(三环各睡 1 秒)
② 串行 4.1 秒 / 并行 4.1 秒(并行省多少,看 worker 开了几个)
③ 汇总结果: {'notifications': ['sms:6001', 'email:6001'], 'all_sent': True}
   耗时 4.0 秒
```

串行和并行**一样慢**——solo 单进程,group 的两条通知还是排着队干的。worker 终端的日志顺序看得清楚:`send_sms received → send_sms succeeded → send_email received → ...`,一个进程里没有"同时"。

**实验二:开两个 worker,并行成真。** 再开一个终端,**原样再跑一份 worker 命令**(celery 允许多 worker 抢同一队列,兔 MQ 第 2 讲的竞争消费),重跑 flow.py:

```
② 串行 4.1 秒 / 并行 2.2 秒(并行省多少,看 worker 开了几个)
```

两条通知分到两个 worker,2 秒出头同时干完。chord 那步也从 4 秒变 2 秒。**canvas 只负责"可以并行",并几路由部署决定**——这话反过来就是第 4 讲的扩容逻辑:哪里慢,加哪个队列的 worker。

worker 日志里还能看到 chord 的机关:两条通知分别 `succeeded` 后,**`settle_summary` 才被投递**(`received`)——判定"全部完成"的那一跳发生在 backend(Redis)侧,这就是第 4 节说"chord 依赖 backend"的具体意思。

## 9 速查表

| API | 作用 |
|---|---|
| `task.s(...) / .si(...)` | 签名 / 不可变签名(编排积木) |
| `chain(a.s(), b.s(), ...)` | 直线;上游 return → 下游第一参数;`.get()` 拿链尾 |
| `group(a.s(), b.s())` | 扇出并行;`.get()` 拿结果列表 |
| `chord(group(...))(callback.s())` | 扇出全 SUCCESS → 回调拿结果列表 |
| `apply_async(link=..., link_error=...)` | 成功 / 失败分支 |
| `starmap` / `chunks` / `.sk(...)` | 批处理 / 分块 / 编排套娃(脸熟) |
