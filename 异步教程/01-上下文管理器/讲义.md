# 第 1 讲 · 上下文管理器——with 协议与 contextlib 全家

> 本讲对应官方文档:[with 语句](https://docs.python.org/zh-cn/3/reference/compound_stmts.html#the-with-statement)、[contextlib](https://docs.python.org/zh-cn/3/library/contextlib.html)。每段代码下面就是真实执行结果,不用自己跑;想跑的话每段都是独立可复制的。

## 0 为什么需要它

后面四讲的一切资源——数据库连接、会话、锁、任务组——都靠 with 保证"**不管块里发生什么,收尾一定执行**":

```
   with 管家:
        进门 __enter__:申请资源
        ……业务代码……            ← 这里随时可能炸
        出门 __exit__:释放资源    ← 炸了也照样走到这
```

不用 try/finally 手写的原因:finally 要在使用点复制一遍,with 把"进门出门"封装在**资源自己身上**。这就是工作项目 `get_db_session()` 能做到"service 层禁止出现 commit/rollback"的地基(第 5 讲拼全图)。

本讲 API 一览:

| API | 作用一句话 |
|---|---|
| `__enter__` / `__exit__` | with 协议本体:进门拿资源、出门收尾 |
| `@contextmanager` | 把生成器函数变成上下文管理器 |
| `__aenter__` / `__aexit__` + `async with` | 协程版协议 |
| `@asynccontextmanager` | 协程版装饰器(FastAPI lifespan 就用它) |
| `contextlib.closing(x)` | 给"有 close 没 `__exit__`"的对象补管家 |
| `contextlib.suppress(E)` | 吞掉指定异常 |
| `contextlib.ExitStack` | 动态批量管理一堆管家 |

## 1 `__enter__` / `__exit__`:with 协议本体

```
__enter__(self)                → 任何值,交给 as
__exit__(self, exc_type, exc_value, traceback) → True = 吞异常;False/None = 继续抛
```

with 语句的等价展开(机关就一行 `if not mgr.__exit__(...): raise`):

```python
mgr = Door()
mgr.__enter__()                          # 进门:as x 拿到的就是它的返回值
try:
    ...                                  # with 块里的所有代码
except BaseException as e:               # 块里炸了
    if not mgr.__exit__(type(e), e, e.__traceback__):
        raise                            # __exit__ 返回 False/None → 异常继续往上抛
else:                                    # 块里平安
    mgr.__exit__(None, None, None)       # 三个参数全 None = "没事,例行出门"
```

**`__exit__` 的返回值是一次投票**:True 表示"这事我处理了,别再抛";False/None(默认)表示"我没处理,继续抛"。魔术方法从来不用手动调——**你定义它,with 替你调**。这也是"协议"思想:with 不查继承链,只看有没有这两个方法(`for` 认 `__iter__`/`__next__`、`async with` 认 `__aenter__`/`__aexit__`,同一个思路)。

最小实现:

```python
class Door:
    def __enter__(self):
        print("进门")
        return self

    def __exit__(self, exc_type, exc, tb):
        print(f"出门:exc_type={exc_type}, exc={exc}")
        return False


with Door():
    print("块里干活")
```

```
进门
块里干活
出门:exc_type=None, exc=None
```

块里炸了,`__exit__` 照样被调,三个参数带着异常信息;`return False` 让异常继续往上抛:

```python
class Door:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):
        print(f"出门:接住了 {exc_type.__name__}: {exc}")
        return False


try:
    with Door():
        raise ValueError("业务炸了")
except ValueError as e:
    print("外面接到:", e)
```

```
出门:接住了 ValueError: 业务炸了
外面接到: 业务炸了
```

`return True` 则吞掉异常——**99% 的场景是 bug**,吞之前必须想清楚上层还知不知道出了事:

```python
class Door:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):
        print(f"出门:接住了 {exc_type.__name__},我说'我处理了'")
        return True


with Door():
    raise ValueError("这个异常消失了")
print("外面毫无感知,继续跑")
```

```
出门:接住了 ValueError,我说'我处理了'
外面毫无感知,继续跑
```

## 2 `@contextlib.contextmanager`:生成器函数变管家

```
@contextlib.contextmanager
def 管家函数(参数):
    进门代码            # ← 相当于 __enter__
    try:
        yield 值        # ← yield 出来的就是 as 拿到的;with 块的代码在这里执行
    finally:
        出门代码        # ← 相当于 __exit__
```

装饰后,调用这个函数得到的不再是生成器,而是一个**替你实现了 `__enter__`/`__exit__` 的对象**。规则:块里炸了,异常会被 throw 进生成器、砸在 `yield` 那一行——在你的函数体看来,异常就像从 yield 里冒出来,普通 `try/except` 就能接。

```python
from contextlib import contextmanager


@contextmanager
def db_connection(name):
    print(f"连接 {name} 建立了")
    try:
        yield name
    finally:
        print(f"连接 {name} 关闭了")


with db_connection("订单库") as conn:
    print(f"用 {conn} 干活")
```

```
连接 订单库 建立了
用 订单库 干活
连接 订单库 关闭了
```

块里炸了,照样关连接、异常照样往外抛:

```python
from contextlib import contextmanager


@contextmanager
def db_connection(name):
    print(f"连接 {name} 建立了")
    try:
        yield name
    finally:
        print(f"连接 {name} 关闭了")


try:
    with db_connection("订单库") as conn:
        raise RuntimeError("查询失败")
except RuntimeError as e:
    print("外面接到:", e)
```

```
连接 订单库 建立了
连接 订单库 关闭了
外面接到: 查询失败
```

**装饰器版的"吞异常"开关:接住后不再抛。** 类版看 `__exit__` 的返回值,装饰器版看"你接住之后抛不抛"——接住不抛,生成器正常结束,with 就认为异常被消化了:

```python
from contextlib import contextmanager


@contextmanager
def swallow():
    try:
        yield
    except ValueError as e:
        print(f"内部接住 {e},没有再抛 → 生成器正常结束")


with swallow():
    raise ValueError("这个异常消失了")
print("外面毫无感知,继续跑")
```

```
内部接住 这个异常消失了,没有再抛 → 生成器正常结束
外面毫无感知,继续跑
```

接住又 `raise` 抛回去(记录日志再抛的惯用法),外面就能接到:

```python
from contextlib import contextmanager


@contextmanager
def log_and_reraise():
    try:
        yield
    except ValueError as e:
        print(f"内部接住 {e},抛回去")
        raise


try:
    with log_and_reraise():
        raise ValueError("业务炸了")
except ValueError as e:
    print("外面接到:", e)
```

```
内部接住 业务炸了,抛回去
外面接到: 业务炸了
```

官网点名的限制:**生成器必须恰好 yield 一次**。yield 两次,with 块结束时生成器还没停,直接 `RuntimeError`:

```python
from contextlib import contextmanager


@contextmanager
def bad():
    yield 1
    yield 2


with bad() as x:
    print(x)
```

```
1
Traceback (most recent call last):
  ...
RuntimeError: generator didn't stop
```

| | 类版 `__enter__`/`__exit__` | 装饰器版 `@contextmanager` |
|---|---|---|
| 适合 | 有状态、要复用的复杂管家 | 一进一出的小管家,十行以内 |
| 记法 | 两个魔术方法 | **yield 之前 = `__enter__`,yield 之后 = `__exit__`** |
| 吞异常开关 | `__exit__` 返回 True | 接住 yield 冒出的异常后不再抛 |

## 3 `async with`:`__aenter__` / `__aexit__`

```
__aenter__(self)                → as 拿到的值(协程,需 await)
__aexit__(self, exc_type, exc_value, tb) → True 吞 / False·None 抛(协程)
```

协程版协议,规则和同步版完全一样,只是进门出门都可以 `await`。同步版对象**不能**用于 `async with`(两套协议互不通用,报错信息会提示 `missed __aexit__ method`)。

日常几乎不手写类版,统一用装饰器:

```
@contextlib.asynccontextmanager
async def 管家函数():
    进门(可 await)
    try:
        yield 值
    finally:
        出门(可 await)
```

```python
import asyncio
from contextlib import asynccontextmanager


@asynccontextmanager
async def async_door():
    print("异步进门(可以 await)")
    await asyncio.sleep(0.1)
    try:
        yield
    finally:
        print("异步出门")


async def main():
    async with async_door():
        print("块里干活")


asyncio.run(main())
```

```
异步进门(可以 await)
块里干活
异步出门
```

第 5 讲的 FastAPI `lifespan` 和 yield 依赖,全是这一个装饰器的企业用法。

## 4 contextlib 工具箱

### `contextlib.closing(thing)`

进块把 thing 原样给你,出块调 `thing.close()`。给"有 close 方法但没实现 `__exit__`"的对象补一个管家:

```python
from contextlib import closing


class Conn:
    def close(self):
        print("close() 被调用了")


with closing(Conn()) as c:
    print("用连接干活:", type(c).__name__)
```

```
用连接干活: Conn
close() 被调用了
```

### `contextlib.suppress(*exceptions)`

进块期间,指定的异常**就当没发生过**——唯一理直气壮的"吞",因为你把要吞的类型写在了明面上:

```python
from contextlib import suppress

with suppress(FileNotFoundError):
    open("不存在的文件.txt")
print("没报错,继续跑")
```

```
没报错,继续跑
```

### `contextlib.ExitStack`

要开的资源数量不定(循环里开文件、按条件开连接),没法逐个写 with 时,用栈统一管理;出块按**逆序**全部收尾:

```python
from contextlib import ExitStack, closing


class Conn:
    def __init__(self, name):
        self.name = name

    def close(self):
        print(f"{self.name} 关闭")


with ExitStack() as stack:
    conns = [stack.enter_context(closing(Conn(f"连接{i}"))) for i in range(3)]
    print("开了", len(conns), "个")
print("出块后:全部已按逆序关闭")
```

```
开了 3 个
连接2 关闭
连接1 关闭
连接0 关闭
出块后:全部已按逆序关闭
```

另有 `AsyncExitStack`(异步版)和 `nullcontext`(啥也不管的占位管家,用于"有时有资源有时没有"的参数),用到再查。`AbstractContextManager` 是可选的体面基类:继承它、只写 `__enter__`,`__exit__` 有默认实现(不吞异常)——不继承也完全合法,协议只认方法。

## 5 真实世界:数据库的事务管家

SQLAlchemy 的 `engine.begin()` 就是一个 async 管家:**块里平安 → 出块提交;块里炸了 → 出块回滚**。第三段是工作项目 `get_db_session()` 的骨架:

```python
@asynccontextmanager
async def session_scope():
    session = Session()
    try:
        yield session
        await session.commit()
        print("→ 自动提交了")
    except Exception:
        await session.rollback()
        print("→ 自动回滚了")
        raise
    finally:
        await session.close()


# 用法一:async with engine.begin() —— 平安路径
async with engine.begin() as conn:
    await conn.execute(User.__table__.insert(), [{"name": "张三"}, {"name": "李四"}])
print("第一幕后:用户数", await count_users())

# 用法二:出事路径,自动回滚
try:
    async with engine.begin() as conn:
        await conn.execute(User.__table__.insert(), [{"name": "王五"}])
        raise RuntimeError("插到一半炸了")
except RuntimeError as e:
    print("外面接到:", e)
print("第二幕后:用户数", await count_users(), "(王五没进去)")

# 用法三:手搓 session_scope(工作项目同款骨架)
async with session_scope() as session:
    session.add(User(name="赵六"))
```

```
第一幕后:用户数 2
外面接到: 插到一半炸了
第二幕后:用户数 2 (王五没进去)
→ 自动提交了
→ 自动回滚了
外面接到: 业务失败
第三幕后:用户数 3 (只有赵六进来了)
```

(完整可跑脚本涉及建表和 .env,骨架如上;三段结构是模板,背下来:`yield 借出 → commit / rollback + raise → close`。)

## 6 速查表

| 写法 | 作用 |
|---|---|
| `with obj as x:` | 进门拿 x,出门自动收拾,异常默认继续抛 |
| `__exit__` 返回 True | 吞异常(99% 是 bug) |
| `@contextmanager` + 一次 yield | 函数式管家;接住不抛 = 吞 |
| `async with` / `@asynccontextmanager` | 协程版,进门出门可 await |
| `closing(x)` / `suppress(E)` / `ExitStack()` | 补管家 / 明面吞异常 / 批量管家 |
