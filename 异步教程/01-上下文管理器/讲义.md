# 第 1 讲 · 上下文管理器——资源的安全边界

## 0 模型

为什么教程从 with 讲起:后面四讲的一切资源——数据库连接、会话、锁、任务组——全靠它保证"**不管中间发生什么,收尾一定执行**":

```
   with 管家:
        ┌────────────────────────┐
        │ 进门 __enter__:申请资源  │
        │  ……业务代码……           │ ← 这里随时可能炸
        │ 出门 __exit__:释放资源   │ ← 炸了也照样走到这
        └────────────────────────┘
        异常继续往上抛(默认),资源已经收好
```

| 概念 | 一句话 |
|---|---|
| 上下文管理器 | 实现了 `__enter__`/`__exit__` 的对象,with 语句的"管家" |
| `__exit__` 的三个参数 | 异常类型、异常对象、调用栈——平安无事时全是 None |
| `@contextmanager` | 把"进门/yield/出门"拍平成一个函数的装饰器 |
| `async with` | 协程版管家:`__aenter__`/`__aexit__`,全程可 await |

为什么不用 try/finally 手写?能写,但每个使用点都要复制一遍 finally;with 把"进门出门"封装在**资源自己身上**,使用点只剩 `async with Xxx() as x:` 一行——这就是工作项目里 `get_db_session()` 能做到"service 层禁止出现 commit/rollback"的地基(第 5 讲拼全图)。

## 1 敲代码:`with_basics.py`(同步版三招 + 一个反面教材)

```python
"""同步上下文管理器:类版、装饰器版,以及一个会吞异常的反面教材。"""

import time
from contextlib import contextmanager


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Timer:
    """类版:__enter__ 进门,__exit__ 出门,中间出事也照样出门。"""

    def __enter__(self):
        self.start = time.monotonic()
        log("进门:开始计时")
        return self

    def __exit__(self, exc_type, exc, tb):
        cost = time.monotonic() - self.start
        log(f"出门:耗时 {cost:.2f} 秒(中途{'出了事:' + str(exc) if exc else '平安'})")
        return False  # 不吞异常,该抛照抛


@contextmanager
def db_connection(name: str):
    """装饰器版:yield 前是进门,yield 后是出门——两段式拍平成一个函数。"""
    log(f"连接 {name} 建立了")
    try:
        yield name
    finally:
        log(f"连接 {name} 关闭了(finally 保证)")


@contextmanager
def swallow_all():
    """反面教材:把 yield 冒出来的异常接住不还,外面毫无感知。"""
    try:
        yield
    except Exception as e:  # noqa: BLE001 —— 故意裸抓,这是反面教材
        log(f"我把 {e} 吞了,外面啥也不知道")
        return True  # 类版协议里 return True 才是开关;装饰器版里起作用的是"接住后没再抛",见 §2 加餐


if __name__ == "__main__":
    log("=== 第一幕:Timer 类版,平安出门 ===")
    with Timer():
        time.sleep(0.5)

    log("=== 第二幕:中途抛异常,门还是出了,异常照常往上抛 ===")
    try:
        with Timer():
            time.sleep(0.2)
            raise RuntimeError("业务炸了")
    except RuntimeError as e:
        log(f"外面接到了:{e}")

    log("=== 第三幕:contextmanager 装饰器版,异常也关连接 ===")
    try:
        with db_connection("订单库") as conn:
            log(f"拿到连接 {conn},干活")
            raise RuntimeError("查询失败")
    except RuntimeError as e:
        log(f"外面接到了:{e}")

    log("=== 第四幕:吞异常的反面教材,外面毫无感知 ===")
    with swallow_all():
        raise RuntimeError("这个异常消失了")
    log("程序若无其事地走到了这里——bug 从此无迹可寻")
```

两个类的分工:

| | 类版 `__enter__`/`__exit__` | 装饰器版 `@contextmanager` |
|---|---|---|
| 适合 | 有状态、要复用的复杂管家 | 一进一出的小管家,十行以内 |
| 记法 | 两个魔术方法 | **yield 之前 = `__enter__`,yield 之后 = `__exit__`** |
| 坑 | 随手 `return True` 会吞异常 | yield 处就是业务代码的执行点,异常从这里"注入"进来 |

**敲黑板:`__exit__` 返回 True = 吞异常,99% 的场景都是 bug。** 默认返回 False/None,让异常继续抛;确要吞(比如"连接池重试失败可忽略"),必须想清楚吞掉后上层还知不知道出了事。另一个常见坑:在 `__exit__` 里又抛新异常,会**顶替**原异常——原异常进了 `__context__`,日志变得难读。

## 2 加餐:把 with 拆开看——魔术方法到底怎么被调用

魔术方法(dunder)从来不用你手动调用:**你定义它,Python 在特定语法里替你调**。`with 管家:` 的完整语义,等价于下面这段手动展开:

```python
mgr = Timer()
mgr.__enter__()                          # 进门:as x 拿到的就是它的返回值
try:
    ...                                  # with 块里的所有代码
except BaseException as e:               # 块里炸了
    if not mgr.__exit__(type(e), e, e.__traceback__):
        raise                            # __exit__ 返回 False/None → 异常继续往上抛
else:                                    # 块里平安
    mgr.__exit__(None, None, None)       # 三个参数全 None = "没事,例行出门"
```

机关就一行:`if not mgr.__exit__(...): raise`。**`__exit__` 的返回值是一次投票**:

| `__exit__` 返回 | with 的反应 | 效果 |
|---|---|---|
| `False` / `None`(默认) | 执行 `raise` | 异常继续往上抛(正常世界) |
| `True` | 不 raise | 异常就地消失(吞) |

`__exit__` 的三个参数,平安时全是 `None`,出事时分别是异常类型、异常对象、调用栈——Timer 里那句 `f"中途{'出了事:' + str(exc) if exc else '平安'}"` 就是在读它。**`__exit__` 永远会被调用**(平安走 else,出事走 except),这就是"资源一定被释放"的根基。

`@contextmanager` 则是这套协议的翻译器:装饰后你拿到的对象**替你实现了** `__enter__`/`__exit__`,你的生成器函数体是它们的剧本——

- `__enter__` = 把生成器跑到 `yield` 为止(yield 出来的值 = `as x`)
- `__exit__` = 块里炸了的话,把异常 **throw 进生成器,精准砸在 `yield` 那一行**——在你的函数体看来,异常就像从 yield 语句里冒出来,普通 `try/except` 就能接住

第四幕 `swallow_all` 的完整链条:

```
with 块里 raise RuntimeError("这个异常消失了")
 → Python 调管家的 __exit__(RuntimeError, e, 调用栈)
 → 装饰器实现的 __exit__ 把 e throw 进生成器,砸在 yield 那行
 → 你写的 except Exception 接住了,没有再抛 → 生成器正常结束
 → 装饰器的 __exit__ 判定"生成器消化了异常" → 返回 True
 → with 看到 True → 不 raise → 外面毫无感知,程序继续走
```

两个版本的开关位置**不同**,别混:

| | 类版 | 装饰器版 `@contextmanager` |
|---|---|---|
| 吞异常的开关 | `__exit__` 的**返回值**(True) | **接住异常后不再抛**(生成器正常结束) |
| `return True` 的作用 | 就是开关本身 | 只是声明意图——实测接住后不 return、甚至 return False,照样吞;生成器 return 的值根本没被读 |

**值得做的实验**:①把 `swallow_all` 的 `except Exception` 整块删掉(只留 `yield`)再跑第四幕——没人接,异常原样冒出去,外面接到;②把 `except` 里加一行 `raise`(接住又抛回去)——外面也接到。对照体会"接住后抛不抛"才是装饰器版的生死线。

## 4 async 版:管数据库

`async with` + `@asynccontextmanager`,资源生命周期一模一样,只是进门出门都可以 await。数据库事务是最好的教材——`engine.begin()` 这个管家承诺:**块里平安 → 提交;块里炸了 → 回滚**。

`db_transact.py`:

```python
"""async with 管数据库:engine.begin() 的自动提交/回滚,再手搓一个工作项目同款。"""

import asyncio
import os
import time
from contextlib import asynccontextmanager
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, func, select
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "async01_user"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(20))


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def count_users() -> int:
    async with Session() as session:
        return (await session.execute(select(func.count(User.id)))).scalar_one()


@asynccontextmanager
async def session_scope():
    """工作项目同款:成功自动 commit,异常自动 rollback,结束必 close。"""
    session = Session()
    try:
        yield session
        await session.commit()
        log("自动提交了")
    except Exception:
        await session.rollback()
        log("自动回滚了")
        raise
    finally:
        await session.close()


async def main() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(User))

    log("=== 第一幕:async with engine.begin() —— 平安干完自动提交 ===")
    async with engine.begin() as conn:
        await conn.execute(
            User.__table__.insert(), [{"name": "张三"}, {"name": "李四"}]
        )
    log(f"第一幕后:用户数 {await count_users()}")

    log("=== 第二幕:块里抛异常 —— 自动回滚,一条不落 ===")
    try:
        async with engine.begin() as conn:
            await conn.execute(User.__table__.insert(), [{"name": "王五"}])
            raise RuntimeError("插到一半炸了")
    except RuntimeError as e:
        log(f"外面接到了:{e}")
    log(f"第二幕后:用户数 {await count_users()}(王五没进去)")

    log("=== 第三幕:手搓 session_scope,工作项目 get_db_session 的骨架 ===")
    async with session_scope() as session:
        session.add(User(name="赵六"))
    try:
        async with session_scope() as session:
            session.add(User(name="钱七"))
            raise RuntimeError("业务失败")
    except RuntimeError as e:
        log(f"外面接到了:{e}")
    log(f"第三幕后:用户数 {await count_users()}(只有赵六进来了)")
    await engine.dispose()


asyncio.run(main())
```

```

```

[11:08:18] 第一幕后:用户数 2
[11:08:18] === 第二幕:块里抛异常 —— 自动回滚,一条不落 ===
[11:08:18] 外面接到了:插到一半炸了

第三幕的 `session_scope` 就是工作项目 `db/session.py` 里 `get_db_session()` 的骨架:**yield 依赖 = "借出资源 + 管好收尾"**。`except` 里 rollback 之后记得 `raise`——回滚是你的职责,异常还是要还给调用方(别学第四幕的反面教材)。

`session_scope` 的三段结构是模板,背下来:

```python
try:
    yield session          # 借出去,业务在这里跑
    await session.commit() # 平安收尾:提交
except Exception:
    await session.rollback()  # 出事收尾:回滚
    raise                     # 异常继续往上抛
finally:
    await session.close()     # 无论如何:关掉
```

## 5 常见的内置管家

| 管家 | 收尾动作 | 用途 |
|---|---|---|
| `open(path)` | 关文件 | 天天用 |
| `threading.Lock()` | 解锁 | 第 4 讲主角 |
| `asyncio.TaskGroup()` | 等全部子任务结束/取消 | 第 3 讲主角 |
| `engine.begin()` | 提交/回滚 | 本讲 |
| `contextlib.closing(obj)` | 调 `obj.close()` | 给"有 close 没 `__exit__`"的对象补管家 |
| `contextlib.suppress(E)` | 吞指定异常 | **唯一**理直气壮的"吞" |
| `contextlib.ExitStack()` | 动态批量管家 | 条件性开多个资源的场合 |

## 7 速查表

| 写法 | 作用 |
|---|---|
| `with obj as x:` | 进门拿 x,出门自动收拾 |
| `@contextmanager` + `yield` | 函数式写管家 |
| `async with obj as x:` | 协程版,进门出门可 await |
| `@asynccontextmanager` | 协程版装饰器管家 |
| `closing(x)` / `suppress(E)` / `ExitStack()` | 三件套小工具 |
