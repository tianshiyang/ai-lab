# 第 5 讲 · 企业场景——从 FastAPI 到 Celery

## 0 模型

前四讲的零件,拼成工作项目(dz-clouddisk 一类)的全套骨架:

```
 uvicorn 启动进程
    │
    ▼
 lifespan(第 1 讲:async 上下文管理器)──── 建连接池 / 关停释放
    │
    ▼
 事件循环 + 若干协程(第 2、3 讲)
    │  每个请求:
    ▼
 FastAPI 路由(async def)
    │  Depends(get_db_session)  ← yield 依赖(第 1 讲):借出会话,管好收尾
    ▼
 service 层(业务逻辑,FOR UPDATE / version ← 锁教程)
    │
    ▼
 响应返回,依赖收尾:成功 commit / 异常 rollback / 必 close

 旁边:Celery worker 进程(第 4 讲:CPU/慢活的归宿,常驻事件循环跑任务)
```

四讲各就各位:**上下文管理器是地基(资源生命周期),协程是主干(请求并发),编排是缰绳(下游并发),线程/进程是外挂(阻塞桥接 + 重活外包)**。这一讲用一个能跑的迷你转账 API 把它们全部钉在一起。

## 1 敲代码:`mini_api.py`

一个文件浓缩工作项目的全部骨架——lifespan、yield 依赖、`Annotated` 类型别名、Query 传参、悲观锁防丢失更新、按 id 排序防死锁:

```python
"""迷你转账 API:工作项目全套骨架的浓缩版——lifespan、请求级会话依赖、悲观锁。"""

import asyncio
import os
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager
from pathlib import Path
from typing import Annotated

import uvicorn
from dotenv import load_dotenv
from fastapi import Depends, FastAPI, Query
from sqlalchemy import String, delete, select
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


class Base(DeclarativeBase):
    pass


class Account(Base):
    __tablename__ = "async05_account"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(20))
    balance: Mapped[int]


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


@asynccontextmanager
async def lifespan(app: FastAPI):
    """进程级资源:启动时建表,关停时释放连接池。"""
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    yield
    await engine.dispose()


app = FastAPI(lifespan=lifespan)


async def get_db_session() -> AsyncIterator[AsyncSession]:
    """请求级会话:成功自动 commit,异常自动 rollback,结束必 close(yield 依赖)。"""
    session = Session()
    try:
        yield session
        await session.commit()
    except Exception:
        await session.rollback()
        raise
    finally:
        await session.close()


DbSession = Annotated[AsyncSession, Depends(get_db_session)]


@app.post("/reset")
async def reset(session: DbSession) -> dict:
    """两账号各重置为 1000。"""
    await session.execute(delete(Account))
    session.add_all(
        [
            Account(id=1, name="阿花", balance=1000),
            Account(id=2, name="阿草", balance=1000),
        ]
    )
    return {"msg": "ok:两账号各 1000,总额 2000"}


@app.get("/balance")
async def balance(session: DbSession) -> dict:
    """查所有账号余额和总额。"""
    rows = (
        await session.execute(
            select(Account.id, Account.name, Account.balance).order_by(Account.id)
        )
    ).all()
    return {
        "accounts": [{"id": r.id, "name": r.name, "balance": r.balance} for r in rows],
        "total": sum(r.balance for r in rows),
    }


@app.post("/transfer")
async def transfer(
    session: DbSession,
    from_id: Annotated[int, Query(description="转出账号")] = 1,
    to_id: Annotated[int, Query(description="转入账号")] = 2,
    amount: Annotated[int, Query(description="金额")] = 100,
) -> dict:
    """正确版:两行按 id 排序后 FOR UPDATE,对向转账也不会死锁。"""
    stmt = (
        select(Account)
        .where(Account.id.in_([from_id, to_id]))
        .order_by(Account.id)
        .with_for_update()
    )
    accounts = {a.id: a for a in (await session.execute(stmt)).scalars()}
    if from_id not in accounts or to_id not in accounts:
        return {"msg": "账号不存在"}
    if accounts[from_id].balance < amount:
        return {"msg": "余额不足"}
    await asyncio.sleep(0.5)  # 拉长持锁窗口,方便观察并发
    accounts[from_id].balance -= amount
    accounts[to_id].balance += amount
    return {"msg": f"{from_id} -> {to_id} 转 {amount} 成功"}


@app.post("/transfer-naive")
async def transfer_naive(
    session: DbSession,
    from_id: Annotated[int, Query(description="转出账号")] = 1,
    to_id: Annotated[int, Query(description="转入账号")] = 2,
    amount: Annotated[int, Query(description="金额")] = 100,
) -> dict:
    """错误示范:先读、再睡、再写,丢失更新原样搬进 API。"""
    rows = (
        await session.execute(select(Account).where(Account.id.in_([from_id, to_id])))
    ).scalars()
    accounts = {a.id: a for a in rows}
    await asyncio.sleep(0.5)
    accounts[from_id].balance -= amount
    accounts[to_id].balance += amount
    return {"msg": f"{from_id} -> {to_id} 转 {amount} 成功(其实未必)"}


if __name__ == "__main__":
    uvicorn.run(app, host="127.0.0.1", port=8010)
```

骨架逐件对号入座:

| 骨架件 | 出自 | 工作项目对应 |
|---|---|---|
| `lifespan` asynccontextmanager | 第 1 讲 | Redis Cluster 客户端在 lifespan 里初始化/释放 |
| `get_db_session` yield 依赖 | 第 1 讲 | `db/session.py` 的 `get_db_session()`:service 层因此禁写 commit/rollback |
| `DbSession = Annotated[...]` | — | `common/dependencies.py` 的类型别名:`DbSession`/`CurrentUser` |
| `async def` 路由 + Query 传参 | 第 2 讲 | 全部路由;ID 走 Query 不走路径 |
| `.order_by(Account.id).with_for_update()` | 锁教程第 2 讲 | 多行更新的固定加锁顺序,防死锁 |
| `asyncio.sleep(0.5)` 持锁窗口 | 第 2 讲反面教材 | 真实代码里这里是业务计算;窗口越长越要锁 |

**敲黑板:yield 依赖不能用 `@asynccontextmanager` 包。** FastAPI 的 `Depends` 只认"原生 async 生成器函数"(函数体里直接 yield);包了 `@asynccontextmanager` 它就变成"返回管家的普通函数",启动直接 `TypeError`。FastAPI 内部用 AsyncExitStack(第 1 讲 ExitStack 的异步版)替你 enter/exit——**yield 依赖就是上下文管理器思想的框架落地**。

## 2 跑起来:并发对转账

```
uv run python "异步教程/05-企业场景/mini_api.py"
```

另开一个终端,先重置、查余额:

```
curl -s -X POST "http://127.0.0.1:8010/reset"; echo
curl -s "http://127.0.0.1:8010/balance"; echo
```

```
{"msg":"ok:两账号各 1000,总额 2000"}
{"accounts":[{"id":1,"name":"阿花","balance":1000},{"id":2,"name":"阿草","balance":1000}],"total":2000}
```

然后**同一秒**发出两笔对向转账(1→2 转 200,2→1 转 300):

```
curl -s -X POST "http://127.0.0.1:8010/transfer?from_id=1&to_id=2&amount=200" &
curl -s -X POST "http://127.0.0.1:8010/transfer?from_id=2&to_id=1&amount=300" &
wait; curl -s "http://127.0.0.1:8010/balance"; echo
```

```
{"msg":"2 -> 1 转 300 成功"}{"msg":"1 -> 2 转 200 成功"}
{"accounts":[{"id":1,"name":"阿花","balance":1100},{"id":2,"name":"阿草","balance":900}],"total":2000}
```

正确版:阿花 1000-200+300=1100,阿草 1000+200-300=900。第二笔在锁上排队了 0.5 秒,但两笔都真实生效。

再试无锁版(先 reset):

```
curl -s -X POST "http://127.0.0.1:8010/reset" > /dev/null
curl -s -X POST "http://127.0.0.1:8010/transfer-naive?from_id=1&to_id=2&amount=200" &
curl -s -X POST "http://127.0.0.1:8010/transfer-naive?from_id=2&to_id=1&amount=300" &
wait; curl -s "http://127.0.0.1:8010/balance"; echo
```

```
{"msg":"1 -> 2 转 200 成功(其实未必)"}{"msg":"2 -> 1 转 300 成功(其实未必)"}
{"accounts":[{"id":1,"name":"阿花","balance":1300},{"id":2,"name":"阿草","balance":700}],"total":2000}
```

**那笔 1→2 的 200 整个蒸发了**(正确应 1100/900,实得 1300/700)。总额还是 2000——每笔转账自身是平衡的——但一笔转账凭空消失,用户 200 块不翼而飞。这就是锁教程第 1 讲的丢失更新,穿上了 HTTP 的外衣:两个请求各自"读→睡 0.5 秒→写",后提交的把先提交的整行覆盖。

(偶尔 naive 版也能出对的结果——窗口没重叠而已。事故的可怕正在于此:**时有时无,压测必现,线上偶发**。)

## 3 异步服务的五大事故模板

这套骨架下,生产事故翻来覆去就这几种:

| # | 事故 | 根因 | 解法(出处) |
|---|---|---|---|
| 1 | 一个接口慢,所有接口跟着超时 | async 路由里混了同步阻塞调用(同步 SDK、`time.sleep`、pandas 算大表) | to_thread 桥接;重活丢 Celery(第 4 讲) |
| 2 | 代码"没跑",结果全是空,还不报错 | 漏了 await,拿到协程对象当结果用 | 见 `RuntimeWarning: ... never awaited` 就查(第 2 讲) |
| 3 | gather 齐发打爆下游 | 没有并发上限 | Semaphore;连接池上限(第 3 讲) |
| 4 | 偶发数据错乱、丢更新 | 并发读写没锁 | 锁教程全家桶 |
| 5 | 共享一个 session 被两个协程同时用 | session/连接非并发安全,一个时刻只能一个协程用 | 请求级会话(每请求一个);跨协程各自开(第 1 讲 + FastAPI 依赖) |

第 5 条展开一句:`AsyncSession` 不是"线程安全"也不是"协程安全"——同一时刻只允许一个协程操作它。FastAPI 的 yield 依赖天然给了每个请求独立会话,这就是为什么**绝不要**把 session 存到模块级全局或长生命周期对象里。

Celery 侧(结合 celery 教程):worker 是独立进程,天然绕开 GIL;worker 里跑协程要用**常驻事件循环**(启动时建一个,任务里 `loop.run_until_complete(...)` 或内部已封装),不要每个任务 `asyncio.run` 反复建循环——工作项目 worker 正是常驻事件循环的写法。
