# 第 2 讲 · 协程与事件循环——单线程的并发

## 0 模型

asyncio 的全部秘密一张图:

```
        事件循环(一个线程,唯一的主角)
   ┌──────────────────────────────────────────────┐
   │   时刻    协程A          协程B          协程C   │
   │   t0    跑到 await ──┐                        │
   │   t1                 │         跑到 await ──┐ │
   │   t2                 ▼                       ▼ │
   │        A 在等网络(挂起,不占线程)  B 在等网络      │
   │   t3    ……谁的网络先回来,谁先恢复运行……           │
   │   t4    A 醒来跑到下一个 await                   │
   └──────────────────────────────────────────────┘
   同一时刻只有一个协程在跑;等待的协程让出线程给别的协程
```

| 概念 | 一句话 |
|---|---|
| 协程 coroutine | `async def` 定义的函数,调用它得到协程对象,**不 await 不执行** |
| await | 让位点:这点上把控制权交还事件循环,自己去等;等的事完成了再回来 | 
| 事件循环 | 调度台,单线程,决定"现在谁跑" |
| Task | 被 create_task 丢上调度台的协程,从此和别的 Task 并行推进 |
| 阻塞 | 不让位的等待(如 `time.sleep`):抱着线程不放,全场冻结 |

和"多线程并发"的根本区别:**协程的切换点是代码里显式写的 await,线程的切换点是操作系统随时插进来的**。前者因此不需要锁保护 `x += 1`(await 之外没人能打断),后者必须加锁(第 4 讲实测对比)。

## 1 敲代码:`hello_async.py`

```python
"""协程的三个第一课:不 await 不执行、await 让位、time.sleep 堵死全场。"""

import asyncio
import time


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


async def cook(name: str, rounds: int) -> None:
    """炒 rounds 道菜:每道菜之间的 await sleep 是让位点。"""
    for i in range(1, rounds + 1):
        log(f"{name}:第 {i} 道菜下锅")
        await asyncio.sleep(0.3)  # 等菜熟的间隙,把 CPU 让给别人
        log(f"{name}:第 {i} 道菜出锅")


async def blocking_guy() -> None:
    """反面角色:在协程里用 time.sleep——它不认识 asyncio,抱着 CPU 不撒手。"""
    log("堵门者:开始 time.sleep(1) —— 全场冻结")
    time.sleep(1)  # noqa: ASYNC251 —— 故意在协程里阻塞,反面教材
    log("堵门者:睡醒了,别人才能继续")


async def main() -> None:
    log("=== 第一幕:定义协程不等于运行协程 ===")
    coro = cook("阿厨", 1)
    log(f"只定义、不 await:它是 {type(coro).__name__},什么都没发生")
    await coro
    log("await 之后才真正开跑")

    log("=== 第二幕:两个厨子轮流掌勺(await 是让位点) ===")
    await asyncio.gather(cook("甲厨", 3), cook("乙厨", 3))

    log("=== 第三幕:time.sleep 一上桌,全场冻结 ===")
    await asyncio.gather(cook("丙厨", 4), blocking_guy())
    log("看时间戳:堵门者睡的那 1 秒里,丙厨一道菜都没出锅")


asyncio.run(main())
```

`tasks.py`——串行 vs Task 并发,以及"单线程 += 不丢"的铁证:

```python
"""Task:把协程丢上调度台;顺带验证单线程事件循环里 += 不会丢。"""

import asyncio
import time


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


async def download(name: str, seconds: float) -> str:
    """模拟调下游接口:耗时 seconds 秒,全程都在等网络,不占 CPU。"""
    log(f"{name} 出发")
    await asyncio.sleep(seconds)
    log(f"{name} 回来了")
    return f"{name}的结果"


async def main() -> None:
    log("=== 第一幕:三个 await 串行,总耗时 = 各自相加 ===")
    start = time.monotonic()
    await download("接口甲", 1)
    await download("接口乙", 1)
    await download("接口丙", 1)
    log(f"串行总耗时 {time.monotonic() - start:.1f} 秒")

    log("=== 第二幕:create_task 并发,总耗时 = 最慢那个 ===")
    start = time.monotonic()
    tasks = [asyncio.create_task(download(f"接口{i}", 1)) for i in range(3)]
    results = await asyncio.gather(*tasks)
    log(f"并发总耗时 {time.monotonic() - start:.1f} 秒,拿到 {results}")

    log("=== 第三幕:事件循环是单线程,+= 之间没有 await 就不会被打断 ===")
    counter = 0

    async def bump(worker: str) -> None:
        nonlocal counter
        for _ in range(10000):
            counter += 1  # 读写之间没有 await,天然原子
            if _ % 1000 == 0:
                await asyncio.sleep(0)  # 让位给别人,但让位点不在 += 中间
        log(f"{worker} 干完")

    await asyncio.gather(*(bump(f"工人{i}") for i in range(4)))
    log(f"4 个工人各 +10000,counter = {counter}(一个不丢;换成线程就未必了,见第 4 讲)")


asyncio.run(main())
```

几个关键写法的含义:

| 写法 | 含义 |
|---|---|
| `coro = cook(...)` | 只造出协程对象,一行代码没跑 |
| `await coro` | 在这里等它跑完(顺序执行) |
| `asyncio.create_task(coro)` | 立刻丢上调度台,**不等它**,先继续干别的 |
| `asyncio.gather(a, b)` | 并发等多个,全好了拿结果列表 |
| `asyncio.sleep(0)` | 纯让位:"轮到别人了",常用于测试并发交错 |
| `asyncio.run(main())` | 建事件循环、跑完、关掉——整个程序的入口,一个进程一个 |

三个现象各自说明了什么:

- **第二幕交错日志**:两个厨子严格轮流,每次 `await sleep` 就是换人点——这就是"单线程并发"的样子,**不是同时跑,是等的时候让别人跑**
- **第三幕冻结**:`time.sleep(1)` 那 1 秒(:35→:36)丙厨零输出——协程世界里,谁阻塞了线程,谁就冻结了整个服务。生产事故版本:"路由里调了个同步的库,整个接口全线超时"
- **tasks 第三幕**:四个"工人"共 40000 次 `+=`,分毫不差——`+=` 两步之间没有 await,事件循环根本没有插手的机会。**对比第 4 讲线程版丢 2993 次,这条分界线要刻在脑子里**

**敲黑板:async 的世界里,"危险"重定义了。** 普通代码怕的是"两段代码同时执行";协程世界怕的是"await 点两侧数据被人改了"。两个 await 之间看过的数据,第二个 await 之后要用,中间就得重新读或确认没被改(数据库侧的保障就是锁教程的 FOR UPDATE / version)。

## 3 让位的前提:等待必须"异步味"

| 调用 | 等待时 | 结论 |
|---|---|---|
| `await asyncio.sleep(n)` | 让出线程 | ✅ |
| `await session.execute(...)`(异步驱动) | 让出线程 | ✅ 异步驱动 = 底层 IO 用非阻塞接口 + 挂起协程 |
| `time.sleep(n)` | 不让 | ❌ 冻结全场 |
| 同步数据库驱动 / requests / 同步 Redis 客户端 | 不让 | ❌ 同上,第 4 讲 to_thread 是出路 |
| `asyncio.sleep(0)` | 让出但立刻排队回来 | 主动制造切换点,测试用 |

**敲黑板:忘了 await 不报错,只是"没跑"。** `session.execute(stmt)` 少写 await,拿到的是协程对象,后面的代码用的是它而非结果,炸点在千里之外,查起来极疼。看到 `RuntimeWarning: coroutine ... was never awaited` 就是它。习惯:看到 `async def`,调用处必带 await;IDE/PyCharm 的灰色提示别忽略。

## 5 速查表

| API | 一句话 |
|---|---|
| `async def` / `await` | 定义协程 / 让位点 |
| `asyncio.run(main())` | 进程入口,建循环跑完关 |
| `create_task(coro)` | 立刻调度,不等 |
| `await coro` | 顺序等它跑完 |
| `asyncio.sleep(n)` | 异步等待;`sleep(0)` 纯让位 |
| `time.sleep(n)` | ❌ 协程里的毒药 |
