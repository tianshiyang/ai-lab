## 0 模型:三个世界怎么选

```
            你的活是什么性质?
                   │
     ┌─────────────┼──────────────────┐
     ▼             ▼                  ▼
  等 IO          等 IO              算数(CPU)
  有异步库        只有同步库           │
     │             │                  ▼
     ▼             ▼                  ▼
 asyncio 一路   asyncio.to_thread    进程:ProcessPool / Celery
 (第 2、3 讲)   把阻塞扔进线程        (线程救不了,§4 实测)
```

选型的物理学基础是 **GIL(全局解释器锁)**:CPython 里同一时刻只许一个线程执行 Python 字节码。两个推论:

- **等 IO 时线程会释放 GIL** → 线程对"等网络/磁盘"有真实收益
- **纯算数全程抱着 GIL** → 线程零收益,只有进程能上多核(§4 实测)

Python 3.13+ 有实验性 free-threading(无 GIL)构建,企业主线仍是带 GIL 的标准构建——按 GIL 设计,不会错。

本讲 API 一览:

| API | 作用一句话 |
|---|---|
| `threading.Thread(target=, args=)` | 起一个线程跑函数 |
| `threading.Lock()` | 线程互斥锁(线程世界的悲观锁) |
| `ThreadPoolExecutor(max_workers=)` | 有界线程池:submit / map |
| `ProcessPoolExecutor(max_workers=)` | 进程池,CPU 密集专用 |
| `asyncio.to_thread(fn, *args)` | 把同步阻塞函数扔进线程,事件循环不冻结 |

## 1 `threading.Thread(group=None, target=None, name=None, args=(), kwargs={}, *, daemon=None)`

`target` 是线程要跑的函数,`args` 是它的参数,`start()` 开跑(不等待),`join()` 等它结束。`daemon=True` 表示守护线程(主进程退出时不等它):

```python
import time
from threading import current_thread, Thread


def download(name: str) -> None:
    print(f"{name} 在线程 {current_thread().name} 里跑")
    time.sleep(0.3)
    print(f"{name} 干完")


threads = [Thread(target=download, args=(f"任务{i}",), name=f"worker-{i}") for i in range(3)]
for t in threads:
    t.start()          # 开跑,不等待
print("主线程继续干别的")
for t in threads:
    t.join()           # 等它结束
print("主线程:全部收工")
```

```
任务0 在线程 worker-0 里跑
任务1 在线程 worker-1 里跑
任务2 在线程 worker-2 里跑
主线程继续干别的
任务1 干完
任务0 干完
任务2 干完
主线程:全部收工
```

谁先干完不确定——**线程的切换由操作系统随时插入**,这是和协程(await 点切换,你说了算)的根本区别,也是下面要加锁的原因。

## 2 `threading.Lock()`:共享可变状态的必答题

第 2 讲验证过"协程的 `+=` 不丢"。同一份读-改-写,换成线程:窗口一拉宽(读出来 → 让一下 → 写回去),丢得惨不忍睹;`Lock` 一上,一个不丢:

```python
import sys
import time
from threading import Barrier, Lock, Thread

sys.setswitchinterval(1e-6)  # 放大线程交错,让丢更新必现
counter = 0
lock = Lock()


def bump_wide(barrier: Barrier) -> None:
    global counter
    barrier.wait()  # 四线程对齐起跑,最大化竞争
    for _ in range(1000):
        tmp = counter
        time.sleep(0)  # 让出 GIL:别的线程此刻也读到同一个 tmp
        counter = tmp + 1


def bump_locked(barrier: Barrier) -> None:
    global counter
    barrier.wait()
    for _ in range(1000):
        with lock:  # 同一时刻只许一个线程做这三步
            tmp = counter
            time.sleep(0)
            counter = tmp + 1


def run(target) -> int:
    global counter
    counter = 0
    barrier = Barrier(4)
    threads = [Thread(target=target, args=(barrier,)) for _ in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return counter


print(f"无锁宽窗口:counter = {run(bump_wide)}(期望 4000)")
print(f"加锁宽窗口:counter = {run(bump_locked)}(期望 4000)")
```

```
无锁宽窗口:counter = 1206(期望 4000)
加锁宽窗口:counter = 4000(期望 4000)
```

这就是锁教程第 1 讲"数据库丢失更新"的线程版——病同构,药也同构:`with lock:` 就是线程世界的 `FOR UPDATE`(悲观锁)。两条纪律:

- **协程 vs 线程的分界线**:协程切换只发生在 await(await 之间天然原子),线程切换随时插入(共享读写必 Lock)
- 裸 `counter += 1` 在今天的 CPython 上"看起来不丢"(GIL 释放在循环回边,恰好不在读写之间)——**这是实现巧合不是语言承诺**,按"会丢"设防,不按"没看见丢"赌

## 3 `concurrent.futures.ThreadPoolExecutor(max_workers=None)`

有界线程池,`with` 出池、出块自动等全部任务收工(shutdown)。两种用法:`submit(fn, *args)` 提交单个任务拿 `Future`,`future.result()` 阻塞收结果;`map(fn, *iterables)` 批量提交、按**提交顺序**迭代结果:

```python
from concurrent.futures import ThreadPoolExecutor


def download(name: str) -> str:
    import time
    time.sleep(0.3)
    return f"{name}的结果"


with ThreadPoolExecutor(max_workers=3) as pool:
    # 写法一:submit 拿 Future,自己收结果
    future = pool.submit(download, "任务A")
    print("提交后立刻返回:", future)
    print("结果:", future.result())

    # 写法二:map 一批提交,按提交顺序迭代结果
    for r in pool.map(download, ["任务B", "任务C", "任务D"]):
        print("结果:", r)
```

```
提交后立刻返回: <Future at 0x101554d70 state=running>
结果: 任务A的结果
结果: 任务B的结果
结果: 任务C的结果
结果: 任务D的结果
```

简单脚本并发下载、批量调接口,`ThreadPoolExecutor` 十行搞定,比 asyncio 顺手就用它。**`max_workers` 一定要设**:默认值是核数×5,突发大列表会开出一堆线程;池存在的意义就是"有界"。

## 4 `concurrent.futures.ProcessPoolExecutor(max_workers=None)`

API 和线程池完全一样(同一套 `concurrent.futures` 接口),但每个工人是**独立进程**:自己的解释器、自己的 GIL,真·多核并行。CPU 密集实测——线程池一点不快,进程池接近核数倍加速:

```python
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def crunch(n: int) -> int:
    """纯 CPU 计算:算 1..n 的平方和。GIL 在场,线程帮不上忙。"""
    return sum(i * i for i in range(1, n + 1))


def run_batch(label: str, executor_cls, chunks: list[int]) -> None:
    start = time.monotonic()
    if executor_cls is None:
        results = [crunch(c) for c in chunks]
    else:
        with executor_cls(max_workers=4) as pool:
            results = list(pool.map(crunch, chunks))
    print(f"{label:<6} 耗时 {time.monotonic() - start:4.1f} 秒,结果校验 {sum(results) % 97}")


if __name__ == "__main__":  # 进程池在 macOS 上用 spawn 起进程,这行保护是硬要求
    chunks = [20_000_000] * 4
    run_batch("串行", None, chunks)
    run_batch("线程池", ThreadPoolExecutor, chunks)
    run_batch("进程池", ProcessPoolExecutor, chunks)
```

```
串行     耗时  2.0 秒,结果校验 67
线程池    耗时  2.1 秒,结果校验 67
进程池    耗时  0.6 秒,结果校验 67
```

(此例需存成文件运行,`__main__` 保护不能省。)注意进程池有启动和数据序列化开销,任务太小不划算;**生产上 CPU 密集的正经归宿不是进程池,是 Celery worker 或独立服务**——重活打包成任务丢给 worker,API 进程永不被拖慢(工作项目正是如此,详见 celery 教程)。

## 5 `asyncio.to_thread(func, /, *args, **kwargs)`

异步世界遇到**只有同步版**的库(老 SDK、`time.sleep` 式等待),把它扔进线程池执行,协程 `await` 它,事件循环照常调度别人。老写法 `loop.run_in_executor(None, func)` 的现代替身(3.9+):

```python
import asyncio
import time

start = time.monotonic()


def log(msg: str) -> None:
    print(f"[{time.monotonic() - start:5.2f}s] {msg}", flush=True)


def sync_sdk_call(seconds: float) -> str:
    """一个只有同步版的旧 SDK:里面是 time.sleep 式的阻塞等待。"""
    time.sleep(seconds)
    return "SDK 结果"


async def heartbeat() -> None:
    for i in range(6):
        log(f"心跳 {i}")
        await asyncio.sleep(0.2)


async def bad_call() -> None:
    result = sync_sdk_call(0.6)  # ❌ 阻塞调用直接占用事件循环线程
    log(f"直接调:{result}")


async def good_call() -> None:
    result = await asyncio.to_thread(sync_sdk_call, 0.6)  # ✅ 阻塞发生在别的线程
    log(f"to_thread:{result}")


async def main() -> None:
    log("=== 第一幕:直接调同步 SDK,心跳冻结 ===")
    await asyncio.gather(heartbeat(), bad_call())
    log("=== 第二幕:to_thread 桥接,心跳不断 ===")
    await asyncio.gather(heartbeat(), good_call())


asyncio.run(main())
```

```
[ 0.00s] === 第一幕:直接调同步 SDK,心跳冻结 ===
[ 0.00s] 心跳 0
[ 0.61s] 直接调:SDK 结果
[ 0.61s] 心跳 1
[ 0.81s] 心跳 2
[ 1.02s] 心跳 3
[ 1.22s] 心跳 4
[ 1.42s] 心跳 5
[ 1.62s] === 第二幕:to_thread 桥接,心跳不断 ===
[ 1.62s] 心跳 0
[ 1.82s] 心跳 1
[ 2.02s] 心跳 2
[ 2.23s] to_thread:SDK 结果
[ 2.23s] 心跳 3
[ 2.43s] 心跳 4
[ 2.63s] 心跳 5
```

第一幕 0.00→0.61s 心跳静默 0.6 秒:直接调用把事件循环线程占了,**FastAPI 异步路由里这么写,冻住的是所有正在处理的请求**。第二幕心跳全程 0.2 秒一拍:SDK 在别的线程里阻塞,谁也不耽误。

## 6 企业真话:多线程到底用不用

| 场景 | 用不用线程 | 真实形态 |
|---|---|---|
| FastAPI/SQLAlchemy 异步栈(工作项目) | 不用 | async 一路到底:asyncpg、aio-pika、redis.asyncio |
| 栈里混进同步 SDK | **用,但只是桥** | `await asyncio.to_thread(sdk_call, ...)`——线程是隔离阻塞的工具,不是并发模型 |
| CPU 密集(转码/压缩/报表/大文件 hash) | 不用线程 | Celery worker(独立进程)/ 独立服务;进程池仅限脚本内小规模 |
| 简单脚本并发(爬 100 个页面、批量调接口) | 随意 | `ThreadPoolExecutor` + `map`,十行以内顺手就用 |
| 长期存在的第三方生态 | 在服役 | 某些数据库驱动、NumPy 密集运算部分(C 层释放 GIL)、监控 agent 后台线程 |

**一句话:线程在 Python 企业代码里的角色是"桥接阻塞调用"和"简单脚本的并发糖",不是服务端的并发主线。** 主线是 asyncio;CPU 是进程的活。看见新代码在 FastAPI 里起 `threading.Thread` 干活,先问一句"为什么不是 to_thread / 为什么不是 worker"。

两条遗留规矩:① 共享可变状态必加 `threading.Lock`,按"会丢"设防;② 线程池必须有界(`max_workers`),无界线程池在突发流量下会内存爆炸。

## 7 速查表

| 工具 | 用途 | 心法 |
|---|---|---|
| `Thread(target, args).start()/join()` | 起线程跑函数 | 切换随时插入,共享必 Lock |
| `with lock:` | 线程互斥 | 线程版悲观锁,锁内别拖长 |
| `ThreadPoolExecutor` | 有界线程池 | IO 密集脚本糖;submit/map 两种用法 |
| `ProcessPoolExecutor` | 进程池 | CPU 密集;`__main__` 保护硬要求 |
| `asyncio.to_thread(fn, ...)` | 同步函数进线程 | 异步世界里的同步桥 |
| Celery worker | 生产级"进程" | CPU/慢活的标准归宿(celery 教程) |
