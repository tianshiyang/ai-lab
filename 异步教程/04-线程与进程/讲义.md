# 第 4 讲 · 线程、进程与阻塞桥接

## 0 模型

三个世界,一张图选型(先背结论,后面全是证据):

```
            你的活是什么性质?
                   │
     ┌─────────────┼──────────────────┐
     ▼             ▼                  ▼
  等 IO          等 IO              算数(CPU)
  有异步库        只有同步库           │
     │             │                  │
     ▼             ▼                  ▼
 asyncio 一路   asyncio.to_thread    进程:ProcessPool / Celery
 (第 2、3 讲)   把阻塞扔进线程        (线程救不了,第 2 节实测)
```

| 概念 | 一句话 |
|---|---|
| GIL 全局解释器锁 | CPython 里同一时刻只许一个线程执行 Python 字节码——线程"并行"执行 Python 代码是假象 |
| threading.Lock | 线程互斥锁——线程世界的悲观锁,锁教程第 2 讲的直系亲属 |
| concurrent.futures | 线程池/进程池统一接口:`ThreadPoolExecutor` / `ProcessPoolExecutor` |
| asyncio.to_thread | 把同步阻塞函数扔进线程池执行,协程 await 它,事件循环不冻结 |

GIL 的关键细节:**等 IO 时线程会释放 GIL**。所以线程对"等网络/磁盘"有真实收益(等待期别的线程能跑);对"纯算数"零收益(全程抱着 GIL,第 2 节实测)。Python 3.13+ 有实验性的 free-threading(无 GIL)构建,企业主线仍是带 GIL 的标准构建——按 GIL 设计,不会错。

## 1 敲代码:`threads_race.py`(线程丢数实录)

第 2 讲验证了"协程的 `+=` 不丢",同一份代码换成线程,画风突变:

```python
"""线程的 += :小窗口看不见丢,窗口一拉大就现形;Lock 一上,一个不丢。"""

import time
from threading import Barrier, Lock, Thread


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


counter = 0
lock = Lock()


def bump_tiny(worker: str, barrier: Barrier) -> None:
    """裸 +=:窗口只有几纳秒,今天大概率撞不见丢数。"""
    global counter
    barrier.wait()  # 四个线程同时对齐起跑,最大化竞争
    for _ in range(200000):
        counter += 1


def bump_wide(worker: str, barrier: Barrier) -> None:
    """读出来→让一下→写回去:窗口拉大,读-改-写拆成三步(和第 1 讲数据库丢更新同构)。"""
    global counter
    barrier.wait()
    for _ in range(1000):
        tmp = counter
        time.sleep(0)  # 主动让出 GIL:别的线程此刻也能读到同一个 tmp
        counter = tmp + 1


def bump_locked(worker: str, barrier: Barrier) -> None:
    """还是宽窗口,但读写全程持锁。"""
    global counter
    barrier.wait()
    for _ in range(1000):
        with lock:
            tmp = counter
            time.sleep(0)
            counter = tmp + 1


def run(version: str, target, per_thread: int) -> int:
    global counter
    counter = 0
    barrier = Barrier(4)
    threads = [Thread(target=target, args=(f"线程{i}", barrier)) for i in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    log(f"{version}:4 线程,counter = {counter}(期望 {4 * per_thread})")
    return counter


if __name__ == "__main__":
    log("=== 第一幕:裸 +=,200 万次更新 ===")
    run("裸加号", bump_tiny, 200000)
    log("没丢?CPython 释放 GIL 的检查点在循环回边等地方,恰好不在 += 的读写之间")
    log("这是实现巧合,不是语言承诺——窗口拉大立刻现形:")

    log("=== 第二幕:读出来、让一下、写回去(窗口拉宽)===")
    got = run("宽窗口", bump_wide, 1000)
    log(f"4000 次更新丢了 {4000 - got} 次——线程真的会同时读到同一个旧值")

    log("=== 第三幕:同样的宽窗口,Lock 全程护送 ===")
    run("上锁版", bump_locked, 1000)
    log("一个不丢;Lock 就是线程世界的悲观锁——正好接上锁教程第 2 讲")
```

三幕连读,两个大结论:

1. **协程 vs 线程的分界线实锤**:协程版(第 2 讲)40000 次零丢失,因为切换只发生在 await 点;线程版读-改-写窗口一拉宽,4000 丢 2993,因为**切换随时可能插进来**。协程的世界 `+=` 天然安全,线程的世界一切共享读写都要问"要不要锁"。
2. **第一幕的"没丢"是巧合不是承诺**:今天的 CPython 恰好不在 `+=` 的读写之间释放 GIL,换实现、换版本、表达式复杂一点(中间有函数调用),窗口就开了。写代码按"会丢"来防,不按"没看见丢"来赌。

注意 `bump_wide` 的结构——读出来、中间有耗时、写回去——**就是锁教程第 1 讲"读-改-写丢更新"的线程版**。两个教程在这一刻合流:数据库用 FOR UPDATE/version,线程用 Lock,病是同一个病。

## 3 GIL 与 CPU 密集:`pools.py` 三池对比

```python
"""同一个 CPU 密集任务:串行、线程池、进程池三种跑法对耗时。"""

import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


def crunch(n: int) -> int:
    """纯 CPU 计算:算 1..n 的平方和。GIL 在场,线程帮不上忙。"""
    return sum(i * i for i in range(1, n + 1))


def run_batch(label: str, executor_cls, chunks: list[int]) -> None:
    start = time.monotonic()
    if executor_cls is None:
        results = [crunch(c) for c in chunks]
    else:
        with executor_cls(max_workers=4) as pool:
            results = list(pool.map(crunch, chunks))
    cost = time.monotonic() - start
    log(f"{label:<8} 耗时 {cost:5.1f} 秒,结果校验 {sum(results) % 97}")


if __name__ == "__main__":
    chunks = [30_000_000] * 4
    log("4 份各 3000 万次平方和,先后用串行 / 线程池 / 进程池跑")
    run_batch("串行", None, chunks)
    run_batch("线程池", ThreadPoolExecutor, chunks)
    run_batch("进程池", ProcessPoolExecutor, chunks)
    log("线程池和串行差不多(GIL);进程池明显快(真·多核)——CPU 密集请交给进程")
```

线程池 3.2 秒 ≈ 串行 3.3 秒:**四个线程没有带来一丝加速**——全程算数,GIL 让它们排队;进程池 0.9 秒,接近核数倍加速——每个进程有自己的解释器和 GIL。两个注意点:进程池有启动/序列化开销,任务太小不划算(macOS 默认 spawn 进程,`if __name__ == "__main__"` 保护是硬要求,本脚本有);**生产上 CPU 密集的正确归宿不是进程池,是 Celery worker 或独立服务**(工作项目正是如此:重活打包成任务丢给 worker,API 进程永不被拖慢)。

## 4 阻塞桥接:`to_thread_demo.py`

最后一块拼图:异步世界里遇到**只有同步版**的库(老 SDK、`time.sleep` 式等待),怎么办?

```python
"""asyncio.to_thread:同步阻塞函数扔进线程,别让它冻结事件循环。"""

import asyncio
import time


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


def sync_sdk_call(seconds: float) -> str:
    """一个只有同步版的旧 SDK:里面是 time.sleep 式的阻塞等待。"""
    time.sleep(seconds)  # 阻塞:抱着线程不放
    return "SDK 结果"


async def heartbeat() -> None:
    """心跳:每 0.2 秒打一个点,用来观察事件循环冻没冻。"""
    for i in range(12):
        log(f"心跳 {i}")
        await asyncio.sleep(0.2)


async def main() -> None:
    log("=== 第一幕:直接在协程里调同步 SDK —— 心跳冻结 ===")
    start = time.monotonic()

    async def bad_call() -> None:
        result = sync_sdk_call(1)  # 阻塞调用直接占用事件循环线程
        log(f"拿到 {result}(期间全场冻结)")

    await asyncio.gather(heartbeat(), bad_call())
    log(f"看时间戳:整整 1 秒没有心跳(共 {time.monotonic() - start:.1f} 秒)\n")

    log("=== 第二幕:to_thread 把 SDK 扔进线程 —— 心跳不断 ===")
    start = time.monotonic()

    async def good_call() -> None:
        result = await asyncio.to_thread(sync_sdk_call, 1)  # 阻塞发生在别的线程
        log(f"拿到 {result}(心跳照常)")

    await asyncio.gather(heartbeat(), good_call())
    log(f"心跳全程不断(共 {time.monotonic() - start:.1f} 秒)")


asyncio.run(main())
```

第一幕的 1 秒心跳空窗,就是第 2 讲"全场冻结"的生产版本:**FastAPI 异步路由里一个同步调用,冻住的是所有正在处理的请求**。`asyncio.to_thread(f, x)` 的原理:f 在线程池的一个线程里跑,它爱怎么阻塞怎么阻塞,事件循环线程照常调度别人;await 只是在等它完成。3.9+ 用 `to_thread`,更老的写法是 `loop.run_in_executor(None, f, x)`。

## 5 企业真话:多线程到底用不用

回到 README 里的问题,现在可以把话讲全:

| 场景 | 用不用线程 | 真实形态 |
|---|---|---|
| FastAPI/SQLAlchemy 异步栈(工作项目) | 不用 | async 一路到底:asyncpg、aio-pika、redis.asyncio |
| 栈里混进同步 SDK | **用,但只是桥** | `await asyncio.to_thread(sdk_call, ...)`——线程是隔离阻塞的工具,不是并发模型 |
| CPU 密集(转码/压缩/报表/大文件 hash) | 不用线程 | Celery worker(独立进程)/ 独立服务;进程池仅限脚本内小规模 |
| 简单脚本并发(爬 100 个页面、批量调接口) | 随意 | `ThreadPoolExecutor` + `map`,十行以内,比 asyncio 顺手就用它 |
| 长期存在的第三方生态 | 在服役 | 某些数据库驱动、NumPy 密集运算部分(C 层释放 GIL)、监控 agent 的后台线程 |

**一句话总结:线程在 Python 企业代码里的角色是"桥接阻塞调用"和"简单脚本的并发糖",不是服务端的并发主线。** 主线是 asyncio;CPU 是进程的活。看见新代码在 FastAPI 里起 `threading.Thread` 干活,先问一句"为什么不是 to_thread / 为什么不是 worker"。

线程遗留的两个规矩,遇到就要守:① 共享可变状态必加 `threading.Lock`,按"会丢"设防;② 线程池要有界(`max_workers`),无界线程池在突发流量下会内存爆炸。

## 7 速查表

| 工具 | 用途 | 心法 |
|---|---|---|
| `threading.Lock` | 线程互斥 | 共享可变状态必锁;线程版悲观锁 |
