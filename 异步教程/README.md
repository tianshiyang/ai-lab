## 先回答你最关心的:企业里真的用多线程吗

**直接结论(第 4 讲展开):**

| 场景 | 企业的选择 |
|---|---|
| Web 服务(IO 密集,新代码) | **asyncio + FastAPI**(工作项目就是) |
| Web 服务里遇到只有同步版的 SDK | `asyncio.to_thread` 桥接,**不另起线程体系** |
| CPU 密集(转码、压缩、报表) | **独立进程**:Celery worker(工作项目就是)/ 容器拆分,不用线程池硬扛 |
| 简单脚本并发下载/调接口 | `ThreadPoolExecutor` 十行搞定,够用 |
| 老项目、特定 SDK(JDBC 风格驱动、NumPy 生态) | 线程仍在服役 |

Python 的多线程因为 GIL,同一时刻只有一个线程执行 Python 字节码——**线程只对"等 IO"有收益,对"算数"没有**。所以服务端新代码主线是 asyncio,线程退居"桥接阻塞调用"的配角,重 CPU 一律甩给进程。这不是"用不用"的问题,是"用在哪一层"的问题。

## 学完标准

- 看到 `async with session:` 能说出**谁在什么时候 commit/rollback/close**
- 看到 `await` 能指出**让位点**,看到 `time.sleep` 在协程里能立刻报警
- 能默写"IO 密集 → asyncio;阻塞库 → to_thread;CPU 密集 → 进程/Celery"三行选型
- 知道**事件循环里唯一的线程被谁占着,谁就是全服务的瓶颈**
