# 第 2 讲 · 悲观锁——先锁后用

## 0 模型

悲观锁的思想一句话:**假设冲突一定会发生,动手之前先把门锁上**。

```
   事务甲                              事务乙
     │  SELECT ... FOR UPDATE
     ▼
   拿到 id=1 的行锁 ─────────┐
     │  干活(转账校验/算手续费) │      SELECT ... FOR UPDATE
     │                        │        │
     │                        │        ▼ 排队等锁(不报错,干等)
     │  COMMIT ───────────────┼───►    │ 锁释放的瞬间轮到乙
     ▼                        │        ▼
   事务结束,锁自动放           │      拿到锁,读到的已是甲改完的最新值
```

| 术语 | 一句话 |
|---|---|
| 悲观锁 | 先加锁再操作,别人等着;数据库里就是 `SELECT ... FOR UPDATE`(排它锁) |
| 持锁周期 | 从语句执行到**事务提交或回滚**,不是语句结束就放 |
| NOWAIT | 锁被占时不排队,立刻报错 |
| SKIP LOCKED | 锁被占的直接跳过那行,拿没被占的——抢任务神器 |
| 死锁 | 互相等对方手里的锁,形成环,数据库杀掉一方自愈 |

## 1 FOR UPDATE:把第 1 讲的窗口锁死

第 1 讲的事故里,"读"是普通 SELECT,不加锁(走 MVCC 快照),所以乙能大摇大摆读到旧值。改成:

```sql
SELECT * FROM lock02_account WHERE id = 1 FOR UPDATE;   -- 锁定读
```

读的同时给这行上排它锁:乙再来 FOR UPDATE 就得排队,直到甲提交。SQLAlchemy 里是 `.with_for_update()`:

```python
stmt = select(Account).where(Account.id == 1).with_for_update()
account = (await session.execute(stmt)).scalar_one()
```

**敲黑板:FOR UPDATE 必须活在事务里,锁到 commit/rollback 才放。** 会话 autocommit 模式下语句一完事务就结束、锁立刻放,等于没锁——所以本教程每个任务用独立会话、显式 `commit()`。同款规则:**锁内代码(临界区)能多短就多短**,别在持锁期间调外部接口、发短信。

## 2 敲代码:`for_update.py`

```python
"""第一幕:FOR UPDATE 排队;第二幕:NOWAIT 拿不到就走。"""

import asyncio
import os
import time
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select
from sqlalchemy.exc import DBAPIError
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Account(Base):
    __tablename__ = "lock02_account"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(20))
    balance: Mapped[int]


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def reset() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Account))
    async with Session() as session:
        session.add(Account(id=1, name="阿花", balance=1000))
        await session.commit()


async def spend_with_lock(who: str, amount: int, hold_seconds: float) -> None:
    """悲观锁扣款:SELECT FOR UPDATE 拿到行锁,睡一会再提交,模拟持锁干活。"""
    async with Session() as session:
        stmt = select(Account).where(Account.id == 1).with_for_update()
        account = (await session.execute(stmt)).scalar_one()
        log(f"{who} 锁住了 id=1,读到余额 {account.balance}")
        await asyncio.sleep(hold_seconds)
        account.balance -= amount
        await session.commit()
        log(f"{who} 扣 {amount} 后提交,锁释放,余额 {account.balance}")


async def try_lock_nowait(who: str) -> None:
    """NOWAIT 版:锁被占时数据库立刻报错,不排队。"""
    async with Session() as session:
        stmt = select(Account).where(Account.id == 1).with_for_update(nowait=True)
        try:
            account = (await session.execute(stmt)).scalar_one()
            log(f"{who} NOWAIT 拿到了锁,余额 {account.balance}")
            await asyncio.sleep(1)
            await session.rollback()
        except DBAPIError as e:
            log(f"{who} NOWAIT 立刻失败:{e.orig}")


async def main() -> None:
    log("=== 第一幕:乙的 FOR UPDATE 要排队等甲提交===")
    await reset()
    start = time.monotonic()
    await asyncio.gather(
        spend_with_lock("甲", 100, hold_seconds=2),
        spend_with_lock("乙", 100, hold_seconds=0.1),
    )
    log(f"两笔扣款共耗时 {time.monotonic() - start:.1f} 秒(乙等了甲整整 2 秒)")

    log("=== 第二幕:丙用 NOWAIT,拿不到锁当场报错===")
    await asyncio.gather(
        spend_with_lock("甲", 100, hold_seconds=2),
        try_lock_nowait("丙"),
    )
    async with Session() as session:
        final = (
            await session.execute(select(Account.balance).where(Account.id == 1))
        ).scalar_one()
    log(f"最终余额:{final}")
    await engine.dispose()


asyncio.run(main())
```

| 参数 | 语义 | 生成的 SQL |
|---|---|---|
| `.with_for_update()` | 排队等锁 | `FOR UPDATE` |
| `.with_for_update(nowait=True)` | 不排队,立刻报错 | `FOR UPDATE NOWAIT` |
| `.with_for_update(skip_locked=True)` | 跳过被锁行 | `FOR UPDATE SKIP LOCKED` |

## 4 SKIP LOCKED:多 worker 抢单

任务表是多 worker 系统的标配(工单、邮件、对账任务):表里一堆 `status='待处理'` 的行,几个 worker 进程同时来领。朴素做法是"查出待处理的,再逐条抢",会互相踩;`FOR UPDATE SKIP LOCKED` 一条语句解决——**被别人锁住的行直接跳过,大家各领各的,不重不漏**。这是 PostgreSQL 9.5+ / MySQL 8.0+ 都支持的企业标配套路。

`skip_locked.py`:

```python
"""SKIP LOCKED:两个 worker 并发抢单,各拿各的,互不等待。"""

import asyncio
import os
import time
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Job(Base):
    __tablename__ = "lock02_jobs"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(20))
    owner: Mapped[str | None] = mapped_column(String(20))


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def reset() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Job))
        await conn.execute(
            Job.__table__.insert(),
            [{"id": i, "name": f"工单-{i}", "owner": None} for i in range(1, 7)],
        )


async def claim_jobs(worker: str, batch: int) -> list[str]:
    """一批领取:领到的直接写上自己名字,占住不放直到提交。"""
    async with Session() as session:
        stmt = (
            select(Job)
            .where(Job.owner.is_(None))
            .order_by(Job.id)
            .limit(batch)
            .with_for_update(skip_locked=True)
        )
        jobs = (await session.execute(stmt)).scalars().all()
        names = [job.name for job in jobs]
        for job in jobs:
            job.owner = worker
        await asyncio.sleep(1)  # 模拟处理耗时,持锁期间另一个 worker 也在抢
        await session.commit()
        log(f"{worker} 领到 {names}")
        return names


async def main() -> None:
    await reset()
    log("6 张工单,两个 worker 同时各抢 3 张")
    results = await asyncio.gather(claim_jobs("worker-A", 3), claim_jobs("worker-B", 3))
    async with Session() as session:
        rows = (await session.execute(select(Job.id, Job.owner).order_by(Job.id))).all()
    log(f"最终归属:{[(row.id, row.owner) for row in rows]}")
    total = sum(len(names) for names in results)
    log(f"两边加起来领了 {total} 张,一张不重、一张不漏")
    await engine.dispose()


asyncio.run(main())
```

```

[11:01:22] worker-B 领到 ['工单-4', '工单-5', '工单-6']
[11:01:22] 最终归属:[(1, 'worker-A'), (2, 'worker-A'), (3, 'worker-A'), (4, 'worker-B'), (5, 'worker-B'), (6, 'worker-B')]
```

worker-A 先到先锁了前三行;worker-B 的同一条 SELECT 发现前三行被锁,**跳过**,领走 4-6。没有任何等待,没有任何一行被两人同时领。把 `skip_locked=True` 去掉再跑:B 会排队等 A 提交后才领到 1-3(行为退化成普通 FOR UPDATE,白瞎了并发);不加 `.with_for_update` 再跑:两人可能领到同一批(第 1 讲的丢失更新换个马甲)。

## 5 死锁:交叉加锁的必然结局

两个事务各锁一行、再要对方的——环就形成了,谁也走不下去。数据库有死锁检测器,发现环后**主动回滚一方**,让另一方活下来。`deadlock.py`:

```python
"""死锁:甲乙交叉加锁,数据库检测到环,杀掉一方。"""

import asyncio
import os
import time
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select
from sqlalchemy.exc import DBAPIError
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Transfer(Base):
    __tablename__ = "lock02_transfer"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(20))
    amount: Mapped[int]


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def reset() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Transfer))
        await conn.execute(
            Transfer.__table__.insert(),
            [
                {"id": 1, "name": "工资卡", "amount": 1000},
                {"id": 2, "name": "储蓄卡", "amount": 2000},
            ],
        )


async def lock_and_update(who: str, first: int, second: int) -> None:
    """按 first→second 的顺序锁两行:甲锁 1 再锁 2,乙锁 2 再锁 1,形成环。"""
    async with Session() as session:
        for row_id in (first, second):
            stmt = select(Transfer).where(Transfer.id == row_id).with_for_update()
            row = (await session.execute(stmt)).scalar_one()
            log(f"{who} 锁住 {row.name}(id={row_id})")
            await asyncio.sleep(1)
        await session.rollback()
        log(f"{who} 两行都到手,干完活提交")


async def main() -> None:
    await reset()
    log("甲按 1→2 加锁,乙按 2→1 加锁,各睡 1 秒……")

    async def guarded(who: str, first: int, second: int) -> None:
        try:
            await lock_and_update(who, first, second)
        except DBAPIError as e:
            log(
                f"{who} 被数据库选中当牺牲品:{type(e.orig).__name__}({getattr(e.orig, 'sqlstate', None)})"
            )

    await asyncio.gather(guarded("甲", 1, 2), guarded("乙", 2, 1))
    log("数据库检测到等待环,主动回滚了一方,另一方得以完成——这就是死锁的自愈")
    await engine.dispose()


asyncio.run(main())
```

```

[11:01:51] 乙 锁住 储蓄卡(id=2)
```

时间线:甲拿着 1 等 2,乙拿着 2 等 1 → 环。约 1 秒后(死锁检测有周期)数据库杀掉甲(`40P01` 就是 PostgreSQL 的 deadlock_detected 错误码),甲的锁全放,乙顺利拿齐。

**怎么防死锁**(比治疗便宜一百倍):

| 手段 | 说明 |
|---|---|
| **固定加锁顺序** | 所有事务都按同一顺序加锁(如按主键升序)。本讲的转账正确姿势:`WHERE id IN (a, b) ORDER BY id FOR UPDATE`,顺序就固定了。异步教程第 5 讲的迷你转账 API 就是这么写的 |
| 事务短小 | 持锁时间越短,环形成的窗口越小 |
| 一次锁齐 | 能一条语句锁住的别拆成多条 |
| 捕获死锁异常重试 | 40P01 / MySQL 1213,当普通冲突重试即可 |

**敲黑板:死锁不是灾难,是数据库的自愈机制;真正的灾难是高并发下死锁频繁发生。** 偶发死锁 → 捕获重试;频繁死锁 → 加锁顺序有毛病,改代码。

## 6 什么时候选悲观锁

| 维度 | 判断 |
|---|---|
| 冲突频率 | 高(热点行、秒杀、账户)——排队比反复重试省 |
| 临界区长度 | 短(几条 SQL)——锁持有久会拖垮并发 |
| 读-改-写复杂度 | 复杂(要查多表、要校验)——塞不进一条 SQL 时,悲观锁最直观 |
| 能否接受等待 | 等待会占连接池;高峰期热点行排队是雪崩起点,要限流/熔断兜底 |

## 7 MySQL 对照

| 点 | MySQL(InnoDB) | PostgreSQL |
|---|---|---|
| `FOR UPDATE` / `NOWAIT` / `SKIP LOCKED` | ✅ 8.0+ 全支持,语法同 | ✅ 9.5+ |
| 默认隔离级别 | Repeatable Read | Read Committed |
| 锁的载体 | **锁加在索引记录上**:WHERE 条件没走索引 → 扫全表,扫到的行全上锁,近似锁表 | 锁加在行版本上,但无索引同样会扫全表,建议永远用主键/唯一索引定位 |
| 间隙锁 | RR 级别有,锁"索引间隙"防幻读,是死锁高发区(第 4 讲) | 没有(靠可串行化隔离级别的 SSI) |
| 死锁错误码 | 1213 / `ER_LOCK_DEADLOCK`,SQLSTATE 40001 | SQLSTATE 40P01 |
| 行锁等待超时 | `innodb_lock_wait_timeout` 默认 50 秒,超时报 1206 | 无默认超时(可用 `lock_timeout` 设置),或 NOWAIT 主动不等 |

工作项目是 MySQL:FOR UPDATE 的写法原样搬过去就能用;要格外记住**WHERE 必须命中索引**,否则"行锁"变"表锁"。

## 9 速查表

| API / 语法 | 作用 | 注意 |
|---|---|---|
| `select(...).with_for_update()` | 排它锁定读,排队等锁 | 必须在事务里,锁到提交 |
| `.with_for_update(nowait=True)` | 不等,立刻报错 | 捕获后按"繁忙"处理 |
| `.with_for_update(skip_locked=True)` | 跳过被锁行 | 多 worker 抢任务标配 |
| `.with_for_update(of=某表)` | 联表时只锁指定表 | PG/MySQL 语法有差异,慎用 |
| `WHERE ... ORDER BY id FOR UPDATE` | 固定加锁顺序 | 防死锁第一招 |
