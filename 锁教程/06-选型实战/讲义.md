# 第 6 讲 · 选型决策 + 秒杀综合实战

## 0 一张决策表走天下

前面五讲各是一件武器。遇到需求先过这张表,**从上往下找第一条命中的**:

```
要保护什么?
│
├─ 单行数字增减/状态置位 ──────────► 一条 SQL:UPDATE ... SET x = x ± n [WHERE x >= n]
│
├─ 复杂读-改-写,冲突少 ────────────► 乐观锁:version / 状态条件 UPDATE + 重试
│
├─ 复杂读-改-写,冲突密(热点行)─────► 悲观锁:SELECT ... FOR UPDATE(短事务!)
│
├─ 同一业务身份不许出现两次 ────────► 唯一约束 + ON CONFLICT(幂等键)
│
├─ 多 worker 抢一批任务 ───────────► FOR UPDATE SKIP LOCKED
│
├─ 跨进程/跨实例互斥,非严格 ────────► Redis 锁:SET NX PX + token + Lua
│
└─ 严格互斥(资金清算级)──────────► 数据库行锁 / ZooKeeper / etcd
```

对照常见企业场景:

| 场景 | 用什么 | 要点 |
|---|---|---|
| 余额扣减 | `UPDATE SET balance = balance - n WHERE balance >= n` | 一条 SQL,别读出来再写 |
| 秒杀防超卖 | 同上 / version CAS | 库存行是热点,冲突密时可上悲观锁 |
| 订单状态流转 | `UPDATE ... WHERE status = '当前态'` | status 即版本 |
| 防重复提交/回调重放 | 唯一约束 + ON CONFLICT | 幂等键:订单号/流水号/用户+商品 |
| 定时任务多实例只跑一份 | Redis 锁 fast-fail | 锁键:任务名;抢不到直接退出 |
| 后台 worker 领工单 | SKIP LOCKED | 一条 SQL 分货,不重不漏 |
| 缓存失效防击穿 | Redis 锁 + 双重检查 | 没抢到的稍后重读缓存 |
| 转账(改两行) | FOR UPDATE + **按 id 排序** | 防死锁的固定顺序 |

**面试高频三问,答案全在前五讲:**

1. *乐观锁和悲观锁的区别?* —— 悲观先锁后用、持锁到事务结束、冲突多时用;乐观不加锁、提交时验版本、失败重试、冲突少时用。
2. *Redis 分布式锁怎样才正确?* —— 一条 `SET k v NX PX`;释放用 Lua 比对唯一 token;防过期要续期;Redis 只保证"尽力互斥"。
3. *怎么防超卖?* —— 条件 UPDATE 或 version CAS 扣库存,唯一约束防一人多单,层层兜底对账。

## 1 综合实战:秒杀

需求:20 个用户抢 10 部手机,u03 和 u07 手抖各点了两次。三个威胁同时在场:

| 威胁 | 解法(出处) |
|---|---|
| 手抖双击 → 一人多单 | 唯一约束 + ON CONFLICT(第 4 讲) |
| 10 部库存卖出 11 部 | version CAS + 重试(第 3 讲) |
| 没抢到的留下一张"成功"订单 | 售罄/重试耗尽时**补偿删单** |

`seckill.py`:

```python
"""秒杀小综合:唯一约束挡重复提交,乐观锁挡超卖,售罄走补偿。"""

import asyncio
import os
import random
import time
from collections import Counter
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select, update
from sqlalchemy.dialects.postgresql import insert as pg_insert
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Stock(Base):
    __tablename__ = "lock06_stock"

    sku: Mapped[str] = mapped_column(String(20), primary_key=True)
    qty: Mapped[int]
    version: Mapped[int] = mapped_column(default=0)


class Order(Base):
    __tablename__ = "lock06_order"

    id: Mapped[int] = mapped_column(primary_key=True)
    order_no: Mapped[str] = mapped_column(
        String(30), unique=True
    )  # 用户+商品唯一:重复点击撞这里
    user_id: Mapped[str] = mapped_column(String(10))


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def reset(stock_qty: int) -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Stock))
        await conn.execute(delete(Order))
    async with Session() as session:
        session.add(Stock(sku="手机", qty=stock_qty))
        await session.commit()


async def buy(user_id: str) -> str:
    """一单的完整防御:先幂等落单,再乐观锁扣库存,售罄则补偿删单。"""
    async with Session() as session:
        order_no = f"SO-{user_id}-phone"
        stmt = (
            pg_insert(Order)
            .values(order_no=order_no, user_id=user_id)
            .on_conflict_do_nothing(index_elements=[Order.order_no])
            .returning(Order.id)
        )
        row = (await session.execute(stmt)).scalar_one_or_none()
        await session.commit()
        if row is None:
            return "重复提交"

    for _ in range(5):  # 乐观锁重试,最多 5 次
        async with Session() as session:
            result = await session.execute(select(Stock).where(Stock.sku == "手机"))
            stock = result.scalar_one()
            if stock.qty < 1:
                await session.execute(delete(Order).where(Order.order_no == order_no))
                await session.commit()
                return "售罄(补偿删单)"
            result = await session.execute(
                update(Stock)
                .where(Stock.sku == "手机", Stock.version == stock.version)
                .values(qty=stock.qty - 1, version=stock.version + 1)
            )
            await session.commit()
            if result.rowcount == 1:
                return "成交"
        await asyncio.sleep(random.uniform(0.02, 0.1))
    async with Session() as session:
        await session.execute(delete(Order).where(Order.order_no == order_no))
        await session.commit()
    return "重试耗尽(补偿删单)"


async def main() -> None:
    await reset(stock_qty=10)
    users = [f"u{i:02d}" for i in range(1, 21)] + [
        "u03",
        "u07",
    ]  # 20 人,3 号和 7 号手抖点了两次
    log("20 人抢 10 部手机,3 号和 7 号各手抖点了两次……")
    results = await asyncio.gather(*(buy(user) for user in users))
    stats = Counter(results)
    async with Session() as session:
        stock = (
            await session.execute(select(Stock).where(Stock.sku == "手机"))
        ).scalar_one()
        orders = len((await session.execute(select(Order.id))).all())
    log(f"结果:{dict(stats)}")
    log(f"库存剩 {stock.qty}(version={stock.version}),订单表 {orders} 条")
    log(
        f"对账:成交 {stats['成交']} + 库存消耗 {10 - stock.qty} = 应为 10;订单 {orders} = 成交数,无一重复"
    )
    await engine.dispose()


asyncio.run(main())
```

```
[11:07:20] 结果:{'成交': 10, '售罄(补偿删单)': 4, '重试耗尽(补偿删单)': 6, '重复提交': 2}
[11:07:20] 库存剩 0(version=10),订单表 10 条
[11:07:20] 对账:成交 10 + 库存消耗 10 = 应为 10;订单 10 = 成交数,无一重复
```

(每个人的成败和分类每轮都不同,但最后两行永远成立——**对账通过才是并发代码的及格线**。)

逐项验证:

- `重复提交: 2` —— u03/u07 的第二击被唯一约束拦下,库里没有他们的第二张单
- `成交: 10` = 库存消耗 10 = 订单表 10 条 —— 没超卖、没少卖、订单和库存对得上
- 失败的 10 人订单全被**补偿删掉**——失败者不留脏数据,下次活动还能买

值得注意的两个设计取舍:

| 决策 | 为什么 |
|---|---|
| 先落单、后扣库存,失败再补偿删单 | 落单(唯一约束)先挡掉重复流量,扣库存的重试只在"新用户"间发生;反过来先扣库存,双击会扣两次 |
| 没用 Redis 锁 | 防重有唯一约束(更强、可对账),扣减有 CAS——Redis 锁在这里没有增量价值。**少一个组件,少一类故障** |

## 3 回到工作项目

把这套思维平移到点众云盘一类的业务系统(MySQL 为主):

| 需求 | 落法 |
|---|---|
| 上传任务、导入任务防重复创建 | 任务表唯一约束(业务键),`INSERT ... ON DUPLICATE KEY UPDATE id = id` 幂等 |
| 文件配额(容量)扣减 | `UPDATE SET used = used + n WHERE used + n <= quota`,一条 SQL |
| 分享链接状态流转(有效→失效) | `UPDATE ... WHERE status = '有效'`,status 即版本 |
| Celery 定时任务多 worker 只跑一份(配合 Celery 教程的 beat) | Redis 锁 fast-fail:任务名做 key,抢不到直接 return |
| 转移文件时同时改源/目标目录行 | `SELECT ... WHERE id IN (a, b) ORDER BY id FOR UPDATE` |

**敲黑板:写并发代码的顺序——先想"能不能一条 SQL",再想"唯一约束兜什么底",然后才轮到悲观/乐观/分布式锁。** 每多一层锁,就多一层等待、超时、死锁的可能性;最好的锁是不需要锁。
