# 第 6 讲 · 选型与综合实战

这一讲只解决一件事：面对一个并发需求，先选**最小且足够**的工具。

## 先选工具，再写代码

| 需求 | 首选 | 一次请求的结果 | 其他请求怎么办 | 总耗时直觉 |
| --- | --- | --- | --- | --- |
| 扣库存、抢名额 | 条件 `UPDATE` | 命中 1 行即成功 | 条件不满足则失败 | 不排队，单次 SQL 的时间 |
| 同一请求不能重复创建 | 唯一约束 | 首次插入成功 | 重复请求被数据库拒绝/忽略 | 不排队 |
| 更新时怕覆盖别人 | 乐观锁 `version` | 版本匹配即成功 | 冲突后重新读取再试 | 不排队；重试会增加时间 |
| 必须“读后判断再写” | `FOR UPDATE` | 拿到行锁后成功 | 等待、快速失败或跳过 | 会排队，取决于前一个事务多长 |
| 多个 worker 领不同任务 | `FOR UPDATE SKIP LOCKED` | 领到一个未锁任务 | 跳过已锁任务，继续找下一个 | worker 可并行 |
| 跨实例的短协调动作 | PG advisory lock / Redis 锁 | 拿到锁才执行 | 立即跳过或等待 | 取决于锁的持有时间 |

记忆口诀：**能用一条 SQL 说清的规则，不要先上锁。**

## 综合案例：报名一次，扣一张票

规则：

1. 同一个 `request_id` 重试多次，只能创建一笔订单。
2. early-bird 只有 3 张，任何时候不能扣成负数。
3. 订单头、明细行、库存、商品销量四件事同生共死。

这里不需要 Redis 锁，也不需要 `FOR UPDATE`。唯一约束负责“只创建一次”，条件更新负责“绝不超卖”，事务负责“一起成功或一起回滚”：

```python
from sqlalchemy import update
from sqlalchemy.dialects.postgresql import insert


class SoldOutError(Exception):
    pass


async def enroll(request_id: str) -> str:
    try:
        async with Session.begin() as session:
            # 第一步：同一个请求只能插入一次
            inserted = await session.scalar(
                insert(Order)
                .values(
                    user_id="u-1",
                    request_id=request_id,
                    total_amount=49900,
                    status="PENDING",
                )
                .on_conflict_do_nothing(index_elements=[Order.request_id])
                .returning(Order.id)
            )

            if inserted is None:
                return "DUPLICATE"  # 重试请求：已有订单，不再扣库存

            # 第二步：有票才扣；rowcount 只能是 0 或 1
            changed = await session.execute(
                update(ProductSku)
                .where(ProductSku.id == 1, ProductSku.stock > 0)
                .values(stock=ProductSku.stock - 1)
            )
            if changed.rowcount != 1:
                raise SoldOutError

            # 第三步：销量 +1，纯 UPDATE 不需要锁
            await session.execute(
                update(Product)
                .where(Product.id == 1)
                .values(sold_count=Product.sold_count + 1)
            )
            # 第四步：明细行，纯 INSERT
            session.add(
                OrderItem(order_id=inserted, sku_id=1, quantity=1, unit_price=49900)
            )

        return "SUCCESS"  # 离开 begin 后事务已提交
    except SoldOutError:
        # 异常离开 begin，订单回滚，销量也不会加
        return "SOLD_OUT"
```

## 实验一：20 个请求同时进来

初始 `stock=3`，20 个请求的 `request_id` 都不同：

```python
import asyncio
import time
from collections import Counter

from sqlalchemy import func, select

from 锁教程.model import Order, OrderItem, Product, ProductSku, Session, reset_lab


async def main():
    await reset_lab()
    prev = time.perf_counter()
    results = await asyncio.gather(*(enroll(f"req-{i:03d}") for i in range(20)))
    print(f"耗时 {time.perf_counter() - prev:.2f}s")
    print(Counter(results))
    async with Session() as session:
        stock = (await session.get(ProductSku, 1)).stock
        sold = (await session.get(Product, 1)).sold_count
        orders = await session.scalar(
            select(func.count()).select_from(Order).where(Order.request_id.notlike("seed-%"))
        )
        items = await session.scalar(
            select(func.count())
            .select_from(OrderItem)
            .join(Order, Order.id == OrderItem.order_id)
            .where(Order.request_id.notlike("seed-%"))
        )
        print(f"终态: stock={stock}, sold_count={sold}, 新建订单数={orders}, 新建明细数={items}")


if __name__ == "__main__":
    asyncio.run(main())
```

真实输出：

```text
耗时 0.37s
Counter({'SOLD_OUT': 17, 'SUCCESS': 3})
终态: stock=0, sold_count=3, 新建订单数=3, 新建明细数=3
```

```text
20 个请求并发执行条件 UPDATE
        │
        ├─ 3 个 UPDATE 命中一行 → SUCCESS
        └─ 17 个 UPDATE 命中零行 → SOLD_OUT（各自新建的订单回滚）

最终：stock = 0，sold_count = 3，订单 3 笔，明细 3 行
```

四个数字互相印证。结果的关键是 `stock > 0` 出现在同一条更新语句里，而不是先 `SELECT` 后在 Python 中 `if stock > 0`。

再把 20 个不同 `request_id` 换成 5 个**相同**的（`enroll("req-same")` × 5）：

```text
Counter({'DUPLICATE': 4, 'SUCCESS': 1})
终态: stock=2, sold_count=1, 新建订单数=1, 新建明细数=1
```

客户端超时后用**相同**的 `request_id` 再试，返回 `DUPLICATE`：不会多一笔订单，也不会再扣一张票。实际接口通常在重复时查询已有订单并返回它，而不只是返回字符串。

## 实验二：什么时候才改用悲观锁？

当“能不能报名”取决于大量必须读出来再计算的规则——会员等级、黑名单、同一用户限购、多个 SKU 之间的组合额度——很难把规则压成一条条件更新，就在短事务内按第 2 讲实验五的模式锁整条链：

```python
from sqlalchemy import select


async def enroll_with_complex_rules(request_id: str) -> str:
    async with Session.begin() as session:
        # 按固定顺序锁完整条读-改-写链：商品 → SKU
        product = await session.scalar(
            select(Product).where(Product.id == 1).with_for_update()
        )
        sku = await session.scalar(
            select(ProductSku).where(ProductSku.id == 1).with_for_update()
        )

        if sku is None or sku.stock <= 0:
            return "SOLD_OUT"

        await asyncio.sleep(0.1)  # 锁内做必须读取后才能判断的复杂规则
        sku.stock -= 1
        product.sold_count += 1
        order = Order(user_id="u-1", request_id=request_id, total_amount=sku.price)
        session.add(order)
        await session.flush()  # 拿 order.id 给明细行用
        session.add(OrderItem(order_id=order.id, sku_id=sku.id, quantity=1, unit_price=sku.price))
    return "SUCCESS"
```

5 个不同 `request_id` 并发，对比实验一的组合版：

```text
悲观锁版×5:   耗时 0.71s   3 SUCCESS + 2 SOLD_OUT
组合版×20:    耗时 0.37s   3 SUCCESS + 17 SOLD_OUT
```

结果一样正确（不超卖、不重复、四表一致），差别在代价：悲观锁版同一 SKU 的请求排队，每个后到者多等约一个持锁事务的长度；组合版谁都不等谁，20 个一起上，靠单条 SQL 的原子性分胜负。**5 个排队 0.71s 跑不过 20 个不排队 0.37s**——这是“能一条 SQL 就不上锁”的量化版本。

先检查 `request_id` 的唯一性或捕获唯一约束异常，仍是生产代码必须补上的部分；这里只展示何时需要行锁。不要在锁内调 HTTP、发消息或慢查询。

## 后台 worker：不要让大家抢同一条订单

创建订单和处理订单是两件事。创建请求写入 `PENDING` 后，多个 worker 用第 2 讲的 `SKIP LOCKED` 各领一条：

```text
worker A ──锁住 order #101──处理 #101──提交
worker B ──跳过 #101，锁住 #102──处理 #102──提交
worker C ──跳过 #101/#102，锁住 #103──处理 #103──提交
```

“整体成功”是**每一笔订单独立**的：`#101` 失败只影响 `#101`。任务处理要设计成可重试、可幂等；锁只解决“同一时刻谁拿到任务”，不解决“任务最终一定完成”。

## 线上出现锁等待时，先做什么

1. 给事务设定合理超时，避免无限等锁：`SET LOCAL lock_timeout = '1s'`。
2. 所有多行更新按同一顺序拿锁（第 2 讲实验五），减少死锁。
3. 记录 `request_id`、事务耗时和受影响行数；这比只记录“拿锁成功”更有用。
4. 对死锁、序列化失败等可重试错误，只在操作幂等时做有限次数重试。
5. 不要在数据库事务或 Redis 锁内调用第三方 HTTP 服务。

排查阻塞的一个 PostgreSQL 查询：

```sql
SELECT pid, pg_blocking_pids(pid), wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

`pg_blocking_pids(pid)` 显示当前会话被哪些会话阻塞。线上执行前按你的数据库权限和监控规范确认范围。

## 最后核对

面对一个新需求，依次问：

1. 这是“不能重复”吗？先想唯一约束。
2. 这是“数值不能越界”吗？先想条件 `UPDATE`。
3. 是“读后判断再写”吗？再考虑乐观锁或 `FOR UPDATE`。
4. 是多 worker 领任务吗？考虑 `SKIP LOCKED`。
5. 是跨实例、数据库外的短协调吗？才考虑 advisory lock 或 Redis 锁。

如果答案是“库存不能超卖”，优先方案仍是：**数据库事务 + 条件更新**，不是 Redis 锁。
