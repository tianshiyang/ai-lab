# 第 6 讲 · 选型与综合实战

这一讲只解决一件事：面对一个并发需求，先选**最小且足够**的工具。

## 先选工具，再写代码

| 需求 | 首选 | 一次请求的结果 | 其他请求怎么办 | 总耗时直觉 |
| --- | --- | --- | --- | --- |
| 扣库存、抢名额 | 条件 `UPDATE` | 命中 1 行即成功 | 条件不满足则失败 | 不排队，单次 SQL 的时间 |
| 同一请求不能重复创建 | 唯一约束 | 首次插入成功 | 重复请求被数据库拒绝/忽略 | 不排队 |
| 更新时怕覆盖别人 | 乐观锁 `version` | 版本匹配即成功 | 冲突后重新读取再试 | 不排队；重试会增加时间 |
| 必须“读后判断再写” | `FOR UPDATE` | 拿到行锁后成功 | 等待、快速失败或跳过 | 会排队，取决于前一个事务多长 |
| 多个 worker 领不同任务 | `FOR UPDATE SKIP LOCKED` | 领到一个未锁任务 | 跳过已锁任务，继续找下一个 | worker 可并行 |
| 跨实例的短协调动作 | PG advisory lock / Redis 锁 | 拿到锁才执行 | 立即跳过或等待 | 取决于锁的持有时间 |

记忆口诀：**能用一条 SQL 说清的规则，不要先上锁。**

## 综合案例：报名一次，扣一个名额

规则：

1. 同一个 `request_id` 重试多次，只能创建一笔订单。
2. 名额只有 3 个，任何时候都不能扣成负数。
3. 创建订单和扣名额必须同时成功或同时回滚。

这里不需要 Redis 锁，也不需要 `FOR UPDATE`。唯一约束负责“只创建一次”，条件更新负责“绝不超卖”，事务负责“二者同生共死”。

```python
from sqlalchemy import update
from sqlalchemy.dialects.postgresql import insert


class SoldOutError(Exception):
    pass


async def enroll(user_id: int, request_id: str) -> str:
    try:
        async with Session.begin() as session:
            # 第一步：同一个请求只能插入一次
            inserted = await session.scalar(
                insert(Order)
                .values(
                    product_id=1,
                    user_id=user_id,
                    request_id=request_id,
                    status="PENDING",
                )
                .on_conflict_do_nothing(index_elements=[Order.request_id])
                .returning(Order.id)
            )

            if inserted is None:
                return "DUPLICATE"  # 重试请求：已有订单，不再扣库存

            # 第二步：有余量才扣减；rowcount 只能是 0 或 1
            changed = await session.execute(
                update(Product)
                .where(Product.id == 1, Product.available > 0)
                .values(available=Product.available - 1)
            )
            if changed.rowcount != 1:
                raise SoldOutError

        return "SUCCESS"  # 离开 begin 后事务已提交
    except SoldOutError:
        # 异常离开 begin，刚才插入的订单也会回滚
        return "SOLD_OUT"
```

### 20 个请求同时进来会怎样？

假设初始 `available = 3`，20 个请求的 `request_id` 都不同：

```text
20 个请求并发执行条件 UPDATE
        │
        ├─ 3 个 UPDATE 命中一行 → SUCCESS
        └─ 17 个 UPDATE 命中零行 → SOLD_OUT（各自新建的订单回滚）

最终：available = 0，订单数 = 3
```

数据库会为每条更新做并发控制；结果的关键是 `available > 0` 出现在同一条更新语句里，而不是先 `SELECT` 后在 Python 中 `if available > 0`。

如果某个客户端超时后用**相同**的 `request_id` 再试，则返回 `DUPLICATE`：不会多一笔订单，也不会再扣一次名额。实际接口通常会在重复时查询已有订单并返回它，而不只是返回字符串。

## 同一个案例，什么时候才改用悲观锁？

当“能不能报名”取决于大量必须读出来再计算的规则，例如：会员等级、黑名单、同一用户限购、多个商品之间的组合额度。此时很难把规则压成一条条件更新，可在短事务内锁住相关行：

```python
from sqlalchemy import select


async def enroll_with_complex_rules(user_id: int, request_id: str) -> str:
    async with Session.begin() as session:
        product = await session.scalar(
            select(Product)
            .where(Product.id == 1)
            .with_for_update()
        )

        if product is None or product.available <= 0:
            return "SOLD_OUT"

        # 这里放“必须读取后判断”的规则；不要在锁内调 HTTP、发消息或慢查询。
        product.available -= 1
        session.add(
            Order(
                product_id=1,
                user_id=user_id,
                request_id=request_id,
                status="PENDING",
            )
        )
    return "SUCCESS"
```

它的代价是同一商品的请求会排队：前一个事务从拿到锁到提交用了 200 ms，后一个请求至少多等约 200 ms。先检查 `request_id` 的唯一性或捕获唯一约束异常，仍然是生产代码必须补上的部分；这里刻意只展示“何时需要行锁”。

## 后台 worker：不要让大家抢同一条订单

创建订单和处理订单是两件事。创建请求写入 `PENDING` 后，多个 worker 可以用第 2 讲的 `SKIP LOCKED` 各领一条：

```text
worker A ──锁住 order #101──处理 #101──提交
worker B ──跳过 #101，锁住 #102──处理 #102──提交
worker C ──跳过 #101/#102，锁住 #103──处理 #103──提交
```

这里的“整体成功”是**每一笔订单独立**的：`#101` 失败只影响 `#101`，不应因为一个 worker 失败就取消另两个已经领走的订单。任务处理要设计成可重试、可幂等；锁只解决“同一时刻谁拿到任务”，不解决“任务最终一定完成”。

## 线上出现锁等待时，先做什么

1. 给事务设定合理超时，避免无限等锁：`SET LOCAL lock_timeout = '1s'`。
2. 所有多行更新按同一顺序拿锁，通常按主键升序，减少死锁。
3. 记录 `request_id`、事务耗时和受影响行数；这比只记录“拿锁成功”更有用。
4. 对死锁、序列化失败等可重试错误，只在操作幂等时做有限次数重试。
5. 不要在数据库事务或 Redis 锁内调用第三方 HTTP 服务。

排查阻塞的一个 PostgreSQL 查询：

```sql
SELECT pid, pg_blocking_pids(pid), wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

`pg_blocking_pids(pid)` 显示当前会话被哪些会话阻塞。线上执行前要先按你的数据库权限和监控规范确认范围。

## 最后核对

面对一个新需求，依次问：

1. 这是“不能重复”吗？先想唯一约束。
2. 这是“数值不能越界”吗？先想条件 `UPDATE`。
3. 是“读后判断再写”吗？再考虑乐观锁或 `FOR UPDATE`。
4. 是多 worker 领任务吗？考虑 `SKIP LOCKED`。
5. 是跨实例、数据库外的短协调吗？才考虑 advisory lock 或 Redis 锁。

如果答案是“库存不能超卖”，优先方案仍是：**数据库事务 + 条件更新**，不是 Redis 锁。
