# 第 4 讲 · 唯一约束——数据库替你把的防重锁

## 0 模型

前几讲锁的是"改",这一讲锁的是"插"——**同一个业务身份只允许落库一次**:

```
   请求甲(支付宝回调)              请求乙(回调重试/用户狂点)
        │ INSERT order_no=SO001          │ INSERT order_no=SO001
        ▼                                ▼
   唯一索引:SO001 不存在            唯一索引:撞上 SO001
        │                                │
        ▼                                ▼
   ✅ 落库                         ❌ 23505 唯一冲突,当场拒绝
```

| 概念 | 一句话 |
|---|---|
| 唯一约束/唯一索引 | 数据库层面的"只此一份",并发插入同一键时必然只成一个 |
| 幂等 | 同一操作做一次和做 N 次,效果相同;唯一约束是幂等的最后防线 |
| 幂等键 | 代表业务身份的唯一键:订单号、支付流水号、"用户+商品"、"任务+日期" |
| ON CONFLICT | PG 的冲突处理子句:`DO NOTHING` 跳过 / `DO UPDATE` 变 upsert |

前两讲的锁保护"改同一行",唯一约束保护"不该有第二行"。**支付、回调、定时任务,任何"可能重放"的入口,唯一约束都是兜底——哪怕上层已经做了防重,表上也要有它。**

## 1 敲代码:`unique_guard.py`

```python
"""两幕:裸插撞唯一约束报错 → ON CONFLICT DO NOTHING 幂等落单。"""

import asyncio
import os
import time
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select
from sqlalchemy.dialects.postgresql import insert as pg_insert
from sqlalchemy.exc import IntegrityError
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Payment(Base):
    __tablename__ = "lock04_payment"

    id: Mapped[int] = mapped_column(primary_key=True)
    order_no: Mapped[str] = mapped_column(
        String(30), unique=True
    )  # 幂等键:同一单只许一笔
    channel: Mapped[str] = mapped_column(String(10))
    amount: Mapped[int]


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def reset() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Payment))


async def insert_naive(tag: str) -> None:
    """回调可能重试、用户可能狂点:两个请求带着同一个 order_no 同时落库。"""
    async with Session() as session:
        session.add(Payment(order_no="SO2026092201", channel=tag, amount=99))
        try:
            await session.commit()
            log(f"{tag} 落库成功")
        except IntegrityError as e:
            await session.rollback()
            reason = e.orig.sqlstate
            log(f"{tag} 被唯一约束拦下(sqlstate={reason}):这一单早已入账")


async def insert_idempotent(tag: str) -> None:
    """幂等写法:撞了不报错,静默跳过,靠 returning 判断自己是首单还是重复。"""
    async with Session() as session:
        stmt = (
            pg_insert(Payment)
            .values(order_no="SO2026092201", channel=tag, amount=99)
            .on_conflict_do_nothing(index_elements=[Payment.order_no])
            .returning(Payment.id)
        )
        row = (await session.execute(stmt)).scalar_one_or_none()
        await session.commit()
        log(f"{tag} {'首单,落库成功' if row else '重复请求,跳过(无任何副作用)'}")


async def main() -> None:
    log("=== 第一幕:支付回调重试,两个请求同单号并发裸插===")
    await reset()
    await asyncio.gather(insert_naive("支付宝"), insert_naive("微信回调重试"))
    async with Session() as session:
        count = len((await session.execute(select(Payment.id))).all())
    log(f"库里最终 {count} 条(唯一约束兜住了,不会重复入账)")

    log("=== 第二幕:同一场景改用 ON CONFLICT DO NOTHING===")
    await reset()
    await asyncio.gather(insert_idempotent("支付宝"), insert_idempotent("微信回调重试"))
    async with Session() as session:
        count = len((await session.execute(select(Payment.id))).all())
    log(f"库里最终 {count} 条:谁先到谁算,后到的安静走开")
    await engine.dispose()


asyncio.run(main())
```

两个写法的分工:

| 写法 | 行为 | 适合 |
|---|---|---|
| 裸插 + 捕获 `IntegrityError` | 冲突**报错**,业务感知后自行处理(记日志/返回"已处理") | 重复本属异常:重复注册、重复建单 |
| `ON CONFLICT DO NOTHING` + `RETURNING` | 冲突**静默跳过**,靠 RETURNING 有无返回行判断自己是不是首单 | 重复属正常:回调重试、消息重投、定时任务重跑 |

PG 的错误码 `23505` = unique_violation(MySQL 是 1062)。`ON CONFLICT DO UPDATE` 则是 upsert:存在就更新,常配合 `SET counter = counter + 1` 做计数器。

**敲黑板:唯一约束是"最后防线",不是"唯一防线"。** 表上有约束,只保证不出现脏数据(重复行);业务层还是要尽量在入口防重(前端按钮置灰、分布式锁、消息幂等表),别把所有压力都怼到数据库报错上。反过来,上层防重做得再花哨,表上没约束,一条重放就穿帮。

## 3 MySQL 对照

| PG | MySQL 等价物 | 注意 |
|---|---|---|
| `ON CONFLICT DO NOTHING` | `INSERT IGNORE`(忽略一切插入错误,太粗)或 `INSERT ... ON DUPLICATE KEY UPDATE id = id`(惯用哑更新) | `INSERT IGNORE` 连数据不合法也忽略,**不推荐** |
| `ON CONFLICT DO UPDATE` | `INSERT ... ON DUPLICATE KEY UPDATE` | 影响行数语义:插入=1,更新=2,没变=0 |
| `RETURNING` 判断首单 | MySQL 无 RETURNING,用 `LAST_INSERT_ID()` 变化或先 `ON DUP UPDATE id=LAST_INSERT_ID(id)` 的老技巧 | 也可以改用影响行数判断 |
| 23505 | 1062(`ER_DUP_ENTRY`) | 两边都是捕获后回滚 |
| `REPLACE INTO` | — | 先删再插,会换主键、丢未列出字段,**别用** |

## 4 锁的内幕:一张脸熟表

企业排查慢查询、死锁、元数据锁等待时,会撞上这些名字。不要求会背,要求**看到不慌、知道谁挡了谁**:

| 锁 | 谁加的 | 挡住谁 | 一句话 |
|---|---|---|---|
| 行锁(记录锁) | UPDATE / DELETE / FOR UPDATE | 其他写者 | 前三讲的主角 |
| 共享锁 S / 排它锁 X | `FOR SHARE` / `FOR UPDATE` | S 挡 X,X 挡 S 和 X | 读读不冲突,读写才冲突 |
| 表锁 | `LOCK TABLE` / DDL | 一切 | DDL 改表时线上 ALTER 卡住的元凶之一 |
| 意向锁 | InnoDB 加行锁前自动加在表上 | 表级操作(如全表写) | "这表里有人锁了行"的路标,不用你管 |
| 间隙锁 Gap Lock | InnoDB **RR 隔离级别**下的写语句/锁定读 | 往间隙里插入的行 | 锁"两行之间的空隙"防幻读;**PG 没有**;死锁高发区 |
| 临键锁 Next-Key | InnoDB RR 默认 | 记录 + 前面的间隙 | 行锁 + 间隙锁的合体 |
| 元数据锁 MDL | 任何查询/DDL | 互相 | 长事务拿着 MDL,ALTER 排队,后续所有查询跟着堵——"一个 select 卡死全表"的经典事故 |

**PG 和 MySQL 最大的分水岭就是间隙锁**:MySQL RR 下 `SELECT ... WHERE id > 100 FOR UPDATE` 会把 (100, +∞) 的"空隙"也锁住,防幻读,代价是插入方被挡、死锁概率上升;PG 选择不加间隙锁,靠 MVCC + 可串行化隔离(SSI)对付幻读。工作的 MySQL 项目里遇到"没改这行却锁等待",先想想是不是踩了间隙。

## 5 亲眼看锁:天眼脚本

第 2 讲我们看到"乙等了 2 秒",那是从外面猜的。`see_locks.py` 三个角色——甲持锁睡觉、乙排队、**丙开天眼查 `pg_stat_activity`,把"谁堵谁"拍在桌子上**:

```python
"""甲持锁睡觉、乙排队等锁、丙开天眼查 pg_stat_activity 看谁堵谁。"""

import asyncio
import os
import time
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select, text
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Account(Base):
    __tablename__ = "lock04_account"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(20))
    balance: Mapped[int]


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def backend_pid(session) -> int:
    return (await session.execute(text("SELECT pg_backend_pid()"))).scalar_one()


async def holder() -> None:
    """甲:锁住 id=1 睡 4 秒,制造一次真实的锁等待。"""
    async with Session() as session:
        pid = await backend_pid(session)
        stmt = select(Account).where(Account.id == 1).with_for_update()
        await session.execute(stmt)
        log(f"甲(pid={pid})已锁住 id=1,开始睡觉 4 秒")
        await asyncio.sleep(4)
        await session.rollback()
        log(f"甲(pid={pid})回滚,放锁")


async def waiter() -> None:
    """乙:晚半秒出发,FOR UPDATE 撞上甲的锁,排队。"""
    await asyncio.sleep(0.5)
    async with Session() as session:
        pid = await backend_pid(session)
        log(f"乙(pid={pid})出发,SELECT FOR UPDATE …… 卡住了")
        stmt = select(Account).where(Account.id == 1).with_for_update()
        await session.execute(stmt)
        log(f"乙(pid={pid})终于拿到锁(甲放锁的瞬间)")


async def observer() -> None:
    """丙:第三方视角,查 pg_stat_activity 看等待关系。"""
    await asyncio.sleep(1.5)
    async with Session() as session:
        rows = (
            await session.execute(
                text(
                    "SELECT pid, state, wait_event_type, wait_event, "
                    "pg_blocking_pids(pid) AS blocked_by, left(query, 45) AS doing "
                    "FROM pg_stat_activity "
                    "WHERE datname = current_database() AND pid <> pg_backend_pid()"
                )
            )
        ).all()
    for row in rows:
        log(
            f"丙看见 pid={row.pid} state={row.state} wait={row.wait_event_type}/{row.wait_event}"
            f" 被谁堵={list(row.blocked_by)} 正在跑={row.doing!r}"
        )


async def main() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Account))
    async with Session() as session:
        session.add(Account(id=1, name="阿花", balance=1000))
        await session.commit()
    await asyncio.gather(holder(), waiter(), observer())
    await engine.dispose()


asyncio.run(main())
```

```

[11:03:44] 甲(pid=847589)已锁住 id=1,开始睡觉 4 秒
[11:03:45] 乙(pid=847590)出发,SELECT FOR UPDATE …… 卡住了
[11:03:46] 丙看见 pid=847589 state=idle in transaction wait=Client/ClientRead 被谁堵=[] 正在跑='SELECT lock04_account.id, lock04_account.name'
[11:03:46] 丙看见 pid=847590 state=active wait=Lock/transactionid 被谁堵=[847589] 正在跑='SELECT lock04_account.id, lock04_account.name'
[11:03:48] 乙(pid=847590)终于拿到锁(甲放锁的瞬间)
[11:03:48] 甲(pid=847589)回滚,放锁
```

天眼的两行就是生产排查的标准姿势:

- 乙 `state=active, wait=Lock/transactionid, 被谁堵=[847589]`——在等行锁,堵它的是甲的 pid
- 甲 `state=idle in transaction`——**SQL 跑完了人却没提交**,拿着锁睡大觉;生产上这个状态往往是"应用里有段代码忘了 commit / 长事务"

线上"接口突然全卡住"的第一反应就是查这张表。MySQL 的对应工具:`SELECT * FROM sys.innodb_lock_waits`(谁等谁、等哪行)、`SHOW ENGINE INNODB STATUS`(最近一次死锁现场)、`performance_schema.metadata_locks`(MDL 等待)。PG 还有 `lock_timeout` 参数可设"等锁超过 N 毫秒就报错",MySQL 对应 `innodb_lock_wait_timeout`(默认 50 秒,偏长)。

## 7 速查表

| 工具/概念 | 位置 | 用途 |
|---|---|---|
| `unique=True` / 唯一索引 | 表定义 | 防重最后防线 |
| `on_conflict_do_nothing(index_elements=[...])` | PG INSERT | 幂等插入 |
| `on_conflict_do_update(...)` | PG INSERT | upsert |
| `IntegrityError` + sqlstate 23505 | 应用层 | 捕获唯一冲突(MySQL:1062) |
| `pg_stat_activity` + `pg_blocking_pids(pid)` | PG | 谁在等、被谁堵 |
| `sys.innodb_lock_waits` | MySQL | 同上 |
