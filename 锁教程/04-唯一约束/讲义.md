# 第 4 讲 · 唯一约束与幂等

用户双击、客户端超时重试、消息重复投递，都会让同一个业务请求到达多次。这里最可靠的第一道防线不是 Redis 锁，而是数据库唯一约束。

## 先分清：它不是锁

```text
悲观锁：让竞争者等待
乐观锁：让竞争者提交时发现版本过期
唯一约束：数据库拒绝第二个相同业务身份
```

`lock_lab_order.request_id` 设置为 `UNIQUE`。同一个请求无论来几次，表中最多一行。

## 用 `ON CONFLICT` 表达“创建或已存在”

```python
from sqlalchemy.dialects.postgresql import insert


async def create_order_once(user_id: str, request_id: str) -> tuple[bool, int | None]:
    async with Session.begin() as session:
        result = await session.execute(
            insert(Order)
            .values(
                product_id=1,
                user_id=user_id,
                request_id=request_id,
                status="PENDING",
            )
            .on_conflict_do_nothing(index_elements=[Order.request_id])
            .returning(Order.id)
        )
        order_id = result.scalar_one_or_none()
        return order_id is not None, order_id
```

两个相同请求并发执行：

```text
请求 A → 插入成功，得到 order_id
请求 B → request_id 冲突，不插入，得到 None
```

这不是错误；它表示“这个业务请求已经被处理过”。真实接口通常还要按 `request_id` 查回原订单，再返回同一份业务结果。

## 订单与扣库存必须同一个事务

如果“创建订单”成功、但“扣名额”失败，不能留下一个假成功订单。把两步放进同一事务：

```python
from sqlalchemy import update
from sqlalchemy.dialects.postgresql import insert


async def enroll(user_id: str, request_id: str) -> str:
    async with Session.begin() as session:
        inserted = await session.execute(
            insert(Order)
            .values(product_id=1, user_id=user_id, request_id=request_id, status="PENDING")
            .on_conflict_do_nothing(index_elements=[Order.request_id])
            .returning(Order.id)
        )
        order_id = inserted.scalar_one_or_none()
        if order_id is None:
            return "DUPLICATE"

        changed = await session.execute(
            update(Product)
            .where(Product.id == 1, Product.available > 0)
            .values(available=Product.available - 1)
        )
        if changed.rowcount != 1:
            raise RuntimeError("SOLD_OUT")  # 事务回滚，订单不会留下

        return "SUCCESS"
```

`RuntimeError` 只是教程中触发回滚的简写；真实项目应使用明确的业务异常，并在事务外转换成接口响应。

## 两个常见误区

| 误区 | 正解 |
| --- | --- |
| 先查“订单是否存在”，再插入 | 两个请求可能都查到不存在；必须靠唯一约束兜底 |
| 用 Redis 锁防重复提交 | 网络、超时、锁过期都会让它复杂；业务身份应由数据库唯一约束定义 |
