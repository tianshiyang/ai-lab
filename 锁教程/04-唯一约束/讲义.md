# 第 4 讲 · 唯一约束与幂等

用户双击、客户端超时重试、消息重复投递，都会让同一个业务请求到达多次。这里最可靠的第一道防线不是 Redis 锁，而是数据库唯一约束。

## 先分清：它不是锁

```text
悲观锁：让竞争者等待
乐观锁：让竞争者提交时发现版本过期
唯一约束：数据库拒绝第二个相同业务身份
```

`lock_lab_order.request_id` 设置为 `UNIQUE`。同一个请求无论来几次，表中最多一行。

## 实验一：先查后插，在并发下形同虚设

最常见的防重写法是“先查订单是否存在，不存在再插”。两个相同 `request_id` 的请求并发进来，实测会发生什么。完整文件：

```python
import asyncio

from sqlalchemy import func, select
from sqlalchemy.exc import IntegrityError

from 锁教程.model import Order, OrderItem, Product, ProductSku, Session, reset_lab


async def create_order_naive(name: str, request_id: str) -> str:
    try:
        async with Session.begin() as session:
            exists = await session.scalar(
                select(func.count()).select_from(Order).where(Order.request_id == request_id)
            )
            await asyncio.sleep(0.2)  # 查完到插入之间的处理窗口
            if exists:
                return f"{name}: 查到已有订单, 跳过"
            session.add(Order(user_id="u-1", request_id=request_id, total_amount=49900))
            return f"{name}: 创建订单"
    except IntegrityError:
        return f"{name}: 插入被唯一约束拒绝(IntegrityError)"


async def main():
    await reset_lab()
    results = await asyncio.gather(
        create_order_naive("请求A", "req-001"),
        create_order_naive("请求B", "req-001"),
    )
    print(results)
    async with Session() as session:
        count = await session.scalar(
            select(func.count()).select_from(Order).where(Order.request_id == "req-001")
        )
        print(f"req-001 订单数 = {count}")


if __name__ == "__main__":
    asyncio.run(main())
```

真实输出：

```text
['请求A: 创建订单', '请求B: 插入被唯一约束拒绝(IntegrityError)']
req-001 订单数 = 1
```

两个请求**都**查到“不存在”，然后都去插入。拦住第二笔的不是那句 `SELECT`，是表上的唯一约束——`request_id` 没建 `UNIQUE` 的话，表里现在已有两笔 `req-001`。约束把“重复订单”这个数据事故变成一次报错；但让用户请求以异常收场（线上就是 500）不体面，实验二把它变成正常的业务返回。

## 实验二：`ON CONFLICT` 表达“创建或已存在”

```python
from sqlalchemy.dialects.postgresql import insert


async def create_order_once(name: str, request_id: str) -> str:
    async with Session.begin() as session:
        result = await session.execute(
            insert(Order)
            .values(user_id="u-1", request_id=request_id, total_amount=49900, status="PENDING")
            .on_conflict_do_nothing(index_elements=[Order.request_id])
            .returning(Order.id)
        )
        order_id = result.scalar_one_or_none()
        if order_id is None:
            return f"{name}: DUPLICATE(订单已存在)"
        return f"{name}: SUCCESS order_id={order_id}"
```

`main()` 里两个协程换成 `create_order_once`：

```text
['请求A: DUPLICATE(订单已存在)', '请求B: SUCCESS order_id=94']
req-001 订单数 = 1
```

`on_conflict_do_nothing`：撞约束时数据库什么都不做也不报错，`returning` 拿到 `None` 就是“这个业务请求已被处理过”。哪边插入成功每次不一定（这轮是 B 抢到、A 拿 DUPLICATE），验收看结果组合和订单数。真实接口通常还要按 `request_id` 查回原订单，返回同一份业务结果。

| 写法 | 第二个相同请求的下场 |
| --- | --- |
| 没有唯一约束 | 两笔订单都落库（数据事故） |
| 有约束，裸插 | `IntegrityError`（接口 500） |
| 有约束 + `ON CONFLICT` | 返回 `DUPLICATE`（业务结果） |

## 实验三：订单、明细、库存、销量必须同一个事务

下单同时做四件事：插入订单头、插入明细行、SKU 扣库存、商品销量加一。任何一步失败，四件事都不能留痕：

```python
from sqlalchemy import update


class SoldOutError(Exception):
    pass


async def enroll(name: str, request_id: str) -> str:
    try:
        async with Session.begin() as session:
            inserted = await session.scalar(
                insert(Order)
                .values(user_id="u-1", request_id=request_id, total_amount=49900, status="PENDING")
                .on_conflict_do_nothing(index_elements=[Order.request_id])
                .returning(Order.id)
            )
            if inserted is None:
                return f"{name}: DUPLICATE"

            changed = await session.execute(
                update(ProductSku)
                .where(ProductSku.id == 1, ProductSku.stock > 0)
                .values(stock=ProductSku.stock - 1)
            )
            if changed.rowcount != 1:
                raise SoldOutError  # 异常离开 begin：订单、明细、销量全部回滚

            await session.execute(
                update(Product)
                .where(Product.id == 1)
                .values(sold_count=Product.sold_count + 1)
            )
            session.add(
                OrderItem(order_id=inserted, sku_id=1, quantity=1, unit_price=49900)
            )
            return f"{name}: SUCCESS order_id={inserted}"
    except SoldOutError:
        return f"{name}: SOLD_OUT(订单已回滚)"
```

5 个**不同** `request_id` 并发（early-bird 只有 3 张）：

```text
['请求1: SUCCESS order_id=101', '请求2: SUCCESS order_id=102', '请求3: SOLD_OUT(订单已回滚)',
 '请求4: SOLD_OUT(订单已回滚)', '请求5: SUCCESS order_id=103']
终态: stock=0, sold_count=3, 新建订单数=3, 新建明细数=3
```

终态四个数字互相印证：扣 3 张票（stock=0）、销量加 3（sold_count=3）、订单 3 笔、明细 3 行。`SOLD_OUT` 的两个请求**订单头和明细行全部回滚**——订单数是 3 不是 5。

再换 5 个**相同** `request_id` 并发：

```text
{'SUCCESS order_id=111': 1, 'DUPLICATE': 4}
终态: stock=2, sold_count=1, 新建订单数=1, 新建明细数=1
```

只创建一笔订单、只扣一张票、销量只加一。四张表四种工具各司其职：订单靠唯一约束管身份，库存靠条件 `UPDATE` 管不超卖，销量是纯 `UPDATE` 自带队列；`FOR UPDATE` 一次都没用。

## 两个常见误区

| 误区 | 正解 |
| --- | --- |
| 先查“订单是否存在”，再插入 | 两个请求可能都查到不存在；必须靠唯一约束兜底 |
| 用 Redis 锁防重复提交 | 网络、超时、锁过期都会让它复杂；业务身份由数据库唯一约束定义 |

## 练习

把 `create_order_once` 改成真实接口语义：`DUPLICATE` 时按 `request_id` 查回原订单、返回**同一个** `order_id`。验收：两次并发调用加一次串行重放，三次拿到的订单号完全相同，表中 `req-001` 仍只有一行。
