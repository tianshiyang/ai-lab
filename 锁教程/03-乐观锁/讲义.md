# 第 3 讲 · 乐观锁：version CAS 与重试

乐观锁不先占住数据库行。它假设冲突相对少：先读数据，提交时再问数据库“我读到的还是这个版本吗？”

## 核心 SQL

```sql
UPDATE lock_lab_product
SET available = :new_available,
    version = version + 1
WHERE id = 1
  AND version = :old_version;
```

| `rowcount` | 含义 |
| --- | --- |
| `1` | 本次更新成功，旧版本仍有效 |
| `0` | 别人已经抢先修改，当前快照过期 |

`rowcount == 0` 是**并发冲突**，不是 SQL 执行失败。

## Python 写法

```python
from sqlalchemy import select, update


async def reserve_once() -> str:
    async with Session() as session:
        product = (
            await session.execute(select(Product).where(Product.id == 1))
        ).scalar_one()

        if product.available < 1:
            return "SOLD_OUT"

        result = await session.execute(
            update(Product)
            .where(Product.id == 1, Product.version == product.version)
            .values(
                available=product.available - 1,
                version=product.version + 1,
            )
        )
        await session.commit()
        return "SUCCESS" if result.rowcount == 1 else "CONFLICT"
```

## 重试必须有边界

```python
import asyncio
import random


async def reserve_with_retry() -> str:
    for attempt in range(3):
        outcome = await reserve_once()
        if outcome != "CONFLICT":
            return outcome
        await asyncio.sleep(random.uniform(0.01, 0.05) * (attempt + 1))
    return "BUSY"
```

只对 `CONFLICT` 重试；不要把网络错误、约束错误、编程错误全吞掉然后重试。高热点行上大量 CAS 重试会形成重试风暴，此时应考虑第 1 讲的条件 UPDATE 或第 2 讲的短事务悲观锁。

## 乐观锁、条件 UPDATE、悲观锁怎么选

| 情况 | 选什么 |
| --- | --- |
| 只需扣库存 / 改状态 | 条件 UPDATE，最简单 |
| 先读后做复杂计算，冲突少 | version CAS |
| 先读后做复杂计算，冲突很高且必须串行 | `FOR UPDATE` |

## 练习
