# 第 3 讲 · 乐观锁——版本号与重试

## 0 模型

乐观锁的思想一句话:**假设冲突很少发生,先干活,提交时核对版本号,输了就重试**。

```
   买家A                                    买家B
     │ SELECT qty=5, version=0
     ▼
   本地算:买 1 件,扣到 4               SELECT qty=5, version=0
     │                                    │ 本地算:买 1 件,扣到 4
     ▼                                    ▼
   UPDATE ... SET qty=4, version=1      UPDATE ... SET qty=4, version=1
     WHERE id=1 AND version=0             WHERE id=1 AND version=0
     → rowcount=1 ✅ 成交                 → rowcount=0 ❌ 版本对不上
                                          │
                                          ▼ 重读(qty=4,version=1)再试
                                          UPDATE ... WHERE version=1 → ✅
```

| 术语 | 一句话 |
|---|---|
| 乐观锁 | 不真正加锁,提交时用条件(WHERE version=旧值)验证"我读的还在不在" |
| CAS | Compare-And-Swap,比较并交换;数据库里就是"条件 UPDATE + 看 rowcount" |
| version 列 | 每次修改 +1 的整数列,行数据的"代数" |
| 重试/退避 | 冲突后重读重算再提交;退避 = 等一小段再试,带随机抖动防止扎堆 |

---

## 1 和悲观锁的取舍

| 维度 | 悲观锁 FOR UPDATE | 乐观锁 version |
|---|---|---|
| 冲突处理 | 先锁,后来者**排队** | 各干各的,冲突者**重试** |
| 数据库连接 | 持锁期间占着连接干等 | 失败立即返回,连接马上还 |
| 冲突频繁时 | 排队,公平,稳 | 重试风暴,越挤越乱 |
| 冲突稀少时 | 白锁一场 | 几乎零开销 |
| 死锁 | 可能 | 不可能(没有持锁等待) |
| 典型场景 | 账户、热点行、秒杀库存 | 后台改配置、订单状态流转、低频更新 |

**一句话选型:写多冲突密 → 悲观;读多写少 → 乐观。** 界于两者之间的,两个都试试,看压测数据。

## 2 敲代码:`optimistic.py` 三连

脚本一幕复现超卖,二幕用**条件 UPDATE**(最轻量的乐观锁)治,三幕上**通用版 version CAS**。开头骨架和第 1 讲相同(表换成带 version 列的库存表),全文如下:

```python
"""三幕:无锁抢购卖超 → 条件 UPDATE 防超卖 → version CAS 带重试。"""

import asyncio
import os
import random
import time
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select, update
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Stock(Base):
    __tablename__ = "lock03_stock"

    id: Mapped[int] = mapped_column(primary_key=True)
    sku: Mapped[str] = mapped_column(String(20))
    qty: Mapped[int]
    version: Mapped[int] = mapped_column(default=0)


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)


async def reset(qty: int) -> None:
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Stock))
    async with Session() as session:
        session.add(Stock(id=1, sku="手机", qty=qty))
        await session.commit()


async def read_qty(session) -> tuple[int, int]:
    row = (
        await session.execute(select(Stock.qty, Stock.version).where(Stock.id == 1))
    ).one()
    return row.qty, row.version


async def buy_naive(buyer: str) -> None:
    """无锁版:读到啥就写回啥-1,读和写之间没有守门员。"""
    async with Session() as session:
        qty, _ = await read_qty(session)
        await asyncio.sleep(0.5)  # 制造大家都读到同一个数的窗口
        await session.execute(update(Stock).where(Stock.id == 1).values(qty=qty - 1))
        await session.commit()
        log(f"{buyer} 买到!(库存 {qty} → {qty - 1})")


async def buy_conditional(buyer: str) -> bool:
    """条件更新版:扣减条件写进 WHERE,超卖在 SQL 层就被挡下。"""
    async with Session() as session:
        result = await session.execute(
            update(Stock).where(Stock.id == 1, Stock.qty >= 1).values(qty=Stock.qty - 1)
        )
        await session.commit()
        ok = result.rowcount == 1
        log(f"{buyer} {'买到' if ok else '没抢到:库存不够'}")
        return ok


async def buy_cas(buyer: str, max_retries: int = 5) -> bool:
    """version CAS 版:改之前核对版本号,对不上说明被人抢先,重读重试。"""
    for attempt in range(1, max_retries + 1):
        async with Session() as session:
            qty, version = await read_qty(session)
            if qty < 1:
                log(f"{buyer} 第 {attempt} 次读:库存 0,收手")
                return False
            result = await session.execute(
                update(Stock)
                .where(Stock.id == 1, Stock.version == version)
                .values(qty=qty - 1, version=version + 1)
            )
            await session.commit()
            if result.rowcount == 1:
                log(f"{buyer} 第 {attempt} 次尝试成功,买到")
                return True
        # 版本被人改了:退避一小段(带随机抖动,别扎堆重试),再战
        await asyncio.sleep(random.uniform(0.05, 0.2))
    log(f"{buyer} 重试 {max_retries} 次都没抢到,放弃")
    return False


async def main() -> None:
    buyers = [f"买家{i:02d}" for i in range(1, 11)]

    log("=== 第一幕:10 人抢 5 部手机,无锁读-改-写===")
    await reset(5)
    await asyncio.gather(*(buy_naive(b) for b in buyers))
    async with Session() as session:
        qty, _ = await read_qty(session)
    log(f"终局:库存 {qty}(卖了 10 单,库存只从 5 变 {qty},超卖了 {-qty} 部)")

    log("=== 第二幕:条件 UPDATE ... WHERE qty >= 1===")
    await reset(5)
    results = await asyncio.gather(*(buy_conditional(b) for b in buyers))
    async with Session() as session:
        qty, _ = await read_qty(session)
    log(f"终局:库存 {qty},成交 {sum(results)} 单,不多卖一部")

    log("=== 第三幕:version CAS + 重试===")
    await reset(5)
    results = await asyncio.gather(*(buy_cas(b) for b in buyers))
    async with Session() as session:
        qty, version = await read_qty(session)
    log(f"终局:库存 {qty},version={version},成交 {sum(results)} 单")
    await engine.dispose()


asyncio.run(main())
```

三幕看三层:

- **第一幕**:10 个人都读到 5,都写 4——卖了 10 部,库存只少 1,还倒欠 4 部

- **第三幕**:抢到的 5 人每次提交 version+1;没抢到的发现版本变了,重读——发现 qty=0,识相收手

## 4 三种武器的关系

| | 条件 UPDATE | version CAS | 悲观锁(上一讲) |
|---|---|---|---|
| 需要额外列 | 不用 | version 列 | 不用 |
| 能做的计算 | 仅"自身增减 + 自身条件" | **任意复杂**:新值可以依赖多字段、多表查询结果 | 任意复杂 |
| 失败后 | 没得重试(条件不满足就是业务失败) | 重读重算重试 | 排队,不失败 |
| 适用 | 库存/余额扣减 | 复杂读-改-写(改价、改配置、状态流转) | 热点行、强实时 |

**企业里最常用的一招其实介于两者之间:状态条件 UPDATE,连 version 列都不用。** 订单状态机的每次流转都拿"当前状态"当版本:

```sql
UPDATE orders SET status = '已发货' WHERE id = 1001 AND status = '待发货';
-- rowcount=0 → 订单已不处于待发货(被取消/已发货),别硬发
```

status 本身就是天然的版本号。**改之前问问自己:这张表有没有一个字段天然代表"我读到的那一版"?**

## 5 重试的门道

`buy_cas` 里三个细节,生产代码都少不了:

| 细节 | 为什么 |
|---|---|
| `max_retries` 上限 | 冲突极频繁时无限重试 = 白白烧 CPU;到上限就抛"操作太频繁,请稍后再试"(工作项目里就是抛 `BizException`) |
| 退避 `sleep(random.uniform(...))` | 失败后等一小段再试;**随机抖动**让挤在同一时刻的失败者错峰,否则永远一起失败 |
| 重试要"从头重读" | 重试用最新数据重新走业务逻辑,不是把旧值再写一遍 |

**敲黑板:乐观锁的成本公式——冲突率低时接近免费,冲突率高时重试风暴比排队惨得多。** 所以秒杀这种人人抢同一行的场景,教科书反而推荐悲观锁(或第 6 讲的综合方案);乐观锁的主场是"偶尔两个人同时改"的场景。

顺带一句 ABA 问题:线程世界的 CAS 会遇到"值从 A 改成 B 又改回 A,你以为没变过"。数据库整行 + 单调递增 version 天然免疫(version 永不回头);但用业务字段当版本(如上面的 status)时要小心"A→B→A"的环——状态机设计成有向无环就行。

## 6 MySQL 对照

| 点 | PostgreSQL | MySQL(InnoDB) |
|---|---|---|
| 条件 UPDATE / version UPDATE | 语法完全一致 | 一致 |
| rowcount 判断 | `result.rowcount` | 一致(Connector 默认返回受影响行数;注意 `useAffectedRows` 连接参数要开,否则返回"匹配行数") |
| UPDATE 中读自身旧值 | `SET qty = qty - 1` 基于锁下最新值 | 一致 |
| 常用替代 | `ON CONFLICT DO UPDATE`(第 4 讲) | `ON DUPLICATE KEY UPDATE` / `UPDATE ... LIMIT 1` |

## 8 速查表

| 写法 | 一行判断 |
|---|---|
| `UPDATE t SET x = x - n WHERE id = ? AND x >= n` | 扣减防超卖,首选 |
| `UPDATE t SET x = 新值, version = version + 1 WHERE id = ? AND version = 读到的version` | 复杂读-改-写,rowcount=0 则重试 |
| `UPDATE t SET status = 新 WHERE id = ? AND status = 旧` | 状态机流转,status 即版本 |
| 重试循环 | 上限 + 退避 + 抖动 + 从头重读 |
