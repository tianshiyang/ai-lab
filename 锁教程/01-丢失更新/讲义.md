# 第 1 讲 · 丢失更新——一切问题的起点

## 0 模型

一个 Web 服务同时接到两个请求,都要改**同一行**数据:

```
                 lock01_account 表(id=1 阿花,balance=1000)
                          ▲
        时刻      任务甲          任务乙
        ─────    ──────          ──────
        t0       SELECT 读到 1000
        t0+ε                     SELECT 读到 1000   ← 也读到 1000!
        t1       算出 1100
        t2       UPDATE 写 1100,提交
        t3                       算出 1100
        t4                       UPDATE 写 1100,提交  ← 甲的 100 被覆盖
                          ▼
                 最终 balance = 1100(期望 1200,丢了 100)
```

| 概念 | 一句话 |
|---|---|
| 竞态条件 | 结果取决于几个并发操作谁先谁后,而顺序不受你控制 |
| 临界区 | 读到写之间这段"基于旧值做计算"的窗口 |
| 丢失更新 | 后提交的事务把先提交的事务的修改整个覆盖掉 |
| 读-改-写 | 应用层最常见的数据操作形态:SELECT → 业务计算 → UPDATE |

数据库没坏,单看每个任务每一步都对——坏在**两个任务的临界区重叠了**。这一讲先把事故亲手造出来,后面五讲全是解法。

---

## 1 为什么"睡 1 秒"能模拟真实业务

演示代码里读写之间会 `sleep(1)`,你会觉得"真实代码没睡觉,不至于吧"。其实真实业务里这段窗口天然存在,而且往往更长:

| 真实场景 | 临界区里在干什么 |
|---|---|
| 转账 | 读完余额,先调风控接口、算手续费,再写回 |
| 订单改价 | 读完订单,等运营在后台点确认 |
| 库存扣减 | 读完库存,先校验优惠卷、积分,再扣 |

只要"读"和"写"之间有任何耗时,两个请求的窗口就可能重叠。sleep 只是把窗口钉在 1 秒,让事故每次必现。

## 2 敲代码

完整脚本 `lost_update.py`,存到 `锁教程/01-丢失更新/`,下面分三段给出——**按顺序敲进同一个文件,段与段之间空两行**。开头十几行(加载 .env、建表、引擎、会话工厂)是**全教程每一讲的固定骨架**,后面各讲只是换表换逻辑:

```python
"""第一幕:读-改-写丢钱;第二幕:单条原子 UPDATE 不丢。"""

import asyncio
import os
import time
from pathlib import Path

from dotenv import load_dotenv
from sqlalchemy import String, delete, select, update
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

load_dotenv(Path(__file__).parents[2] / ".env")
DATABASE_URL = os.environ["DATABASE_URL"]


def log(message: str) -> None:
    print(f"[{time.strftime('%H:%M:%S')}] {message}", flush=True)


class Base(DeclarativeBase):
    pass


class Account(Base):
    __tablename__ = "lock01_account"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(20))
    balance: Mapped[int]


engine = create_async_engine(DATABASE_URL)
Session = async_sessionmaker(engine, expire_on_commit=False)
```

| 骨架件 | 作用 |
|---|---|
| `load_dotenv(parents[2] / ".env")` | 从脚本往上跳两级到仓库根读连接串,和 RabbitMQ 教程同一招 |
| `Base` + `__tablename__` | SQLAlchemy 声明式表;`Mapped[int]` 自动推导类型 |
| `create_async_engine` | 进程级连接池,建一次,全脚本共用 |
| `async_sessionmaker` | 会话工厂;**每个任务自己开一个会话**,就是"两个独立请求" |

然后是第一幕的主角——"读-改-写"版入账:

```python
async def reset() -> None:
    """建表并把阿花的余额重置为 1000。"""
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
        await conn.execute(delete(Account))
    async with Session() as session:
        session.add(Account(id=1, name="阿花", balance=1000))
        await session.commit()
    log("重置完成:阿花余额 1000")


async def read_balance(session) -> int:
    result = await session.execute(select(Account.balance).where(Account.id == 1))
    return result.scalar_one()


async def earn(who: str, amount: int) -> None:
    """模拟一次入账:先读余额,睡 1 秒(真实业务这里是调外部接口/算费率),再写回。"""
    async with Session() as session:
        balance = await read_balance(session)
        log(f"{who} 读到余额 {balance}")
        await asyncio.sleep(1)
        new_balance = balance + amount
        await session.execute(
            update(Account).where(Account.id == 1).values(balance=new_balance)
        )
        await session.commit()
        log(f"{who} 写回 {new_balance} 并提交")
```

注意 `earn` 里算 `new_balance` 用的是**自己 1 秒前读到的旧值**,这就是事故的种子。第二幕换成单条 SQL,把加法**下放到 SQL 里**:

```python
async def main() -> None:
    log("=== 第一幕:两笔入账各 +100,应该得到 1200===")
    await reset()
    await asyncio.gather(earn("任务甲", 100), earn("任务乙", 100))
    async with Session() as session:
        final = await read_balance(session)
    log(f"最终余额:{final}  (期望 1200,少了个 {1200 - final})")

    log("=== 第二幕:改成单条 UPDATE balance = balance + 100===")

    async def earn_atomic(who: str, amount: int) -> None:
        async with Session() as session:
            await session.execute(
                update(Account)
                .where(Account.id == 1)
                .values(balance=Account.balance + amount)
            )
            await session.commit()
            log(f"{who} 单条原子 UPDATE +{amount} 提交")

    await reset()
    await asyncio.gather(earn_atomic("任务甲", 100), earn_atomic("任务乙", 100))
    async with Session() as session:
        final = await read_balance(session)
    log(f"最终余额:{final}  (期望 1200,这次对了)")
    await engine.dispose()


asyncio.run(main())
```

**值不值得做的实验**:把 `asyncio.sleep(1)` 改成 `asyncio.sleep(0.05)`,多跑几次——有时对有时错。真实生产的事故就是这样:**测试环境单线程跑没事,大促一并发就丢**,还时好时坏,极难排查。

## 4 为什么单条 UPDATE 就安全

```sql
UPDATE lock01_account SET balance = balance + 100 WHERE id = 1;
```

数据库执行一条 UPDATE 时:

1. 找到 id=1 这一行,**给这行上行级锁**(别的 UPDATE 想改这行,排队等);
2. 基于**锁保护下的最新值**计算 `balance + 100`;
3. 写入,语句结束时锁仍持有到事务提交(第 2 讲展开),后到的那条 UPDATE 等前一条提交后,**重新读最新值再算**。

关键差别:第一幕"读"和"写"是**两次独立的数据库交互**,中间门是开的;第二幕读、算、写发生在**一条语句内**,数据库自己保证不可分割。这就是"原子"的本义。

| | 第一幕:应用层读-改-写 | 第二幕:单条 UPDATE |
|---|---|---|
| 交互次数 | SELECT + UPDATE 两次 | 一次 |
| 计算在哪 | Python 里,基于旧值 | 数据库里,基于锁下最新值 |
| 并发结果 | 丢失更新 | 排队累加,正确 |
| 适合 | 改动逻辑复杂、需要业务判断 | 纯数字增减、状态置位 |

**敲黑板:能一条 SQL 解决的,绝不在应用层拆成"读-改-写"。** 余额增减、库存扣减、计数器、状态流转,先想"能不能塞进一条 UPDATE 的 SET 和 WHERE"。塞不进去(要查别的表、要调外部接口、要复杂校验),才轮到后面几讲的锁。

## 5 MySQL 对照

这套实验在 PostgreSQL 上跑,工作的 MySQL(InnoDB)结论完全一致:

| 点 | PostgreSQL | MySQL(InnoDB) |
|---|---|---|
| 单条 UPDATE 原子 | ✅ | ✅,语句执行期间持行锁 |
| 应用层读-改-写丢更新 | ✅ 会丢 | ✅ 会丢(RR 隔离级别下普通 SELECT 是快照读,同样读到旧值) |
| 默认隔离级别 | Read Committed | Repeatable Read |

差异细节(间隙锁、锁定读在 RR 下的行为)到第 4 讲统一讲,先记住:**丢失更新是应用层的病,什么数据库都救不了你,只能靠写法或锁**。

## 7 速查表

| 写法 | 安全性 | 说明 |
|---|---|---|
| SELECT → 业务算 → UPDATE(应用层) | ❌ 并发丢更新 | 本讲第一幕 |
| `UPDATE ... SET x = x + n` | ✅ | 单语句原子,数字增减首选 |
| `UPDATE ... SET x = x - n WHERE x >= n` | ✅ 且防超卖 | 条件写进 WHERE,第 3 讲 |
| `SELECT ... FOR UPDATE` 再改 | ✅ | 悲观锁,第 2 讲 |
| version 列比对再改 | ✅ | 乐观锁,第 3 讲 |
